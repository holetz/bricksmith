## Problem

Reproduced 2026-10-17 by the epic #47 correctness review on main (6f3ef40), range 77e04d9..6f3ef40.

- Grain check with duplicate date keys, limit 5: `({'d': date(2024,10,1)}, {'d': date(2024,9,1)})` — dates fall to the `repr` fallback, so `'10' < '9'`.
- accepted_values over `[5.0, nan, 2.0, 3.0]` gives `(5.0, nan, 2.0, 3.0)`, unsorted; the same values starting with `nan` give `(nan, 2.0, 3.0, 5.0)`: NaN breaks Python's sort, so the sample depends on input order.

Cause: `src/bricksmith/quality/checks_rows.py:36-44` (the sort key added by #53). Spark `orderBy` sorts dates chronologically and NaN as largest (read, not run).

Consequence: #53/#48 promise row/Spark parity on sample content and order; it fails for date/timestamp keys and NaN whenever `sample_limit` truncates, and NaN makes row samples nondeterministic. Nulls-first must stay.

## Proposal

- Row-engine truncated samples order dates by calendar value and timestamps by instant, as Spark `orderBy` does, instead of by `repr` text.
- NaN sorts after every other number, so an `accepted_values` sample no longer depends on input order.
- Nulls stay first (#53); numbers, strings and the existing fallback order are unchanged.

## Out of Scope

- Spark-side changes: Spark already orders dates and NaN correctly (read, not run).
- Mixed-type columns: a column holds one type in Spark, so cross-type order stays the existing type-rank fallback.

## Impact

### Product code this spec expects to touch

- `src/bricksmith/quality/checks_rows.py` - the `_value_key` sort key.
- `tests/unit/quality/test_checks.py` - regression tests for dates, timestamps and NaN.

## Validation

- `uv run pytest tests/unit/quality/test_checks.py` passes, including new tests that fail on the base: date keys `2024-10-01`/`2024-09-01` truncated to 1 sample give September; accepted values `[5.0, nan, 2.0, 3.0]` give the same sample as `[nan, 2.0, 3.0, 5.0]`.
- `uv run ruff check`, `uv run ruff format --check`, `uv run pyright` and the full `uv run pytest` stay green.

## Design

Decision (durable rule): the row-engine sort key mirrors Spark ascending order per value class: null, then numbers by value with NaN last, strings, dates by ordinal, timestamps by UTC instant (naive values read as UTC), then the type/text fallback. Per #47 policy this keeps #53's nulls-first order. Alternative weighed: normalizing only NaN and leaving dates on `repr`; rejected because dates are the reported parity break. Aware and naive datetimes are normalized to naive UTC so comparison never raises.

## Alternatives Considered

- Sort with a Spark-collected order: rejected, the row engine is the local reference and must not need Spark.

## Open Decisions

- none - Spark's NaN-largest and chronological date order are the stated contract; nulls-first is fixed by #53.

## Risks

- Mixed naive and aware datetimes in one column: mitigated by normalizing to naive UTC. ACCEPTED - a naive value is assumed UTC, which only affects tie-ordering between naive and aware.
- Decimal NaN: `value != value` also covers `Decimal('NaN')`, tested via float only.
