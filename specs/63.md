## Problem

Data teams already run per-domain workflows (bundle, MLOps, analysis) as private Claude Code commands; the generic part belongs in bricksmith and must run as harness-independent agents. Extract the generic versions as bricksmith agents, leaving vocabulary and parameters to a private overlay. Depends on quenching's harness-independent agent format (forge epic S12).

Member S24 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- Three harness-independent Omnigent agent bundles exist under `plugins/bricksmith-omnigent/agents/`: `bricksmith-bundle`, `bricksmith-mlops` and `bricksmith-analysis`, each a `config.yaml` plus `instructions.md` in the S12 format (`spec_version: 1`, executor `omnigent`, one deny-only CEL policy).
- Each bundle operates only bricksmith's public CLI (`bricksmith <group> <verb>`) and the project's own files; it names no catalog, schema, workspace, host, prefix or organization.
- Each bundle grants the minimum: read-only file tools plus a shell limited to a fixed list of non-mutating `bricksmith` verbs. Write, edit, web, delegation and every mutating or applying verb are denied.
- Vocabulary and parameters are left to an overlay: the bundles point at `bricksmith.toml`, `BRICKSMITH_*` variables and the overlay's `agents/*.json` slot, and carry none of their own values.
- A synthetic dry run proves each agent with no model call: stdlib-only tests load each bundle, run synthetic tool-call events through the exact policy expression and assert allowed and denied calls, plus a leak scan of the bundle files.

## Out of Scope

- Generating bundles from a source tree (the quenching `sync_omnigent_plugin.py` flow): bricksmith has no command source to translate, and the three bundles are authored, not derived. Ruled out to avoid a generator for three files.
- Mutating workflows (`model train|register|promote|rollback|retire`, `run … --apply`, `experiment … --apply`, `schema` changes, `monitor fit --out`, `catalog render --output`): wider than a minimal grant; a human decision, parked as an open decision.
- The Claude Code plugin `plugins/bricksmith/` of the delivery contracts: a different surface (skills), owned by other slices.
- Any CI workflow change, new dependency or `pyproject.toml` change: the tests run under the existing `pytest` job with the standard library only.
- Private overlay content, real organization names, and the private commands the epic's Problem alludes to.
- Hosting, publishing or running the bundles on an Omnigent server, and any model-quality evaluation (no model call, no paid eval).

## Design

Decisions, as durable rules:

- **Location.** Bundles live in `plugins/bricksmith-omnigent/agents/<id>/`, mirroring `plugins/quenching-omnigent/agents/<id>/` of quenching (S12). They are outside `src/`, so the wheel and `scripts/verify_dist.py` are unaffected (decision 0009: one distribution).
- **Format (S12).** `config.yaml` carries `spec_version: 1`, `name`, `description`, `instructions: instructions.md`, `executor: {type: omnigent, config: {harness: opencode}}` (the loader requires one; `omnigent run --harness X --model Y` overrides it and no model is pinned), `os_env: {type: caller_process, cwd: .}` and `guardrails.policies.source_tools` with `omnigent.policies.builtins.cel.cel_policy`. No `spawn`.
- **Deny-only.** Omnigent has no positional allow list and a DENY outranks ALLOW, so the one CEL policy returns DENY on a `tool_call` whose name is in the denied set, else ALLOW. The denied set is the S12 name families for Write, Edit/MultiEdit/NotebookEdit, WebFetch/WebSearch, delegation and Skill. Read, Grep and Glob are granted (the agents inspect `bricksmith.toml`, task files and reports).
- **Shell rule.** Shell tools are denied unless the `command` matches, in full, one or more `bricksmith <verbs>` segments joined by `&&`, `||` or `;`, each followed by arguments free of `; & | < > $`, backtick, backslash and newline (the S12 shell rule with `bricksmith` in place of `cq`). The per-agent verb lists are the only variable part:
  - `bricksmith-bundle`: `bundle resources`, `bundle validate`, `tasks list`, `tasks graph`, `tasks validate`, `context show`.
  - `bricksmith-mlops`: `dataset validate`, `dataset describe`, `model card`, `tasks list`, `tasks graph`, `tasks validate`, `context show`.
  - `bricksmith-analysis`: `quality compare`, `quality check`, `ops report`, `ops diagnose`, `ops readiness`, `ops explain`, `monitor compare`, `monitor evaluate`, `tasks list`, `context show`.
  Every listed verb is read-only in the current CLI: none registers `--apply`, `--out`, `--output` or `--freeze`. The shell rule cannot forbid a flag, so a verb that gains a mutating flag must leave the list in the same change; the test pins each listed verb to the CLI parser by asserting the flag set.
- **Domain split.** Bundle = resource and task-graph inspection; MLOps = model dataset contracts and the model card (read-only lifecycle view; lifecycle changes stay human); analysis = data comparison, checks, run reports, diagnosis and monitoring windows.
- **Instructions.** Each `instructions.md` has a workflow (read project config → run the granted verbs with `--json` → report), explicit exit-code handling from `docs/guide/context-and-cli.md` (0, 1, 2, 3, 4), a refusal rule (a denied tool stays denied; report it, never route around it), the context rule (one explicit `--env`/`--profile`, never `DEFAULT`, never switch workspaces after a failure), and the overlay hook: names, vocabulary and thresholds come from the project and the overlay, never from the bundle.
- **Overlay binding (forge `overlay-contract.md`).** An overlay binds a role by an `agents/<name>.json` file holding `name` and `description` that matches a bundle id; it holds no credential and no real URL. The bundles and tests use only reserved example hosts and synthetic names.
- **Dry run.** `tests/test_omnigent_agents.py` uses only the standard library (no `pyyaml`, no `celpy`, no new dependency): it reads the flat `config.yaml` with a line parser, extracts the expression, and evaluates the policy through a small evaluator for the fixed expression shape (name-in-list and one anchored `re.match` over the command). Its synthetic events are tool calls (write, edit, web, spawn, shell with granted and ungranted verbs, injection characters, a missing command) and no model is contacted.

## Alternatives Considered

- **Generate the bundles with a bricksmith port of `sync_omnigent_plugin.py`.** Lost: it needs a command source tree, a manifest and a drift check for three small files, and it would copy quenching tooling into a library repository.
- **One universal `bricksmith` agent with all verbs.** Lost: a wider grant per agent; three narrow ones keep each shell allow-list small and reviewable, and match the three domains of the epic.
- **Claude Code plugin skills only.** Lost: not harness-independent; the epic requires the Omnigent agent format.
- **Granting the mutating verbs behind `--apply`.** Lost: the shell rule cannot forbid a flag, so a granted verb would be granted with its `--apply`.

## Open Decisions

- Why now / appetite: the epic S24 depends on S12's format, which exists in quenching; whether to publish these bundles in the next release is decided by the human at release time.
- Whether a fourth, write-capable agent for lifecycle verbs (`model promote`, `run --apply`) should exist at all: decided by a human in a separate spec with its own approval; not built here.
- Whether `env check` (remote preflight) belongs in a grant: left out here; decided when a workflow needs it, by the same minimal-grant review.
- Whether the harness-independent bundles should later also be cut as a Claude Code plugin from the same instructions: decided by the delivery-contracts owner (BS-17), not by this spec.

## Risks

- A listed verb gains a mutating flag and the shell rule still lets it through. Mitigation: the test pins every granted verb to its parser's flag set and fails on `--apply`, `--out`, `--output`, `--freeze`, `--write-baseline` or `--authorize`.
- The test emulates CEL rather than running Omnigent, so a real CEL difference could hide. ACCEPTED — Omnigent and `celpy` are not dependencies and the expression has a fixed, simple shape; a real-engine proof is left to a host that has Omnigent.
- Read access exposes project files to the agent. ACCEPTED — Read, Grep and Glob are the minimum for inspecting the project; credentials stay in the environment and `.env`, which the instructions tell the agent never to open or echo.
- `quality compare|check` and `monitor evaluate` read tables with the selected context's credentials. ACCEPTED — they are read-only by design; the instructions require an explicit context.
- A real organization name or host slips into a bundle. Mitigation: synthetic names only, the leak gate, and a test-level scan for non-reserved URL hosts.
- Widening any grant, adding a mutating verb or touching a CI workflow is outside this spec; it returns `blocked` with `needs-human`.
