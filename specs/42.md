## Problem

`src/bricksmith/ops/redact.py:24` leaves secret values visible for several real-world spellings.
Reproduced with synthetic inputs (2026-10-16):

- doubled-quote escapes: `password='it''s my secret'` → `password='<redacted>''s my secret'`;
  `password="a""b c"` leaks `b c`;
- triple quotes: `password="""a b"""` → `password="<redacted>""a b"""`;
- backticks and curly quotes: ``password=`a b` `` → `password=<redacted> b``;
  `password=“a b”` → `<redacted> b”`;
- Python prefixes: `{'password': b'x y'}` (also `r'`, `f'`, `u'`) → `{'password': <redacted>'x y'}`;
- separators `=>`, `:=`, `==`: `password => 'x y'` leaves `'x y'`;
- keys with spaces or escaped quotes: `"API Key": "x y"`, `{\"password\": \"x y\"}` untouched;
- older patterns: URL credentials `https://user:pa/ss@host/x` unchanged and
  `https://user:p@ss@host/x` leaks `ss`; `jdbc:…;password=abc def;` leaks `def`; YAML block
  `password: |\n  multi line secret` leaks the block.

Over-redaction since PR #9: `compass: 'north east'`, `bypass='keep this text'`,
`tokens: 'the quick brown fox'` are masked whole.

Consequence: secrets reach logs, events and reports that redaction is meant to protect, while
unrelated text is destroyed. Depends on spec 41 (same pattern); keep the matching linear.

## Proposal

- Quoted values are masked whole for every spelling in the Problem: doubled-quote escapes, triple quotes, backticks, curly quotes, and Python string prefixes (`b`, `r`, `f`, `u`); the quote characters are preserved around `<redacted>`.
- The separators `=>`, `:=` and `==` are recognised next to `=` and `:`.
- Keys written inside quotes may contain spaces (`"API Key"`) and may carry escaped quotes (`{\"password\": \"x y\"}`).
- URL credentials mask a password containing `/` or `@` (`https://user:pa/ss@host/x`, `https://user:p@ss@host/x`).
- A value in a `;`-delimited connection string (`jdbc:...;password=abc def;`) is masked up to the next `;`.
- A YAML block scalar (`password: |` followed by indented lines) is masked with its indented lines.
- A sensitive keyword must be a whole word of the key: `compass`, `bypass` and `tokens` are no longer masked; `access_token`, `DB_PASSWORD`, `clientSecret`, `dbpassword` still are.
- Matching stays linear in the input, keeping the bound from spec 41.

## Out of Scope

- Changing `MAX_TEXT`, the scan cap, `redact_value` or the sensitive dict-key set (`_SENSITIVE_KEY`).
- Recognising new secret formats (token shapes, cloud keys): this spec widens quoting and separators only.
- Masking a password that itself contains a space when it is unquoted and not in a `;` connection string: the whitespace boundary is kept.

## Design

- Rule: one header regex finds `key SEP` (the key is either an unquoted token anchored at a token start, as in spec 41, or a quoted key of at most 64 characters of `[\w .-]` with optional escaping backslash). A small scanner then decides where the value ends; the output keeps the header, the opening quote, `<redacted>` and the closing quote. Matches that start inside a value already consumed are skipped, so the pass is a single left-to-right sweep.
- Rule: the keyword test is `(?<![a-z]) | camelCase-boundary` + keyword + `(?![a-z])`, case-sensitive for the boundary through `(?-i:...)`; `password`, `passwd`, `passphrase` and `apikey` need no left boundary so `dbpassword` stays masked. This is what stops `compass`, `bypass` and `tokens`.
- Rule: value forms, tried in order after the separator: YAML block (`|` or `>` then newline; consume following lines indented deeper than the key's line, or blank), optional Python prefix `[bBrRuUfF]{1,2}` before a quote, triple quote, escaped quote (`\"`, closed by the same), single quote with doubled-quote and backslash escapes, curly quote closed by its pair, then unquoted. Unterminated quoted values run to the end of the text, as today. Unquoted values stop at whitespace, `,`, `;`, quotes, `&` or `)`; when the key directly follows `;`, they run to the next `;` or end of line.
- Rule: URL credentials: after `://user:` take the non-space run; the password ends at the last `@` found before the first `/` that follows the first `@`; no `@` means no match, so `http://host:8080/path` is untouched. Assumption: a `host:port/path@x` URL is over-masked rather than risk a leak.
- Assumption: nothing needs the old behaviour where `tokens`, `compass` or similar were masked.

## Alternatives Considered

- Add more alternations to the existing regexes: rejected, doubled quotes and nested block scalars are not regular enough to stay readable or provably linear.
- A full tokenizer per language: rejected, redaction is a safety net over free text, not a parser.

## Open Decisions

- none - choices are recorded in Design; revisit the 64-character quoted-key cap and URL over-masking only if real inputs show a leak.

## Risks

- The new keyword boundary may stop masking a key that was masked by accident. Mitigation: the compatibility tests list `access_token`, `DB_PASSWORD`, `clientSecret`, `dbpassword`, `api_key`, `private-key`.
- A scanner bug could be quadratic. Mitigation: the position only advances, and the spec 41 timing test plus a new input with many keys run in the suite.
