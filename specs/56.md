## Problem

Reproduced 2026-10-17 by the epic #47 correctness review on main (6f3ef40), range 77e04d9..6f3ef40.

Comparing 77e04d9 and main on key variants: the old redaction masked `passwords=`, `secrets=`, `smtppass=`, `ldappass=` and `mypass=`; main returns them unchanged, e.g. `redact_text('passwords=s3cretval tail')` and `redact_text('secrets: "s3 cret" tail')` come back as given. Cause: `src/bricksmith/ops/redact.py:22-26`: the trailing `(?-i:(?![a-z]))` rejects plurals, and lowercase `…pass` matches only after a fixed prefix list (db, user, sql, ftp, ssh, admin, root). Intended non-secrets (`compass`, `bypass`, `tokens`) are not part of this regression.

Consequence: secrets under common key names reach events and reports again (regression from #42/#51). Define the accepted plural/suffix forms explicitly, keep the over-redaction guards and #41's linear-time bound.

## Proposal

- `redact_text` masks the values of plural password and secret keys (`passwords`, `passwds`, `passphrases`, `secrets`) again, quoted and unquoted.
- `redact_text` masks the values of keys that end in `pass` after any letters (`smtppass`, `ldappass`, `mypass`, `dbpass`), again.
- Keys that only look like secrets stay unmasked: `compass`, `bypass`, `tokens`, and the other dictionary words ending in `pass`.
- #41's linear-time bound on long input still holds.

## Out of Scope

- Plural `tokens`, which is an intended non-secret and stays unmasked.
- The `_SENSITIVE_KEY` search used for dictionary keys in `redact_value`: it already matches by substring and is not part of the regression.
- The follow-ups on this file owned by #55 and #54, which are serialized after this spec.

- The same suite asserts `compass=north`, `bypass=on`, `tokens=12` come back unchanged.
- The existing long-input timing test still passes.
- `uv run ruff check && uv run ruff format --check && uv run pyright` is clean.

## Design

- The plural is explicit, not a generic trailing `s`: an optional `s` is added to `password`, `passwd`, `passphrase`, `secret` and the bare `pass` family only. `token` gets none, so `tokens` stays a non-secret.
- The fixed prefix list (`db`, `user`, `sql`, `ftp`, `ssh`, `admin`, `root`) is replaced by "`pass` preceded by a letter and not by a known word ending": negative fixed-width lookbehinds for `com` (`compass`, `encompass`), `by`, `over`, `sur`, `tres`, `under` and `im`. The old over-redaction behaviour (any `...pass`) is restored minus these dictionary words.
- Only fixed-width lookbehinds and optional single characters are added, so the pattern stays linear and #41's bound holds; the existing timing test covers it.
- The trailing `(?-i:(?![a-z]))` stays, so `passing`, `passed` and `secretsmanager` are not matched.

### Mapa de dependências

- 2026-10-23: `_KEYWORD` is used only by `_HEADER` in `src/bricksmith/ops/redact.py`, which feeds `_mask_assignments`, called from `redact_text` and, through it, `redact_value`. Tests in `tests/unit/ops/test_ops.py` import both. #55 and #54 edit the same files later.

## Alternatives Considered

- A generic trailing `s?` on every keyword: rejected, it would mask `tokens`, which is an intended non-secret.
- An allow-list of suffix prefixes (extend the db/user/sql list): rejected, it keeps losing `smtppass`-style keys; the deny-list of dictionary words is smaller and fails toward masking.

## Open Decisions

- none — the accepted forms are settled in `## Design`; the dictionary-word list may grow, one lookbehind each, if review finds another.

## Risks

- A key such as `hubpass` or `tokenpass` over-redacts a non-secret: ACCEPTED — redaction fails toward masking, as it did before the regression.
- A new lookbehind could slow the scan: mitigated, fixed-width only, and the long-input timing test runs in the same file.
