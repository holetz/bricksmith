## Problem

.githooks/pre-commit (line 3) and .githooks/pre-push (line 6) invoke `python3 scripts/leak_check.py`. On Windows, `python3` usually resolves to the Microsoft Store app-execution-alias stub rather than a real interpreter. The leak gate therefore cannot run, and every commit or push from a Windows checkout either fails or would need `--no-verify`, which the ground rules forbid.

## Proposal

Have the hooks resolve a working interpreter portably, for example the project environment through `uv run`, or the first of `python3`/`python` that actually executes. Fail closed with a clear message when none is found. The leak gate must never be skipped silently. Hooks are an executable surface reserved for human decision, so the resolution strategy needs human approval before any implementation.

## Out of Scope

Changing leak-check patterns or the denylist; bypassing or weakening the gate; CI changes.

## Impact

.githooks/pre-commit; .githooks/pre-push; possibly scripts/setup.sh and docs/development notes.

## Validation

On Windows with only the Store stub on PATH as `python3`, and on Linux, a staged commit containing a denylisted synthetic pattern is blocked and a clean commit passes. Removing every interpreter makes the hook fail closed with a readable message.

## Open Decisions

needs-human: approve the interpreter resolution strategy for git hooks (uv-managed environment vs. PATH probing) and whether hooks may depend on uv.
