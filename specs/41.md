## Problem

`redact_text` takes roughly cubic time on long word-like input. The assignment pattern at
`src/bricksmith/ops/redact.py:24` reuses the backtracking key prefix `[\w.-]*(?:pass|…)[\w.-]*`
(same shape as line 30), and `redact_text` runs every pattern before truncating
(`redact.py:50` patterns, `:52` truncation), so the 500-character cap does not bound the work.

Reproduction (synthetic, 2026-10-16): `redact_text("pass"*1000)` (4,000 chars) took 225 s;
1,000 chars took 4.65 s; `redact_text("a"*20000)` took 27 s. The old pattern alone took 1.65 s on
1,000 chars; PR #9's new pattern adds about 1.5 s more.

Consequence: one long log line or error message can stall event, report or alert emission for
minutes. Direction: make the key matching linear (atomic/possessive structure or token-based
scan) and bound the scanned length before the patterns run; add a timing regression test.

## Proposal

- `redact_text` runs in time linear in its input: `redact_text("pass"*1000)` and `redact_text("a"*20000)` finish in well under a second.
- Patterns scan at most a fixed cap of 32,768 characters (`_MAX_SCAN`, or `limit` when that is larger), so a very long input costs no more than a bounded prefix.
- Redaction results for ordinary inputs are unchanged, including the quoted, unquoted and URL-credential forms.
- A timing regression test guards the bound without depending on machine speed.
## Out of Scope

- Changing which secrets are recognised or the `MAX_TEXT` default: this spec changes cost, not coverage.
- Redacting beyond the truncation window: text past the window is dropped by truncation anyway.
- Bounding `redact_value` depth or list fan-out, which are already capped.

## Design

- Rule: the sensitive-key patterns are anchored at a token start (`(?<![\w.-])`) and use a lookahead `(?=[\w.-]*?keyword)` before consuming the key token `([\w.-]+)`. The old `[\w.-]*keyword[\w.-]*` prefix backtracked cubically; token anchoring tries each token start once, so the scan is linear in the token length.
- Rule: after literal-secret replacement (a linear `str.replace`), only the first `max(limit, 32768)` characters go through the patterns; when text was cut, the result ends with the ellipsis. The cap is a fixed constant rather than a multiple of `limit`, because a `limit * 4` window (2,000 characters by default) was judged too small a margin for a secret that begins late in a long value, and the token-anchored patterns already bound per-token work. Assumption: no pattern's match needs context beyond the cap to be correct for the kept prefix.
- The timing test runs four 200,000-character-class inputs (key prefix, plain word, open bracket, open quote) against a 5-second ceiling (about ten times the measured worst case; the base took minutes) and checks the output stays within the limit, so it is not machine-speed sensitive.
## Alternatives Considered

- Only truncate before the patterns: rejected, a 2,000-character window would still cost seconds under cubic matching.
- Possessive/atomic groups: needs Python 3.11+ semantics and still leaves the optional-prefix ambiguity; the token callback is simpler to reason about.

## Open Decisions

- none - the window multiple (4) is a design choice recorded in Design; revisit only if a real input shows a cut-off secret.

## Risks

- A token-callback rewrite could change a match edge case. Mitigation: the existing redaction tests, including the quoted-value cases, stay and must pass unchanged.
- A timing test can flake on a loaded runner. Mitigation: ceiling about 20x above expected runtime, versus the base's minutes.
