## Problem

Found by the correctness review of epic 98 (2026-11-24), reproduced on main e564870.

`bricksmith stability check --state s.json` rewrites the state file from `result.tables` (`src/bricksmith/monitor/stability/cli.py:37`), not from every kind it loaded (`ALL_KINDS`). With revision off, `check` returns no revisions table, so the stored first-publication snapshots are dropped:

```
--config on.json  → {'alerts': 0, 'binnings': 1, 'profiles': 10, 'results': 18, 'revisions': 10, 'runs': 1}
--config off.json → {'alerts': 0, 'binnings': 1, 'profiles': 10, 'results': 18, 'runs': 1}
```

Consequence: switching revision back on snapshots the current (possibly already revised) profiles as the "first publication", so any revision made before that point can never be detected. The project hook writes only declared tables and is unaffected; only the CLI `--state` path loses data.

Proposal: write back every loaded kind, replacing only those the run returned; add a CLI test that runs on → off → on and asserts the snapshots survive.

## Proposal

`bricksmith stability check --state` writes back every stability kind it loaded, replacing (by key-merge) only the kinds the run returned. A kind the run did not produce — the revisions snapshot while `revision` is off — is written back untouched, so switching revision back on compares against the true first publication.

## Out of Scope

- The project hook path — it writes only declared tables and is unaffected (Problem).
- Engine and revision metrics behavior (`engine.py`, `revision.py`) — unchanged; the engine already returns no revisions table when revision is off.
- Pruning or migrating stale kinds in a state file — a loaded kind is kept as it was read.

## Impact

### Product code this spec expects to touch

- `src/bricksmith/monitor/stability/cli.py` — the `--state` write-back in `_check`
- `tests/unit/monitor/stability/test_stability_revision.py` — CLI regression test on → off → on

## Validation

- `uv run pytest tests/unit/monitor/stability/test_stability_revision.py -q -k cli` fails on the base (`KeyError: 'revisions'` after the off run) and passes after the fix.
- The affected stability unit suite stays green; the full repository gate runs once at conclude.

## Design

- In `_check`, build the written mapping over the union of loaded kinds and returned kinds: `merge_rows(k, loaded, returned)` for a returned kind, the loaded rows verbatim otherwise. Key order stays sorted by `json.dumps(sort_keys=True)`.
- Rows loaded from JSON already carry plain (ISO text) values, so passing them through `_plain` is idempotent.

### Assumptions

- Only `ALL_KINDS` are loaded (existing filter), so unknown keys in a hand-edited state file are still dropped — Out of Scope.

## Alternatives Considered

- Make the engine always return an empty revisions table — rejected: an empty list merged by key keeps the rows too, but it changes the engine's contract (`test_engine_without_revision_has_no_revisions_table_and_no_revision_result`) for a CLI-only defect.
- Write back `ALL_KINDS` unconditionally — equivalent output, but would add empty kinds the state never held; the union of loaded and returned is the minimal change.

## Risks

- A state file grows nothing new: kinds kept are only those it already held. Low risk, CLI-local.
