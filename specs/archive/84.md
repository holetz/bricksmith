## Problem

Each capability has unit tests, but nothing proves the whole flow works together on Databricks: feature tables → engineered features → training set → selection → training and registration → scoring → technical document → model monitoring with stability on the same tables.

## Proposal

- An example project under `examples/` with synthetic data only: a periodic source, feature tables at two entity grains, engineered windows, a spine with exclusions and an out-of-time sample, the selection funnel, a trained model registered in Unity Catalog with an alias, monthly scoring, the generated technical document, and declared model monitoring plus data stability on the feature and prediction tables.
- Guides under `docs/how-to/` for the feature store, feature engineering (with the benchmark result and engine choice), selection, model stages and documentation, and an updated monitoring guide; a decision record for the closing-based feature store and the engine choice.
- A Free Edition remote proof (explicit free context, cleanup in finally) recorded under `docs/project/evidence/`; Unity Catalog Feature Engineering adapter proof only where the workspace supports it, recorded as supplementary.

## Out of Scope

- Corporate workspace proof as a requirement.

## Design

- **One example project, `examples/model_flow/`.** It is separate from `shared_schema`, which shows the older snapshot-based model datasets. It uses catalog alias `demo` and schema alias `flow`, and declares one model, `attrition`. Every task is an ordinary bricksmith task: one graph and one runner (decision 0009).
- **Synthetic periodic source.** A deterministic generator (seeded `random.Random`, no wall clock) writes monthly closings (month-end DATE) for a few hundred accounts held by about half as many customers. It covers numeric balances and payments, a delinquency counter, a status category, a segment and a closed flag. It produces a binary attrition outcome that the label task derives over a forward window. The data stays small so the free proof finishes in minutes.
- **Two feature grains.** `account_features` (entity `account_id`) and `customer_features` (entity `customer_id`, aggregated from accounts at each closing). Both are declared `feature_table` tasks. Both compute windowed aggregates with `compute_features` under `engine="auto"`, with an optional `kernel_function` task parameter that names an installed Unity Catalog kernel. Per epic 85 Design (2026-11-24), the example and the guide use the engine `auto` resolves to (the JVM kernel). When the compute refuses the kernel, they show where the run report records the fallback reason. Both tables also declare `stability` (closing period, fixed baseline over the development closings, warn-only gate), so data stability runs on the same tables the model reads.
- **Development stages.** A development declaration (TOML under `models/`, loaded with `load_development_file`) declares train, test, out-of-time and prediction samples, a label horizon, an exclusion cascade, grade bands and lookups at both grains, with one offset lookup. Tasks build the population (the spine, cascade applied), the labels and the training ABT, and run the selection funnel. The ledger and variables tables use the selection `write_options`.
- **Training.** The train task fits a scikit-learn logistic regression on the selected features. It creates the MLflow run through the tracking client, as the spec 80 proof does, because `ModelStore.log_run` verifies by listing, which the free tier breaks (spec 88). It logs the development, composition, selection, specification and narrative artifacts, plus a bricksmith model artifact (`model/` with `bricksmith_model.json`), so the run can be registered on a workspace that supports it. It writes a one-row run record table that holds the run id.
- **Registration and alias are a deliberate step**, as in the existing example: `register_run` and an alias plan to `champion`. The free tier cannot register a model version (spec 88), so the free proof attempts registration and records **Unsupported** with the platform's reason. It does not fail the run.
- **Scoring pins its model explicitly.** It uses alias `champion` by default, or the task parameter `model_run=<run id>` for a run that is not registered yet. Nothing resolves "latest". The scoring task scores the development, out-of-time and prediction samples (`purpose="scoring"`), writes the prediction contract with `prediction_frame` plus the matured label, and declares `model_monitoring`. Monitoring uses the development and out-of-time references, grades and a label lag. Feature CSI uses bins shared with the feature tables' stability binning where the configuration allows it. On free, the proof scores with `model_run`.
- **Evaluation and document.** A task evaluates the scored labelled samples (`evaluate`) and writes the results tables. It logs the evaluation to the training run, then renders and publishes the technical document from the run's artifacts (`collect_run`, `publish_document`). The version tag is set only when a registered version exists.
- **No new decision record.** The closing-based feature store is decision 0013. The engine choice is decisions 0014 and 0019. The guide links them. The Proposal's "decision record for the closing-based feature store and the engine choice" is therefore already satisfied on `main`.
- **Unity Catalog Feature Engineering adapter.** It is supplementary. The remote dependency group does not install the `features` extra, so the free proof records it as not run (as in the spec 76 evidence) rather than adding a dependency.
- **Guides.** A new `docs/how-to/model-flow.md` walks the example stage by stage and links the per-capability guides. Each of those guides gets a pointer back to the example. Writing follows the repo's plain-English how-to style and OKF frontmatter.
- **Binding contracts:** AGENTS.md (English, no organisation content, lightweight imports, no generated YAML), decision 0010 (synthetic data, independent development), `docs/project/databricks-tests.md` (explicit free context, Unsupported state, cleanup in finally), and lazy Spark imports with `# pyright: ignore[reportMissingImports]` because CI runs pyright without pyspark.

### Assumptions

- The free workspace still installs the JVM kernel as a Unity Catalog Scala function (proved in the spec 91 evidence). If it refuses, `auto` falls back to native Spark, and the evidence states the reason (Design, Validation).
- `download_artifacts` of single files still works on free while listing does not (spec 88). The document collection depends on it, as in the spec 80 proof (Design).
- A `feature_table` task may also declare `stability`. If the plan refuses the combination, stability moves to a downstream view task over the same table (Design).

## Alternatives Considered

- **Extend `examples/shared_schema` instead of a new project.** Rejected. That project demonstrates the older snapshot-based datasets and its remote tests assert exact row counts. Mixing in the closing-based flow would break those proofs and blur two APIs.
- **Score with the coefficients in Spark expressions instead of loading the model.** Rejected. It would add a second scoring path that differs from the registered artifact, and it only works for linear models.
- **Fix spec 88 here, so `log_run` and registration work on free.** Rejected. Spec 88 owns the defect and its open question about whether the condition is temporary. This spec records the free limitation as Unsupported, as epic 85 Design directs.
- **A notebook instead of tasks.** Rejected. The point is to prove that the capabilities compose on the shared runner.

## Open Decisions

- Whether `model_monitoring.feature_binning` can reuse the stability binning of a feature table, when the predictions table is a different dataset from the feature tables. This is decided during task 1.3 by the plan validator. If it refuses, monitoring fits its own bins, and the guide says why.

## Risks

- The free proof runs long (kernel cold start, many tasks). Mitigation: small synthetic sizes. The proof runs once at the end, in the foreground, with an explicit timeout.
- Free-tier refusals turn the proof red for reasons outside the code. Mitigation: each known refusal (kernel registration, model registration) is detected by its error and recorded as Unsupported with the reason. Any other error fails.
- Leftover workspace objects. Mitigation: cleanup in `finally` deletes the experiment and any registered model before the schema fixture verifies that the schema, volume and function are gone.
- ACCEPTED: registration, alias and alias-pinned scoring are proven only offline and on a workspace that supports registration. The free tier cannot register versions (spec 88).

**Left out**

- The Unity Catalog Feature Engineering adapter (not run: the remote group does not install the `features` extra). No new decision record: decisions 0013, 0014 and 0019 already cover the Proposal's ask.
- Monitoring fits its own feature bins. Reusing a feature table's stability binning would need a fixed stability `dataset` name, because the default is the physical table and changes by context.

**For the next reader**

- Before the remote proof, build the kernel JAR with `scripts/build_kernel.py` (a gitignored build artifact). Without it, `auto` records the native fallback and its reason.
- MLflow 3 serializes scikit-learn models as `model.skops`. Read the file name from `MLmodel`, never hardcode `model.pkl`.
- In Spark, a boolean chain over a nullable column can yield null. Labels use `when`/`otherwise`.
- A refused `register_run` still creates the registered model. Teardown deletes it whatever the outcome.
