## Problem

Stability monitoring accepts three invalid declarations at plan time that later misbehave, contradicting docs/how-to/stability.md:74 ("An invalid declaration is a plan error") and docs/how-to/model-monitoring.md:88 ("invalid values are plan errors"):

1. Unknown rule metric (medium). `src/bricksmith/monitor/stability/config.py:468` calls `parse_rules(...)` without checking `rule.metric` against the known metrics; `rules.py:204-206` only requires presence and `rules.py:68` matches by equality. The model side rejects it (`monitor/model/config.py:509-511`). Repro: a stability rule `{"id":"r","metric":"psi_strict",...}` is accepted; the same rule under model_monitoring raises `unknown metric 'psi_strict'`. Consequence: a typo (`"PSI"`, `"mean_shfit"`) inline or in monitoring/rules.toml passes plan and never matches — the reviewed limits never apply and gates/alerts follow the defaults.
2. `exclude` as a string (medium-low). `stability/config.py:449` iterates `data.get("exclude", [])` with no list check (segments has one, :334). Repro: `"exclude": "sale_id"` → `('s','a','l','e','_','i','d')`. Consequence: the id column is still monitored under `columns="auto"` (false PSI/unseen drift, red alerts) and single-letter columns are dropped.
3. `epsilon` not validated (low), both configs: `stability/config.py:467`, `model/config.py:678` take bare `float(...)`; `stats.py:26-27` floors with `max(share, epsilon)`. Repro: `epsilon: 0` is accepted, then `psi({"a":10,"b":0},{"a":5,"b":5},0.0)` → ZeroDivisionError; every PSI/CSI with an empty bin errors at run time.

Evidence: round-7 scout ses_def315899ffedIUdasly80BqzQ (repro /tmp/scout/r1.py), C1/C2 re-checked by the conductor against code.

## Proposal

- A stability rule whose `metric` is set and is not one of the stability metrics fails plan with `stability: rule '<id>': unknown metric '<m>'; known: <metrics>`, inline or from a rules file, as model monitoring already does.
- A stability `exclude` that is not a list of column names (a bare string included) fails plan; there is no auto-wrap.
- `epsilon` must be a finite number greater than 0 in both the stability and the model monitoring declarations; `0`, a negative value, `nan`, `inf` or a boolean fails plan naming `epsilon`.
- `docs/how-to/stability.md` carries a migration note: declarations that were silently wrong before now fail plan; `docs/how-to/model-monitoring.md` states the epsilon bound.

## Out of Scope

- The `epsilon` stored in a `monitor fit` reference (`monitor/reference.py`, `monitor/measure.py`): it is not a stability or model monitoring declaration; parked as a discovery.
- Rules without a `metric` (selector-only rules, informational rules): still valid, unchanged.
- Auto-wrapping `exclude: "col"` into a list: rejected by the owner decision (epic 136 ## Design).
- Validating other loose numeric keys of the stability declaration (`baseline.lag`, `periods`): not reported by the scout, no evidence of misbehavior.

## Design

- **Rule metric check lives in the owner's config, not in `parse_rules`.** `monitor/rules.py` is shared and takes no metric catalog; model monitoring checks `rule.metric not in METRICS` after `parse_rules` (`model/config.py:_rules`). Stability mirrors it with a `_rules` helper over `parse_rules(..., owner="stability")`, message `rule {id!r}: unknown metric {m!r}; known: {', '.join(METRICS)}`, wrapped by `_fail` (prefix `stability:`). An empty metric stays legal.
- **`exclude` must be a list** (`isinstance(value, list)`), each item through `_name`; anything else raises `exclude must be a list of column names, got …`. Same shape as `_segments`'s list check.
- **Epsilon is a finite float > 0.** A helper per config (`_epsilon`) rejects booleans and non-numbers, converts with `float`, and requires `math.isfinite(v) and v > 0`; message `epsilon must be a finite number > 0, got …`. Rationale: `stats.psi_terms` floors shares with `max(share, epsilon)` and divides by them, so `0` divides by zero and `nan`/`inf` poison every PSI/CSI.
- **Plan error = `MonitorError` from `parse_config`.** The plan already maps it to `invalid_stability`/`invalid_model_monitoring`; no new error class.
- Binding: decision 0021 (limit rules selectors), docs/how-to/stability.md:74 and docs/how-to/model-monitoring.md:88 ("an invalid declaration is a plan error"); epic 136 ## Design owner decisions of 2026-11-25.

### Assumptions

- A boolean `epsilon` is invalid (`True` would read as 1.0) — Design, Tasks 1.1/1.2.

## Alternatives Considered

- **Validate the metric inside `parse_rules` with a `metrics=` argument**: rejected — changes the shared parser's contract for both owners when the model side already validates in its own config; mirroring keeps the change local.
- **Auto-wrap a string `exclude`**: rejected by the owner (a plan error is clearer and matches `columns` strictness).
- **Clamp `epsilon` to a minimum at run time**: rejected — hides a wrong declaration; the docs promise plan errors.

## Open Decisions

- none — the owner settled all three behaviors and the doc note in epic 136 ## Design (2026-11-25).

## Risks

- Existing projects with a typo'd rule metric, a string `exclude` or `epsilon: 0` now fail plan — ACCEPTED — the intended behavior; the migration note in docs/how-to/stability.md tells users what to fix.
- A rule file shared between stability and model monitoring with metrics of both kinds would now fail on the stability side — ACCEPTED — the same rule already fails on the model side for stability-only metrics, so such a shared file could not be valid today.
