## Problem

Regression from spec 135 (PR #83), reproduced by the round-7 reviewer (ses_def2691baffemtp9IDLIQpL5Vc). `src/bricksmith/monitor/model/actions.py:52` calls `astimezone` outside the try at :48, which only catches ValueError. A valid ISO-8601 created_at whose UTC conversion leaves Python's date range (e.g. `9999-12-31T23:00:00-03:00`, `0001-01-01T00:00:00+01:00`) raises `OverflowError: date value out of range` from `latest_actions` (:123) and `action_row` (:94).

Repro: `{ git show origin/main:src/bricksmith/monitor/model/actions.py; printf '%s\n' 'print(latest_actions([{"alert_id":"a","created_at":"2026-01-01T00:00:00+00:00"},{"alert_id":"a","created_at":"9999-12-31T23:00:00-03:00"}]))'; } | uv run python -` → OverflowError.

Consequence: one stored action row with such a placeholder date makes `latest_actions` crash, so apply_actions, replay_alerts and the model report fail for every model — contradicting 135's owner decision that stored rows keep working (parsed where possible, raw text otherwise). On write, the CLI `act` command raises a bare OverflowError instead of the MonitorError refusal. Before 135, raw-text ordering never crashed.

## Proposal

`_utc_instant` catches `OverflowError` together with `ValueError` around both `datetime.fromisoformat` and `astimezone(UTC)` and returns `None`. Reads (`_order`, so `latest_actions`, `apply_actions`, replay and the report) then treat such a stored value as unparsable: ordered by raw text before every parsable instant. Writes (`action_row`, so the CLI `act`) refuse it with the existing `MonitorError`. The model-monitoring how-to notes that an instant outside the supported date range counts as unparsable.

## Out of Scope

- The SQL `actions_latest` view text ordering of legacy rows (already accepted in 135).
- No change to how valid instants are stored or ordered.

## Impact

### Product code this spec expects to touch

- `src/bricksmith/monitor/model/actions.py` — catch `OverflowError` in `_utc_instant`.
- `tests/unit/monitor/model/test_model_actions.py` — both extreme offsets: refused on write, folded by raw text on read.
- `docs/how-to/model-monitoring.md` — one sentence on out-of-range instants.

## Validation

`uv run pytest tests/unit/monitor/model -q` proves: `action_row(created_at="9999-12-31T23:00:00-03:00")` and `"0001-01-01T00:00:00+01:00"` raise `MonitorError`; `latest_actions` over stored rows carrying those values returns without error, ordering them by raw text before parsable ones. `uv run ruff check`, `uv run ruff format --check`, `uv run pyright` and `uv run pytest` stay green.

## Design

- `_utc_instant` wraps both the parse and the `astimezone(UTC)` in `try/except (ValueError, OverflowError)`; one helper serves both sides, so read and write stay consistent.
- Owner decision: epic 138 `## Design`, third 2026-11-25 bullet.

### Assumptions

- Both extremes overflow only on `astimezone`, not on `fromisoformat` — affects task 1.1 tests.

### Mapa de dependências

2026-11-25: `_utc_instant` is private to `actions.py`; callers are `_order` (reads) and `action_row` (writes, reached from `monitor/model/cli.py` `act`). No other file changes.

## Alternatives Considered

- Clamp the instant to the date range: rejected, invents a time the person never wrote.
- Refuse on read too: rejected, stored rows must keep working (135).
