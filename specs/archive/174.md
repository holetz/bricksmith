## Problem

Reproduced by the round-3 reviewer on 2026-11-26 (main ad054ad; base 5a8ed5b identical). #172 (PR #119) fixed `/` before `@` in a bare-host password but not `@` before `/` or `?`:

```
redact_text("postgres://admin:p@ss/word@db.example.com") -> 'postgres://admin:<redacted>@ss/word@db.example.com'
redact_text("postgres://admin:p@ss?word@db.example.com") -> 'postgres://admin:<redacted>@ss?word@db.example.com'
redact_text("redis://u:x@y/z@cache.example.com")         -> 'redis://u:<redacted>@y/z@cache.example.com'
```

`src/bricksmith/ops/redact.py:286-287` (`_after_host`) treats any `/`, `?`, `#` after an earlier `@` as a host/path boundary, and `:309` pops the last `@` as a "path address". Consequence: realistic generated passwords (containing `@` and `/`) leak their tail into logs. Three review rounds patched one ordering each; this spec closes the class (see the round epic's fail-closed decision).

## Proposal

- In a `scheme://user:` URL the password/host separator is the rightmost `@` followed by a plausible host (`name[.name]*`, or a bracketed IPv6 literal, optional `:port`) and then a non-host character or the end; everything between `user:` and it is masked, whatever `@`, `/`, `?` or `#` it holds.
- The three round-3 reproductions (`p@ss/word`, `p@ss?word`, `y/z`) mask the whole password and keep only the real host.
- The host:port reading (`user:1234/...`) stays a no-credential reading only when every `@` is a path address tail or a `/@` handle; otherwise the same rightmost rule applies.
- Tests: reviewer reproductions, a generated table of every ordering of `@ / ? #` in the password with and without path/port, an exact-output no-over-redaction table, and a timed linear test at 4k/64k.

## Out of Scope

- Preserving a path address after a credentialed host (`https://u:pw@host/a/bob@x.com`): ruled out by the epic's fail-closed decision; it may now mask more of the path.

## Design

- Rule (epic 176, fail closed): the separator is the rightmost `@` whose tail matches a plausible host[:port] followed by end or a non-host character; the whole password up to it is masked. Where no `@` qualifies but one exists, the rightmost `@` still separates, so the redactor never leaves a credential visible.
- Host:port ambiguity: a leading `1-5 digits` then `/`, `?`, `#` or end is host:port. Such text holds a credential only when an `@` (not a `/@` handle) that is not an address tail (`name.tld`) sits before the first `?` or `#`; then the rightmost rule applies over all those `@`.
- Matching uses possessive quantifiers and one local match per `@`, so the pass stays linear.
- Known accepted consequence: `https://u:pw@host/a/bob@x.com` and `.../users/@alice` mask the path up to the last address.

### Assumptions

- Python 3.12 regex supports possessive quantifiers (`requires-python >=3.12`) — depends on the host pattern.

## Alternatives Considered

- Keep patching one ordering per round (rejected: three rounds each found a leak beside the last fix).
- Parse with `urllib.parse` (rejected: it takes the rightmost `@` of the netloc only up to the first `/`, which is exactly the leak).

## Open Decisions

- none — the epic's design decision settles the rule.

## Risks

- Over-masking a path address after a credentialed host. ACCEPTED — the fail-closed decision prefers it to a leaked secret.
- Pathological input making the host match quadratic. Mitigation: possessive quantifiers and a timed test at 4k/64k.
