## Problem

Model inputs are chosen by hand with no shared tooling or record of why a variable was kept or dropped. Information value, correlation, VIF and importance are computed ad hoc in notebooks; auditors cannot reproduce the choice. `bricksmith.monitor` already has binning and PSI (`monitor/bins.py`, `monitor/stats.py`) that a funnel can reuse.

## Proposal

- `bricksmith.mlops.selection` (or a sibling module): a reproducible funnel over a training set with development and out-of-time samples split by closing before any metric. Steps, each optional and configurable, in order: quality (missing share, constant share, categorical cardinality); stability (PSI development vs out-of-time and month-over-month, reusing the monitoring bins); univariate power (binary target: IV with WoE over monotone/quantile bins, KS, Gini; continuous target: Spearman), with expected-sign checks; redundancy (pairwise correlation clustering keeping the strongest per cluster, then VIF on the survivors); multivariate (L1/elastic-net logistic and permutation importance, behind the `mlops` extra); judgment (a declared list of manual keeps/drops with reasons).
- Thresholds are configuration with defaults, never hard truth; PSI may use sample-size-aware critical values.
- Output: a selection ledger (one row per variable × step: metric values, threshold, decision, reason, step where it left) and the final feature set; both persist as a table and as MLflow artifacts/params when a run is active.
- Engines: aggregate metrics (bins, IV, PSI, correlations) in Spark and pure rows with parity tests; VIF and importance on a bounded sample in pandas/numpy.
- Supervised transforms (WoE, supervised binning) are fitted on training only and never written to feature tables.

## Out of Scope

- Automated stepwise search over model families; SHAP as a hard dependency (optional only).

## Design

- **Module.** `bricksmith.mlops.selection` (a package): `config` (parsed `SelectionConfig`, defaults, `SelectionError`), `metrics` (pure statistics), `summary` (the per-engine reduction), `funnel` (steps, ledger, `select_features`), `spark` (the Spark reduction), `multivariate` (scikit-learn, lazily imported), `tables` (typed table rows) and `tracking` (MLflow). The package import loads only the standard library and `bricksmith.monitor` pure modules.
- **Samples split first.** The config names the closing column and two closing ranges (`development`, `out_of_time`, inclusive, compared as ISO text). Rows outside both are ignored; every metric is computed after the split. Quality, univariate, redundancy and multivariate run on development; stability compares development against out-of-time and consecutive closings month over month.
- **One reduction, one fold (the monitoring pattern).** Each engine reduces the training set to a `SelectionSummary`: per variable and closing the `value -> count` map; per variable on development the `value -> (events, non-events)` map (binary target) or rank inputs (continuous target); pairwise correlation sums for numeric variables; a bounded complete-case sample for VIF and the multivariate step. A single pure fold turns the summary into the ledger, so the pure and Spark engines agree by construction and parity tests compare outputs, not code paths.
- **Steps, in order, each optional (`steps: {name: false}` disables one):**
  1. `quality` — `missing_share`, `constant_share` (top non-null value share), `cardinality` (categorical). Defaults: drop above 0.95 missing, above 0.99 constant, above 50 categories.
  2. `stability` — `psi_oot` (development vs out-of-time) and `psi_mom_max` (worst consecutive-closing PSI) over bins fitted on development with `monitor.bins.fit_bins` and scored with `monitor.stats.psi`. Default threshold 0.25; `psi_max: "critical"` uses the sample-size-aware critical value `chi2_{B-1}(1-alpha) * (1/N + 1/M)` (default alpha 0.05).
  3. `univariate` — binary target: `iv` from WoE over `quantile` or `monotone` bins (adjacent bins pooled until the event rate is monotone), smoothed by 0.5 per empty cell; `ks` and `gini` (`2·AUC-1`, absolute) over raw values for numerics and over categories ordered by event rate for categoricals. Continuous target: `spearman` (absolute). Defaults: drop when IV < 0.02 or |Spearman| < 0.05; KS and Gini thresholds off unless configured. `expected_signs: {variable: "+"|"-"}` drops a numeric variable whose direction (AUC above or below 0.5, or the Spearman sign) disagrees.
  4. `redundancy` — absolute Pearson correlation over numeric survivors; variables are clustered greedily by univariate strength (strongest first) and every survivor correlated above 0.8 with a kept variable leaves with the kept one named in the reason; then VIF on the remaining numerics from the inverse of their correlation matrix over the bounded sample, iteratively removing the largest VIF above 10.
  5. `multivariate` — off by default; needs the `mlops` extra. L1 logistic regression (binary) or elastic net (continuous) on standardized complete cases drops zero-coefficient variables; permutation importance on the out-of-time sample (development when it is empty) drops variables at or below `min_importance` (0.0).
  6. `judgment` — `keep` and `drop` maps of `variable -> reason`; a reason is required. A drop removes, a keep reinstates a variable a metric step dropped; both write a ledger row.
- **Ledger.** One row per variable × step × metric: `variable, step, metric, value, threshold, rule, decision (pass|drop|info|keep), reason`, plus a per-variable summary row (`variable, selected, left_at, reason`). Long form keeps every column a dashboard filters on a scalar, like the stability tables. A variable is evaluated only by the steps it reaches.
- **Engines.** Pure rows (`Sequence[Mapping]`) and Spark DataFrames. Spark computes the per-value counts with `groupBy(...).count()` (one row per distinct value, as `monitor.spark.fit_spark` already does), class counts with conditional sums, Spearman through mid ranks joined back from the collected rank maps, and pairwise Pearson sums in one aggregate. VIF and the multivariate step use a bounded sample (`sample_rows`, default 50 000): all rows when the development sample is smaller, else a seeded Spark `sample` — exact parity is promised only below the bound.
- **Supervised transforms stay in training.** The result exposes the fitted WoE tables and an `apply_woe` helper that returns new mappings; nothing in this package writes them to a feature table.
- **Outputs.** `tables.py` declares two schemas (`selection_ledger`, `selection_variables`) keyed by `selection, run_id, variable[, step, metric]`, `to_frame(spark, kind, rows)` and `write_options(kind)` (merge on the key) so an ordinary task returns the frame. `tracking.log_selection(result)` logs thresholds as params, counts as metrics and the ledger, summary and final feature set as JSON artifacts when MLflow is importable and a run is active; otherwise it returns `False` and does nothing.

### Assumptions

- Numeric means `int`/`float` (not `bool`) in rows and numeric Spark types; booleans and strings are categorical — `## Design` steps 3–4.
- Closings compare as ISO text, matching `monitor.spark.window_frame` — `## Design` samples split.
- VIF from the inverse correlation matrix is exact for complete cases and needs no numpy — `## Design` step 4, `## Alternatives Considered`.

## Alternatives Considered

| Approach | Cost | Buys | Forecloses |
| --- | --- | --- | --- |
| **Summary-then-fold, two engines (chosen)** | a reduction per engine | parity by construction; reuses the monitoring bins and PSI | — |
| pandas/numpy only, collect to the driver | numpy and pandas in a required path | simpler code | large training sets; the light import; Free Edition proofs without extras |
| Spark ML (`ChiSqSelector`, `VectorAssembler` + `Correlation`) | ties selection to MLlib vectors | built-ins | an auditable per-variable ledger; the pure engine |
| VIF via numpy linear regressions per variable | numpy dependency | familiar formula | running without extras; the inverse-correlation form is equivalent |

## Risks

- **Spark/pure float drift** in correlations and Spearman — parity is asserted with a relative tolerance of 1e-9, and the fold is shared.
- **High-cardinality numerics** make the per-value count collection large — the same cost profile as `monitor.spark.fit_spark`; documented, with `sample_rows` bounding VIF and the multivariate step.
- **scikit-learn absent in CI** — the multivariate test is skipped there; it runs under `--group remote`, and the step refuses with a clear message naming the `mlops` extra.
- **Remote proof may not run in this round** if the free workspace is unavailable — recorded in `## Handoff`, never marked as passed.

**What shipped**

- `bricksmith.mlops.selection`: a reproducible feature selection funnel over a training set split by closing into development and out-of-time samples. It runs six optional steps (`quality`, `stability`, `univariate`, `redundancy`, `multivariate`, `judgment`) and leaves a per-variable ledger (value, threshold, rule, decision, reason) plus a per-variable summary row.
- Pure statistics with no numpy (quality shares, WoE/IV with quantile or monotone bins, KS/Gini, Spearman, Pearson, VIF from the inverse correlation matrix, chi-square quantile and the sample-size-aware PSI critical value). Bins and PSI/KS/AUC are reused from `bricksmith.monitor`.
- Two engines: rows and Spark DataFrames. Both fold through the same code, and a Free Edition remote test proves they produce the same ledger and final set.
- The multivariate step (L1 logistic or elastic net plus permutation importance) sits behind the `mlops` extra and is imported lazily. Without scikit-learn it refuses with a clear message.
- Outputs: typed `ledger` and `variables` tables with merge write options, `log_selection` for MLflow params, metrics and JSON artifacts when a run is active, and `apply_woe` for training-time WoE encoding. Nothing writes WoE into feature tables.
- Guide: `docs/how-to/feature-selection.md`, listed in the how-to index.

**Deviation from `## Design`**

There is no up-front `SelectionSummary`. The shared reduction is an `Engine` protocol that the fold queries step by step, so only variables still in play get aggregated. Parity still holds by construction (see `## Discoveries`).

**Left out**

Automated stepwise search over model families, SHAP, and correlation/VIF for categorical variables. Above `sample_rows`, Spark draws a seeded sample and exact parity is not promised.

Spec 80 (evaluation and documentation) consumes the ledger columns and the `selection/*.json` artifact names. Renaming either breaks it.
