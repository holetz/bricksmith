## Problem

Stability alerts only follow their automatic lifecycle. The gate counts every open alert and open critical
alert of the window (`stability/engine.py:536-538`), so with `fail_on: [critical]` or `[alert]` a known and
understood alert fails the task and blocks its dependents on every run until `close_after` greens arrive. Model
monitoring already has analysis / closed / risk-accepted actions in an append-only table
(`monitor/model/actions.py:1-7`, decision 0017), but spec 71 excluded stability.

## Proposal

- Lift the action rules (`action_row`, `latest_actions`, `apply_actions`, ordering, `insert_statement`) from
  `monitor/model/actions.py` into a shared `monitor/actions.py`; model monitoring keeps its behavior and tables.
- New `stability_alert_actions` table; runs and replays fold the latest action into the alert state at the run
  date; `risk_accepted` until `valid_until` keeps the alert out of the gate and notifications; `analysis`
  records ownership without changing the state; `closed` closes it with a reason.
- Add `acknowledged` (stops re-notification of the same alert) and `snoozed` (until a date) if the shared core
  supports them for both monitors.
- CLI verbs `bricksmith stability action` mirroring the model ones; open-alerts view exposes action columns and
  response-time measures (time to first action, time to close).
- Typed resolutions, as in commercial observability tools: `fixed`, `expected` (excluded from baselines and the
  trend — writes the matching period mark), `new_normal` (included, regime change mark), `false_positive`
  (included; counted in the false-positive rate per rule), each with author, reason and timestamp.
## Out of Scope

- Period marks (separate spec). Two-person approvals. Editing or deleting actions (append-only).

## Impact

### Product code this spec expects to touch

- `src/bricksmith/monitor/actions.py` (new) — shared action core lifted from model monitoring
- `src/bricksmith/monitor/model/actions.py` — thin wrapper over the core, same behavior and rows
- `src/bricksmith/monitor/stability/tables.py` — `actions` table, action views, response measures
- `src/bricksmith/monitor/stability/engine.py` — fold actions into the gate, notifications and judgment fingerprint
- `src/bricksmith/monitor/stability/cli.py` — `bricksmith stability action`
- `docs/how-to/stability.md` — the user guide of the capability

## Validation

- A risk-accepted critical alert does not fail a `fail_on: [critical]` gate until `valid_until`, and fails
  again the day after.
- Model monitoring tests pass unchanged after the lift.

## Design

- Shared core `monitor/actions.py` is parameterized by the entity column (`model` or `dataset`) and the allowed
  actions; model monitoring binds `model` and keeps its signatures, rows, hashes and tables.
- Stability keeps the stored alert rows in their automatic state (so replay, carry and supersede logic is untouched).
  Actions are folded into a derived copy of the alert rows at the run date: that copy drives the gate counts and
  the notifications, and the open-alerts view joins the latest action for display.
- `risk_accepted` until `valid_until` (inclusive) keeps an alert out of the gate and out of notifications;
  `closed` takes it out of both; `analysis` only records ownership. Gate counts: open = automatic open and not
  accepted/closed by a human.
- Typed resolutions (`fixed`, `expected`, `new_normal`, `false_positive`) are a `resolution` column of the action
  row, allowed only with `closed`. They are stored and exposed by the
  views (false-positive rate per rule); their effect on baselines and period marks belongs to the marks spec.
- The judgment fingerprint takes an optional digest of the dataset's actions (absent when none, so existing
  fingerprints stay equal): a new decision re-judges the window deterministically (decision 0017).
- `actions` joins the stability `KINDS`: the hook declares it as a merge target with an empty write that creates it.
- CLI `stability action` mirrors `model-monitoring act` (`--dataset`, `--alert-id`, `--action`, `--resolution`,
  `--reason`, `--author`, `--valid-until`, `--created-at`, `--scope`, `--prefix`, `--state`).

### Assumptions

- `acknowledged` and `snoozed` are not added: the shared core would change model monitoring's allowed actions, which
  the spec's validation requires unchanged.
## Alternatives Considered

- Writing the folded state (`accepted`) into the stored alert rows: rejected, it breaks the carry and supersede replay
  that reads `open`/`closed` states and mixes automatic and human facts in one table.
- Copying the action code into stability: rejected, two serialized forms would drift.

## Open Decisions

- none — every choice is recorded in `## Design`; the marks effect of typed resolutions is deferred by `## Out of Scope`.

## Risks

- Refactoring the model actions into the shared core must keep its serialized forms; covered by existing
  model monitoring tests.

Shipped: stability alerts now take human actions. A shared core `monitor/actions.py` (entity column, optional typed resolutions) backs both model monitoring (unchanged rows and behavior) and the new `stability_actions` table. Runs fold the latest action per alert into the gate counts, notifications and the judgment fingerprint at the run date: `risk_accepted` holds until `valid_until` inclusive, `closed` (with `fixed|expected|new_normal|false_positive`) and `analysis` as specified. `bricksmith stability action` records decisions; the views add action columns, response times and a per-rule false-positive rate; the how-to documents it.
