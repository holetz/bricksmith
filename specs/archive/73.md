## Problem

One set of limits per metric is too coarse: a segment may be informational only, a column may be naturally volatile, or a specific dataset may need stricter limits. Overrides scattered in code are hard to audit.

## Proposal

- Limit rules with selectors (dataset, column, segment, metric) and validity dates; the most specific matching rule wins (dataset +4, segment +2, column +1), ties by highest version.
- Rules may mark segments informational (computed and shown, never classified or gated), either by listing controlled segment values or the uncontrolled ones.
- Rules stored as reviewable data (a table or a project file), versioned and reported on each result row (`rule_id`).

## Out of Scope

- Reading rules from a Delta table: the reviewable store is a project file (TOML or JSON) or an inline list. Rules are plain mappings, so a later spec can add a table reader without changing the resolver.
- A CLI verb that explains which rule applied: every result row carries `rule_id` and `rule_version`, which is the audit trail this spec asks for.
- Rules for `monitor fit` / `monitor evaluate` (the legacy project-free pipeline): it keeps its single-threshold rules, as in spec 70.
- Per-grade calibration tests and exclusion composition (spec 82), which will consume informational segments; the monitoring report (spec 83).
- Informational handling in alerts, trend and gate beyond "never enter them": no new alert kinds.
- `relative` and `control` limit kinds in stability rules: stability keeps refusing them (spec 70); only model monitoring rules may use them.

## Validation

- `uv run pytest tests/unit/monitor -q` passes, including new tests that assert:
  - specificity: a rule naming the dataset scores 4, the segment 2, the column 1; the highest score wins, equal scores go to the highest `version`, then to the smallest `id`; a rule whose selector differs does not match; a wildcard selector matches anything.
  - validity: `valid_from` / `valid_to` are inclusive ISO dates compared with the result's period date; a rule with a bound never matches a period without a date; an expired rule falls back to the next match or the declaration defaults.
  - parsing refuses an unknown key, a duplicated `(id, version)`, a missing `id`, a limits rule without `metric`, a bad date, `valid_from > valid_to`, both informational lists at once, and (stability) a `relative` or `control` limit.
  - a rule file in TOML and in JSON loads to the same rules as the inline list; a missing file is a clear error.
  - an informational rule (`informational_segments: [...]` or `controlled_segments: [...]`) turns the matching results into status `informational` (never a color, never an alert, never counted by the gate); the whole population is always controlled.
  - stability and model results carry `rule_id` and `rule_version` (empty and `0` without a rule); a declaration without `rules` produces the same rows, fingerprints and lights as before.
  - model `replay_alerts` with a config recolors stored rows with the current rules and stamps the rule columns.
- `uv run pytest tests/remote/test_stability.py tests/remote/test_model_monitoring.py -q` on the free profile: rule columns written, a table created before the columns gains them, informational segment never gates.
- `uv run ruff check && uv run ruff format --check && uv run pyright` clean; `uv run pytest` green.

## Design

- 2026-11-24 — **Scope: one shared resolver, two monitors.** The proposal names dataset, column, segment and metric selectors; stability has all four natively, model monitoring has the model (as dataset), column, segment and metric. The resolver lives in `monitor/rules.py` and both monitors call it at the single place each builds a result (`stability.metrics._result`/`_judge`, `model.engine._result` and `model.alerts.relight`). Evidence: epic 85 task S10 (after S7, S8), spec 70 (shared limits).
- 2026-11-24 — **Rule shape.** A rule is a mapping with `id` (required), `version` (integer ≥ 1, default 1), optional selectors `dataset`, `column`, `segment`, `metric` (absent or empty = any), optional `valid_from` / `valid_to` (inclusive ISO dates), and one body: `limits` (a limits mapping, or `null` to disable the judgment) or one of `informational_segments` / `controlled_segments` (non-empty lists of segment values). A limits rule must name a `metric`; an informational rule may omit it. `(id, version)` is unique.
- 2026-11-24 — **Specificity.** Score = 4 if `dataset` is set + 2 if `segment` is set + 1 if `column` is set (the proposal's weights; `metric` is a required filter of limits rules and adds nothing). The highest score wins; ties go to the highest `version`; remaining ties go to the smallest `id` so the choice is deterministic. An informational rule counts its list as the segment selector (+2). Two resolutions run independently over the same key: the limits rule (else the declaration's `limits` / `column_limits` / defaults) and the informational rule.
- 2026-11-24 — **Validity.** Compared as ISO date text with the result's `period_date` (the monitoring period in model monitoring). A rule with any bound does not match a period without a date, so an undated period can never be judged by a time-boxed rule by accident.
- 2026-11-24 — **Informational segments.** `informational_segments: [v…]` makes the listed segment values informational; `controlled_segments: [v…]` makes every segment except the listed ones and the whole population informational. The verdict comes from the best matching informational rule alone (a more specific rule overrides a broader one entirely). A result of an informational segment is computed and stored with status `informational` (a new suppressed state, rank −1, reason `informational segment`), its limits columns empty and its direction empty, so alerts, trend, persistence and gate counts skip it as they skip any suppressed row; dashboards show it with its value. The whole population (`""`) is never informational.
- 2026-11-24 — **Segment text.** A segment selector or list item is compared with the stored segment text exactly: `channel=web` in stability (the canonical `col=value` key) and the segment value in model monitoring.
- 2026-11-24 — **Storage.** `rules` on a declaration is an inline list or a path to a TOML (`[[rules]]`) or JSON (`{"rules": [...]}` or a list) file, read when the declaration is parsed (the project file is the reviewable, versioned store; git carries the history). `to_dict` and the stability judgment fingerprint include `rules` only when there are some, so existing fingerprints and stored runs do not change; a rule edit rewrites the stability window like any limits edit.
- 2026-11-24 — **Reported on rows.** Result rows gain `rule_id` (STRING, empty without a rule) and `rule_version` (INT, `0` without a rule) in both monitors: the winning limits rule, or the informational rule for informational rows. Both tables gain them additively through the `evolution` write option (stability gets the option now; model monitoring has it since spec 70). Views select the row columns, so dashboards see the rule without a statement change.
- 2026-11-24 — **Rule kinds per monitor.** Stability rule limits are `absolute` only (spec 70). Model rule limits may be `relative` (same reference validation as the declaration) or `control`; the metrics of control rules join the set whose per-period baselines are measured, and replay reads stored baselines as for declared limits.
- Binding contracts: AGENTS.md (English, lightweight imports: no Spark at import, stdlib `tomllib`/`json` only), decision 0010 (synthetic tests, neutral vocabulary), decision 0012 (run-keyed tables), decision 0016 (limit kinds), epic 85 design.

### Assumptions

- Rules are evaluated per result row by selector equality, not globs — the proposal names exact selectors; recorded in `## Design`.
- An informational rule verdict is taken from the single best-matching informational rule — recorded in `## Design`.
- Decision number 0020 (0019 is reserved for spec 91 by epic 85's design) — lands in the task that writes it.

## Alternatives Considered

- **Overrides inside code only (`column_limits`).** Lost: the Problem rejects scattered overrides; `column_limits` stays as the declaration-level override and rules sit above it.
- **Rules in a Delta table first.** Deferred: it needs a reader on every monitor and a Spark dependency in parsing; a file reviewed in git meets "reviewable data, versioned" with no new infrastructure.
- **Glob selectors.** Lost: ranking specificity of overlapping globs is ambiguous; exact selectors keep the proposal's additive weights.
- **A new results table for informational rows.** Lost: the status column already expresses it, and every view and replay keeps working over one table.
- **Stability only.** Lost: the epic orders this spec after the model monitoring specs and spec 82 needs informational model segments.

## Open Decisions

- none — shape questions are settled by the Proposal, spec 70 and the stability and model precedents; defaults sit under `### Assumptions`.

## Risks

- A new column in existing stability results tables would break the merge. Mitigation: the `evolution` write option and a remote test over a table created without the columns.
- Overlapping rules surprise reviewers. Mitigation: deterministic tie-breaks, `rule_id` on every row, and a guide section with the scoring.
- A rule file read at parse time depends on the working directory. ACCEPTED — paths are as the declaration gives them (relative to the project root where tasks are discovered); an unreadable file is a plan error naming the path.
- Informational rows hide a real problem. ACCEPTED — they are stored and shown with their value; only classification and gating are skipped, by explicit declaration.
- Model monitoring replay recoloring with changed rules rewrites past lights. ACCEPTED — same behaviour as a limits change since spec 70; `rule_version` makes it visible.
