## Problem

Operating stability today means SQL in a client plus CLI verbs that only emit `INSERT` statements (the
model action pattern, `monitor/model/actions.py:172`), and code changes for limits and rules. Rules can only come
from inline declarations or files; reading them from a Delta table is documented as not covered
(docs/how-to/stability.md:329). There is no single place to look at a series, mark a period, act on an alert and
trigger a reprocess.

## Proposal

- A workspace operations layer: CLI verbs (`stability status|series|marks|actions|reprocess`) that execute through
  the SQL Statement Execution API on a declared warehouse and the Jobs API, using one explicit profile from `.env`
  (never `DEFAULT`, per the test setup rules), through `bricksmith.clients`.
- `bricksmith console`: a local web app (optional extra, served on localhost) built only on those public verbs:
  dataset list with status, series chart with band and marks, alert queue with actions, mark/unmark periods,
  run a reprocess job, view run history. The same app can be deployed as a Databricks App.
- `rules` accepts a Delta table (`rules: {table: catalog.schema.stability_rules}`) read at plan/run with the same
  validation, so the console can edit rules as data with an audit trail.
- All SQL goes through the Statement Execution API with named parameters, never string interpolation; this also
  replaces the literal-building `insert_statement` helper for writes the console performs.
- Deployed as a Databricks App, queries run with on-behalf-of-user authorization so Unity Catalog grants on the
  stability tables decide who can mark or act.
## Out of Scope

- Authentication beyond Databricks profiles/OAuth; multi-user permissions beyond Unity Catalog grants on the
  tables.

## Validation

- With a free profile, the console lists the example datasets, marks a period excluded, and the next run's

## Design

- **Everything the console does is a public verb.** `ops.py` holds one function per operation and takes two injected
  clients: a SQL runner (`run(statement, params) -> rows`) and a jobs client. The CLI verbs and the console are two
  thin callers of the same functions; the console owns no query of its own, so tests cover the verbs, not the pixels.
- **One explicit profile, the Statement Execution API.** `sql.py` builds the `WorkspaceClient` through
  `bricksmith.clients.Clients(context).workspace()` (never `DEFAULT`) and runs statements with
  `statement_execution.execute_statement(warehouse_id=..., statement=..., parameters=[StatementParameterListItem])`,
  polling until a terminal state; a failed statement raises `MonitorError` with the service message.
- **Named parameters only.** Values never enter statement text. Table names are the only interpolated part, and they
  pass `table_name` (plain-name validation). `write_row(table, row, columns)` returns `INSERT INTO t (cols) VALUES
  (:c1, ...)` plus the parameter list; `valid_until` is cast with `CAST(:valid_until AS DATE)` so it stays a
  parameter. This replaces `insert_statement` for every write the verbs perform; the printed-INSERT path of the
  existing verbs stays as it is.
- **Writes are the existing append-only rows.** `mark_row` and `action_row` build the row (so validation is the
  core's), `write_row` appends it. Nothing is updated in place; unmark is an `unmarked` row.
- **Reprocess runs a job.** `reprocess(jobs, job_id, periods, dataset)` calls `jobs.run_now(job_id=...,
  job_parameters={"reprocess": "<periods>"})`; the job's runner task passes it to the new `--reprocess` option of the
  entrypoint, which feeds `run_plan(reprocess=...)` (S7). Run history reads `<prefix>runs`.
- **Reads go through the views.** Status reads `<prefix>stability_datasets`-style views through the contract of
  `VIEW_COLUMNS`; series read `<prefix>series`; marks, actions and runs read their tables. Filters are parameters.
- **Rules from a Delta table.** `rules: {table: catalog.schema.stability_rules}` parses to `rules_table`; the hook
  reads the table with Spark at run time and replaces `rules` with the parsed rows. Rows are one rule per line:
  `rule_id`, `version`, `body` (the rule mapping as JSON, the exact shape of a rules file), `author`, `created_at`;
  for a repeated `(rule_id, version)` the latest `created_at` wins, so the table is an audit trail the console edits by
  appending. The same `parse_rules` validation applies; an invalid row fails the run naming it.
- **Console.** Standard-library `http.server` bound to `127.0.0.1` by default, no new dependency (so no extra is
  required; the SDK extra already covers the workspace client). A JSON API over `ops` plus one self-contained HTML page
  (dataset list, series chart as inline SVG with band and marks, alert queue, mark/unmark, reprocess, run history).
  State-changing routes accept only `POST` with `Content-Type: application/json` and a matching `Host`, which blocks
  cross-site form posts and DNS rebinding.
- **On-behalf-of-user.** With `--app` the console reads `x-forwarded-access-token` per request and builds the
  workspace client from it (token auth against the app's host), so Unity Catalog grants decide who can mark or act;
  without `--app` it uses the explicit profile.

### Assumptions

- The Databricks App runtime forwards the user token in `x-forwarded-access-token` (depends on the OBO proposal line).
- A deployed job already exposes a runner task; the job id is passed by the caller (depends on the reprocess line).

## Alternatives Considered

- **A web framework (FastAPI, Streamlit, Dash).** Rejected for now: a new dependency and extra for a thin client; the
  standard library covers a JSON API and a static page.
- **Spark through Databricks Connect for the operations.** Rejected: the proposal names the Statement Execution API
  on a warehouse, which needs no cluster and works with OBO.
- **Editing rules in place.** Rejected: append-only rows give the audit trail the proposal asks for.

## Open Decisions

- Live proof on Free Edition (marks, trend reflecting the mark, a reprocess from the console) needs workspace
  credentials absent from this run: recorded as pending evidence, decided at the next remote proof round.
- Deploying the console as a Databricks App resource (`app.yaml` through a bundle) is left to a follow-up once the
  App runtime shape is proved live.

## Risks

- A UI is a large surface to maintain; keep it a thin client over the CLI contracts and test the verbs, not
  the pixels.

## Discoveries

- decision: standard-library http.server instead of a framework and no new extra — the console is a thin client over the verbs; the proposal's optional extra is not needed (Alternatives Considered)
- decision: rules table rows are rule_id/version/body(JSON)/author/created_at, latest created_at wins — append-only audit trail; read at run time only, not at plan time
- decision: reprocess from the console starts a job with job parameter reprocess; added the runner option --reprocess (task 1.1) so the job's entrypoint can carry it into run_plan
- decision: live Free Edition proof and the Databricks App bundle resource are pending (no workspace credentials in this run) — recorded in Open Decisions
- decision: the console does not edit rules rows; rules_table is read-only from the console, rule_row builds rows for callers

## Outcome

Shipped: the workspace operations layer for stability. `stability status|series|actions|marks` read, and `mark|unmark|action|reprocess` write, through the SQL Statement Execution API on a declared warehouse (named parameters only, `sql.py`) and the Jobs API (`ops.py`), with `--warehouse`/`--scope` on the existing verbs keeping their offline forms. The runner entrypoint gained `--reprocess`, so a job run started by `stability reprocess --job` carries periods into `run_plan(reprocess=...)`. `rules: {table: catalog.schema.name}` reads rules from an append-only Delta table at run time (`rulestable.py`, latest `created_at` wins per rule version, same validation as an inline list). `bricksmith console` serves a standard-library local web app (dataset list, series chart with band and marks, alert queue, mark/unmark, reprocess, run history) over the same operations, with host/origin/content-type guards and a per-request user token for the Databricks App mode. `docs/how-to/stability.md` documents all of it. Verified: ruff, pyright and the full pytest suite (1879 passed, 100 skipped for missing pyspark/databricks extras).

Left out: the live Free Edition proof (a mark changing the next run's trend, a reprocess from the console) and the Databricks App bundle resource, both needing workspace credentials; editing rules rows from the console; the `Validation` statement is therefore covered by injected-client tests only.

Next reader: nothing in the console or verbs has touched a real workspace, so the first live run is the real check of the Statement Execution parameter typing (all parameters are sent as STRING and `valid_until` is cast in SQL) and of the OBO token flow.
