## Problem

Stability alerts are replayed only from the results inside the window (`src/bricksmith/monitor/stability/metrics.py:260`), and `alert_id` hashes the opening period (`metrics.py:410-413`). When an alert stays open longer than `max_periods`, its true opening period leaves the window, the replay opens it at a later period, its id changes, and `engine.py:303` marks the stored row `superseded`.

Consequence: one continuous incident becomes two alert rows, its open-period history is lost, and once alerts are notified (spec 74) a false "opened" notification is sent. No test covers `max_periods` for stability.

Proposal: carry an alert still open in the store forward (keep its id and opening period) instead of re-deriving it from the window; add a synthetic test that slides the window past the opening period.

## Proposal

`alerts()` receives the alerts already stored for the dataset. A replayed span that begins inside the window, for a metric whose stored alert is still `open` with an opening period older than the metric's first window period, adopts that stored alert: it keeps the stored `alert_id`, `opened_period`, `escalated_period`, `recurrence` and the higher severity, and counts the stored flagged periods plus the new ones. The engine passes the stored rows in, so `_superseded` no longer sees the id change. One continuous incident stays one row.

## Out of Scope

- Closing a stored open alert whose metric is all green across the window (it stays superseded, as today); recorded as a discovery.
- Notification delivery (spec 74).
- Reading only the window's stored rows (spec 100).

## Impact

- `src/bricksmith/monitor/stability/metrics.py` (`alerts`), `src/bricksmith/monitor/stability/engine.py` (call site).
- No table schema change; alert ids of incidents that never left the window are unchanged.
- Users: no configuration change.

## Validation

- Synthetic unit test: `max_periods` smaller than an incident's duration; run incrementally; assert one alert id, the original `opened_period`, no `superseded` row, a growing `flagged_periods`.
- `uv run pytest tests/unit/monitor/stability`, `uv run ruff check`, `uv run pyright`.

## Design

- `alerts(..., stored: Iterable[Mapping] = ())`: index stored rows with `state == open` by `(segment, column, metric, kind)` and the same `version`.
- For each key and kind, only the first replayed span can adopt, and only when the stored `opened_period` is earlier than the first period of that key's series. Later spans keep their own identity.
- Adopted fields: `alert_id`, `opened_period`, `escalated_period` (stored, else the span's), `recurrence` (stored or span), severity = critical if either is critical, `flagged_periods` = stored count + span flagged periods after the stored `last_period`.
- The message is built from the adopted opening period.
- Engine: `stored = store.rows(ALERTS, dataset)` read once and shared with `_superseded`.
- Decision recorded: Free-first and decision 0010 apply; tests are synthetic and offline, no remote proof is needed.

## Alternatives Considered

- Load every stored result so the replay starts at the true opening: rejected, it grows with the history and contradicts the window bound.
- Hash the id from the metric without the opening period: rejected, it breaks recurrence as a new incident after a close.

## Open Decisions

- none — the approach is decided above.

## Risks

- A stored open alert whose window begins at an unrelated new span could be adopted wrongly; mitigated by adopting only a span that starts in the first window period or when the stored alert's last period precedes the span's opening and no close lies between. Test covers a close then re-open.

## Outcome
