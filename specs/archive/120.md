## Problem

The model monitoring engine has its own pure/Spark split that diverges (reproduced on e2716ad with local pyspark 4.0.1):

1. Segment names: pure `segments()` gives ['False','True'] and NaN → "(null)" (`src/bricksmith/monitor/model/engine.py:309-313`); Spark gives ['false','true'] and "NaN" (`engine.py:375-386`). Results, alert-rule segment matching and per-segment baselines key differently per engine, so a baseline built on one engine misses on the other.
2. Decimal features: pure `numeric()` uses `isinstance(v, (int, float))`, False for `Decimal` (`engine.py:305-307`); Spark treats `decimal*` as numeric (`engine.py:371-373`). A feature without settings is fitted categorical in pure (`_feature_bins`, `engine.py:528`) but quantile-binned on Spark → different bins and CSI for the same development data (pure sees Decimal from collected Spark rows or DB drivers).

Consequence: model monitoring results and alerts depend on the engine. Done when both cases agree between engines using the same canonical segment spelling chosen in spec 118, with Spark parity tests skipped when pyspark is absent.

## Proposal

- The pure model-monitoring frame treats `Decimal` values as numeric, so a feature without settings is quantile-binned on both engines.
- The Spark model-monitoring frame names and selects segments with the canonical helpers (`segment_values`, `segment_frame`), so booleans are `true`/`false` and NaN or null is `(null)` on both engines.
- Spark null counting uses the shared `null_condition` rule.
- Local-pyspark parity tests prove both cases and skip where pyspark is absent.
- `docs/how-to/model-monitoring.md` states the segment spelling and the Decimal typing.

## Out of Scope

- Changing the canonical spelling itself: owned by spec 118 and the epic 121 owner decision.
- Timestamp or period spelling and unparseable label strings: marginal, noted in epic 121.

## Design

- Pure `numeric` accepts `int`, `float` and `Decimal` (never `bool`), matching Spark's `decimal*` rule; bins already go through `float(value)`.
- Spark `segments(column)` returns the keys of `segment_values`; `segment(column, name)` selects with `segment_frame` over that name's raw values, so the spelling is `segment_name`'s on both engines (decision 118: booleans lowercase, NaN is null). Spark `null_count` uses `null_condition`.
- Binding: epic 121 owner decision for 118/120; decision 0010 (independent development, synthetic tests).

### Assumptions

- A Decimal column holding NaN cannot occur (Decimal NaN is out of scope); `is_null` already ignores it. Depends on: Design.

## Alternatives Considered

- Converting Decimal to float in the pure frame before profiling: rejected, `Decimal` values keep their `category_text` spelling for categorical features and only the numeric test needs to change.

## Open Decisions

- none — the spelling was decided by the epic 121 owner decision.

## Risks

- A stored per-segment baseline built on Spark with a `NaN` segment keeps the old `NaN` key and misses once. ACCEPTED — documented as a migration note in the how-to.
