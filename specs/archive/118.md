## Problem

`measure_spark` (`src/bricksmith/monitor/spark.py`) diverges from the pure engine (`measure.py`, `bins.py`) on the same input; there are no pure-vs-Spark parity tests (`tests/unit/monitor` never imports Spark). Reproduced on e2716ad with local pyspark 4.0.1, fitting once and comparing `measure_rows` vs `measure_spark`:

1. NaN label: pure skips it as null (`measure.py:108`); Spark casts to double, `isNotNull()` is true for NaN, so it counts as labeled and invalid (`spark.py:79,82-83`) → auc, gini, ks, brier, ece all `unavailable: invalid_labels` on Spark while pure computes them.
2. NaN in a categorical numeric column: pure → null bin (`bins.py:63`); Spark checks only `isNull()` and NaN casts to "NaN" → `unseen` (`spark.py:26-29`) → CSI 0.0 vs 3.91, null_rate 0.25 vs 0.0.
3. Double categories: pure spells `str(1e7)` = "10000000.0" (`bins.py:30-34`, also used by `fit_spark` `spark.py:52`); Spark `cast("string")` gives "1.0E7" (`spark.py:25`) → always `unseen`, CSI 0.0 vs 8.52.
4. Segment names: pure `str(True)` = "True", NaN → "(null)" (`measure.py:233-235`); Spark cast gives "true"/"NaN" (`spark.py:116`) → per-segment baselines and rule matching miss across engines (`volume_ratio` `empty_reference`). The stability engine already lowercases booleans (`stability/spark.py:43-48`).

Consequence: the same data yields false or hidden alerts depending on the engine. Done when the four cases agree between engines with one canonical spelling, covered by Spark parity tests (skipped when pyspark is absent).

## Proposal

- `measure_spark` and `measure_rows` return the same measurements (statuses, reasons, counts, values within 1e-9, per-bin details, segment names) on the same rows for the four reproduced cases: a NaN label, a NaN in a categorical numeric column, double categories, and boolean or NaN segment values.
- One canonical text spelling holds on both engines (owner decision for 118/120, epic 121): booleans are `true`/`false`, NaN is null (null bin, `(null)` segment, unlabeled row), doubles are spelled as the pure engine and the stored references already spell them (`str(float)`), so frozen references stay valid.
- `bricksmith.monitor.spark` exposes the Spark spelling helpers spec 120 reuses: the null-or-NaN condition, the segment values grouped by canonical name, and the segment filter.
- Spark parity tests cover the four cases; they run where a local pyspark session can start and skip otherwise.
- `docs/how-to/monitoring.md` states the canonical spelling and the migration note for pure-engine boolean segment names.

## Out of Scope

- The model monitoring engine's own pure/Spark split (`src/bricksmith/monitor/model/engine.py`): spec 120, which reuses this spec's helpers.
- The stability engine (`src/bricksmith/monitor/stability/spark.py`) calling `bin_expression` without the column type: spec 116 owns that file in this wave; parked as a discovery.
- Timestamp microsecond spelling, NaN window columns and unparseable label strings (e.g. the string `"NaN"` as a label): kept out by the epic's map as marginal.
- `-0.0` versus `0.0` as distinct segment names: Spark's `distinct` normalizes them; accepted risk.
- Remote proof on a workspace: the parity is a property of Spark's cast semantics, proved on local pyspark; no corporate execution.

## Design

- **Canonical spelling** (owner decision, epic 121): a non-null value's text is `category_text(value)` — `true`/`false` for booleans, `str(value)` otherwise; null and float NaN are null (`is_null`). Pure `segment_name` adopts `category_text`; categorical bins already used it.
- **NaN on Spark** is null only for `float`/`double` columns (`null_condition(df, column)`: `isNull() | isnan(col)` when the dtype is float or double, else `isNull()`). This mirrors `is_null`, which treats only Python floats as NaN: a string `"NaN"` stays a value on both engines.
- **Double categories on Spark** cannot be spelled by `cast("string")` (`1.0E7`, `1.0E-5`). `bin_expression(spec, dtype="")` matches a float/double column's categories by value (`col == float(category)`), so the bin id carries the stored category text; other types keep the string cast (booleans and integers already agree). The default `dtype=""` keeps current callers unchanged.
- **Labels on Spark**: a NaN label (float/double column) is unlabeled, as `summarize` skips it.
- **Segments on Spark**: distinct raw segment values are collected (one small row per value, as before) and named on the driver with `segment_name`; each segment is filtered by its raw values (`isin`, plus `null_condition` for the `(null)` segment). Names therefore equal the pure engine's by construction, doubles included.
- Helpers spec 120 reuses live in `bricksmith.monitor.spark`: `null_condition`, `segment_values`, `segment_frame`.
- Parity tests start a local `SparkSession` (`local[1]`) and skip when pyspark is missing or the session cannot start (the project venv carries Databricks Connect, which refuses local sessions).

### Assumptions

- No stored artifact in the repo keys a segment as `True`/`False` (grep over tests, docs, examples found none) — `## Design`, migration note in `docs/how-to/monitoring.md`.

## Alternatives Considered

- **A Python UDF calling `category_text` on Spark**: exact for every type but serializes every row through Python; rejected for the cost on large tables when a finite category list and driver-side segment naming give the same spelling.
- **Change the pure engine to Spark's spelling (`1.0E7`)**: would invalidate every stored reference with double categories; rejected by the owner decision.
- **Format doubles in Spark SQL with `format_number`/`printf`**: cannot reproduce Python's shortest round-trip repr; rejected.

## Open Decisions

- none — the canonical spelling is the owner decision in epic 121; the remaining choices are settled by the code evidence in `## Design`.

## Risks

- Pure boolean segment names change from `True`/`False` to `true`/`false`: stored per-segment measurements, baselines and segment-specific alert rules written by the pure engine key differently. Mitigation: migration note in `docs/how-to/monitoring.md`; the Spark engine already wrote lowercase.
- ACCEPTED — `-0.0` and `0.0` collapse into one Spark segment (`0.0`) while the pure engine keeps two; negligible for segment columns.
- Parity tests skip in the project venv; mitigation: the task `verify:` runs them in an isolated local-pyspark environment and requires them not skipped.
