## Problem

Found by the autopilot round 2 model scout (2026-11-24), reproduced on main e564870 with a synthetic pure-engine run: development 2024-01..03, `label_lag: 3`, metrics `discrimination` and `grade_order`, `model_version_column` switching v1 → v2 at 2024-09.

`src/bricksmith/monitor/model/engine.py:1053-1054` takes `version` from the monitoring-period rows; `engine.py:1033` and `:1039` measure the lagged data-period rows and stamp them with that version. The `gini` and `grade_inversions` rows for 2024-09/10/11 carry `model_version=v2` although their data periods 2024-06/07/08 were all scored by v1.

Consequence: after a release, the first `label_lag` periods report the old model's matured performance as the new version's. Trend and persistence series are keyed by version (`engine.py:896-897`), so the new version's series starts with the old model's Gini and calibration, and alerts and human actions attach to the wrong version.

Proposal (decided by the autopilot as delegated owner): stamp matured-label results with the version of the measured (lagged) rows; version-keyed alert identities of those results shift accordingly — document it in the model guide; add the v1 → v2 sequence as a regression test. A lagged frame holding more than one version is measured per version or reported as mixed — the worker picks the smaller correct behavior and records it in Design.

## Proposal

- A result whose `data_period` differs from its `monitoring_period` (a matured-label metric under `label_lag` or `lags`) carries in `model_version` the version of the rows it measured, not the version of the monitoring period's rows.
- With `model_version_column` switching v1 → v2 at a release, the first `label_lag` monitoring periods after it report the matured `gini`/`grade_inversions` under `v1`; the v2 series starts only when v2-scored rows mature.
- The run record's `model_version` lists every version its results carry, lagged versions included.
- The model monitoring guide states that matured results are stamped with the measured rows' version, so version-keyed series and alert identities follow the measured model.
- A regression test reproduces the v1 → v2 sequence of the problem and pins the stamped versions.

## Out of Scope

- Splitting a multi-version lagged frame into one result per version — ruled out by the owner decision (smaller correct behavior); see `## Design`.
- Migrating alert identities or human actions already stored under the old stamping — the owner accepted the shift; old alerts close or expire by their own rules.
- Results with an unavailable data period (`data_period_unavailable`): nothing was measured, they keep the monitoring period's version so their series stays continuous.
- Estimating performance before labels mature — out of the round's scope (epic 109 policy).

## Design

- **Rule: a result is stamped with the version of the rows it measured.** In `_measure_family`, when `lagged` is not `None` and differs from the monitoring period, the version is `_version(rows, config)` over the lagged rows; otherwise the monitoring period's version. `_version` already returns a literal `model_version` unchanged, so only `model_version_column` declarations move.
- **Multi-version lagged frame (owner decision: smaller correct behavior):** `_version` already joins the sorted distinct versions with `,` (the same "mixed" text a monitoring period holding two versions gets today). The lagged result is stamped that joined text and is measured once over all its rows — no per-version split. It is correct (the label says which models scored the rows) and adds no new result rows, series or table shape.
- **Run record:** the lagged version is added to the window's `versions`, so the run's `model_version` lists every version its results carry.
- **Accepted consequence (owner decision):** trend and persistence series and alert identities are keyed by `model_version` (`_series`, `alert_rows`), so after this change the matured results of a release's first `label_lag` periods join the old version's series; alerts and actions recorded under the previous stamping no longer match those results. Documented in `docs/how-to/model-monitoring.md`.
- **Spark path:** `Frame.texts` is already called on the monitoring frame per period; the lagged call adds one distinct-values read per lagged data period. No remote proof is required (pure-engine fix; epic 109 caution).

### Assumptions

- The lagged rows' version column is populated like the monitoring rows' (same declaration) — `## Design` rule depends on it; an all-null column yields `""`, as today for the monitoring frame.

## Alternatives Considered

- **Measure a multi-version lagged frame per version** (one result per version for the same monitoring period): rejected — it multiplies result rows per period, breaks the one-result-per-series-per-period invariant of `apply_trend`/`_span_alerts`, and the owner asked for the smaller correct behavior.
- **Keep the monitoring version and add a `data_model_version` column:** rejected — leaves series and alerts attached to the wrong version, which is the defect, and changes the table schema.

## Open Decisions

- none — the owner decisions recorded in epic 109 `## Design` settle the stamping, the multi-version case and the identity shift.

## Risks

- ACCEPTED — alert identities and actions of matured results stored before this change stop matching after a version release (owner decision); documented in the model guide.
- A dashboard filtering `latest` by the newest version shows no matured metrics for the first `label_lag` periods after a release — correct behavior (no v2 labels matured yet); documented.
