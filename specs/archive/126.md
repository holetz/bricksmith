## Problem

Found by the round-5 map of the 2026-11-24 autopilot (epic 125), reproduced on main 3d125c7 with synthetic rows (MemoryStore + merge_rows, the pattern of `tests/unit/monitor/stability/test_stability_revision.py`).

With `revision: true` and `refresh_periods: 2`, a period that already has a first-publication snapshot and is deleted from the data in a later run (a correction that wipes a month) is reported nowhere:

- `src/bricksmith/monitor/stability/engine.py:440` builds the period list from today's rows only (`_engine_periods`), so the vanished period never reaches the window or `_revisions` (`engine.py:403-426`);
- `src/bricksmith/monitor/stability/revision.py:135-138` compares only periods present in the current profiles;
- `src/bricksmith/monitor/stability/tables.py:102-107` only upserts, so the first publication's profile and result rows stay, and the `dataset_status` view (`tables.py:166-174`) keeps showing the old `row_count`.

Reproduction: three months of 100 rows, run r1, then r2 with 2026-02 deleted → `results periods: []`, `revision 02: []`, `profiles 02 run_ids: {'r1'}`. Deleting the latest period gives the same silence. A segment that vanishes inside a present period already works (`reg=N` → -1.0 red), and a vanished category gets zero-count bins.

Consequence: `docs/how-to/stability.md:122-136` promises revision catches re-published history that silently changes numbers; an emptied period — the largest such change — raises no alert, no gate failure, and the dashboard keeps the stale count.

Done when: a snapshotted period inside the range the run refreshes that has no rows now yields `revision_row_change = -1.0` per snapshotted segment (judged by the configured limits), its current profile no longer shows the stale count, the behavior is covered by regression tests (middle and latest period), and the how-to states the rule.

## Proposal

When `revision` is on, find the periods that have a first-publication snapshot, lie in the refresh range (the `refresh_periods` most recent periods of stored history, the latest included even when it vanished) and have no rows in today's data. Replace each one's current profile with zero-count rows of this run (spec 116 convention) and judge it through the existing revision comparison, so each snapshotted segment gets `revision_row_change = -1.0` under the configured limits. State the rule in the stability how-to.

## Out of Scope

- Periods older than the refresh range are not judged (owner decision of 2026-11-25, epic 125).
- Rewriting the stale `row_count` result row of a vanished period in `stability_results`.
- A separate Spark code path: the engine reads only through the `Store`, so the rule is engine-level.

## Impact

`src/bricksmith/monitor/stability/engine.py`, its regression tests and `docs/how-to/stability.md`. No schema, table or config change. Existing behavior without `revision` is unchanged.

## Validation

`uv run pytest tests/unit/monitor/stability -q` covers a vanished middle period, a vanished latest period (gate fails), a period older than the range (not judged, profile kept), configured limits and `revision` off. `uv run ruff check`, `uv run pyright` and the full `uv run pytest` stay green.

## Design

`_vanished` takes the periods of the revisions snapshots (stored history), keeps the last `refresh_periods`, and returns those absent from today's periods. `_emptied` copies their stored profile rows with count, weight and sums at zero and this run's id. These rows join the current profiles and the written profile rows. The revision comparison runs over the window plus the vanished periods; their results are emitted, and the alert replay sees them. The run's latest period is the newest of the window and the vanished periods, so a vanished newest period counts for the gate.

## Alternatives Considered

Reading stored history from the profiles table instead of the snapshots: needs an unfiltered read of the largest table. With `revision` on, every stored period has a snapshot, so the snapshots give the same range at lower cost.

## Open Decisions

- none — the owner decided the rule on 2026-11-25 (epic 125 Design).

## Risks

A dataset that legitimately drops its newest period now fails a red gate when `revision` is on: that is the requested behavior. Periods stored before `revision` was switched on are snapshotted only if still loaded, so they are judged only after a snapshot exists.
