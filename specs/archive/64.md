## Problem

Data projects need to know, on every run, whether the tables they publish still look like the data they were designed and validated on. Today bricksmith can measure drift (`bricksmith.monitor`, BS-13), but only as separate, hand-wired `monitor` tasks around a fitted reference oriented to model scores. Nothing observes an ordinary table where it is produced: no task can declare "watch these columns per period", no period history accumulates automatically, no traffic light or persistence rule turns noise into an actionable alert, and the run cannot decide to fail on a confirmed instability. A second round of behavioral review of the private reference and of the earlier standalone binning prototype found the same gap there: frozen binnings and per-period counts existed without any consumer, and a model-monitoring engine re-implemented banding, PSI, traffic lights, trend checks and persistence alerts on its own, with no shared core and no dashboard model.

## Proposal

Deliver data-stability monitoring as one capability of the library, declared on tasks and executed by the shared runner right after a task writes, with a statistical core that model monitoring also uses:

1. A shared, pure core in `bricksmith.monitor`: traffic-light limits with suppressed states, a least-squares trend check and an alert-persistence lifecycle.
2. Frozen, versioned binnings with type inference (numeric quantiles with an optional exact-zero bin, low-cardinality numerics and text as categories, skipped types with reasons).
3. Period profiles (bin counts, weights and per-bin moments per period and segment, pure and Spark engines with identical results), baselines (fixed window, previous period, rolling periods) and stability metrics.
4. A `stability` key in task metadata: the plan lists the stability tables as declared targets, the worker profiles the task's output after a successful write, persists the results and applies a gate that warns or fails the task.
5. Dashboard-ready tables and views (results, bin shares, alerts, runs) with a documented star model, a guide, an example and Free Edition proof.

## Out of Scope

- A dashboard file. The tables and views are the deliverable; a BI model is built on them by the project.
- Human alert workflow (acknowledgement, risk acceptance), notification delivery, maturation lag between monitoring and data dates, per-segment rule specificity and revision reliability. They are captured as separate follow-up specs listed under Tasks.
- Changing the BS-13 contracts: references, measurements, rules and the four monitor tables keep their behavior and serialized forms.

## Impact

- `src/bricksmith/monitor/` gains the shared core and a `stability` subpackage; `bricksmith.plan.build`, `bricksmith.runner.execute` and `bricksmith.runner.report` gain the declared-targets and post-write hook.
- New CLI group `bricksmith stability`.
- New guide `docs/how-to/stability.md`, example tasks in `examples/shared_schema`, remote test and evidence.

## Validation

- Every member spec passes its own validation; the full gate (`ruff check`, `ruff format --check`, `pyright`, `pytest`) is green locally and in CI.
- Remote proof on Free Edition: a synthetic monthly table with an injected drift produces profiles, results, alerts and runs; a gated task fails and blocks its dependents; a rerun is idempotent; the Spark and pure engines agree.

## Design

Member specs carry the design. Cross-cutting rules:

- One statistical core. Bins (`BinSpec`), PSI (`stats.psi_terms`) and the versioned `Reference` are reused; new pieces (limits, trend, persistence) are generic and engine-free.
- Computation stays DataFrame in, rows out. Persistence happens through the run's `TableIO` and only into targets the plan declares, so dry runs and plan review show every stability write.
- Observing never breaks a run unless the task opts in: the default gate warns; failing is declared per task.

## Alternatives Considered

- Separate monitoring tasks per table (the BS-13 pattern). Rejected as the only way: it doubles the task count, needs manual wiring per table and cannot gate the producing task. It remains available.
- Writing stability tables as hidden side effects of the runner. Rejected: decision 0009 requires visible writes; the targets are declared in the plan instead.

## Open Decisions

- none — decisions are recorded in the member specs.

## Risks

- Per-period history is collected on the driver to compute results; very large `periods × segments × columns × bins` products need the documented caps.
- Concurrent merges into the shared stability tables from parallel tasks can conflict on Delta; writes are serialized per process and retried on conflicts.
