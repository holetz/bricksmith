## Problem

Found by the round-5 map of the 2026-11-24 autopilot (epic 125) from a spec-118 runner lead, reproduced on main 3d125c7 with local pyspark: `uv run --isolated --no-project --with pyspark==4.0.1 --with-editable . --with pytest python <script>` (synthetic: 2 months × 40 rows, double column declared `type: categorical` with {1e7, 0.5, 2.0, NaN}).

Spec 118 made the generic Spark measures NaN-aware and value-matched for floating columns when `bin_expression` receives the column `dtype` (`src/bricksmith/monitor/spark.py:72-79`). The stability Spark engine still calls `bin_expression(spec)` without `dtype` at `src/bricksmith/monitor/stability/spark.py:145` (`_with_counts`) and `:227` (`profile_spark`), so the column is cast to string: NaN becomes `"NaN"` and 1e7 becomes `"1.0E7"`, both landing in `unseen`.

Output: `('rate','cat:10000000.0') pure 10 spark 0`, `('rate','null') pure 10 spark 0`, `('rate','unseen') pure 0 spark 20`; `null_rate` pure 0.25 vs spark 0.0; `unseen_rate` pure 0.0 vs spark 0.5. The fit matches (it counts in Python), so the Spark profile disagrees with the fitted reference. Numeric doubles with NaN already match.

Likely the same class (unverified): segment text `stability/spark.py:45-50,155` casts a double segment value to `1.0E7` instead of the pure engine's canonical spelling.

Consequence: on Spark, a categorical double column reports a wrong null rate and an inflated unseen rate; against a fixed baseline or a limit on those metrics it yields wrong PSI and false yellow/red alerts, and pure and Spark runs of the same data disagree.

Done when: the stability Spark profile (and segment keys, if confirmed) bins categorical double and NaN values exactly like the pure engine, with parity tests in the existing local-pyspark parity suite.

## Proposal

Pass the column Spark dtype to `bin_expression` in the stability Spark engine (`_with_counts`, `profile_spark`), so categorical double columns bin NaN as `null` and match categories by value like the pure engine. Spell a floating segment value in `segment_column` like `segment_text` (`str(float)`, `(null)` for NaN). Prove both with parity tests in the local-pyspark parity suite.

## Out of Scope

- Making the parity suite part of the default gate (owner: epic 124, spec 122).
- Model-monitoring Spark engine (already covered by specs 118 and 120).
- Fit paths: the fit counts in Python and already matches.

## Impact

`src/bricksmith/monitor/stability/spark.py` and `tests/unit/monitor/test_spark_parity.py`. No schema, table or config change; non-floating columns behave as before.

## Validation

`uv run --isolated --no-project --with pyspark==4.0.1 --with-editable . --with pytest pytest tests/unit/monitor/test_spark_parity.py -q` proves pure and Spark profiles agree on a categorical double column with `{1e7, 0.5, 2.0, NaN}` and on double and NaN segments. `uv run ruff check`, `uv run pyright` and `uv run pytest` stay green.

## Design

`_with_counts` and `profile_spark` look the dtype up in `dict(df.dtypes)` and pass it to `bin_expression`. `segment_column` builds, for a float/double segment column, an expression that is null for NaN, uses the Spark string cast of the double value inside `[1e-3, 1e7)` (where Java and Python spell alike) and a driver-collected `when` chain of `repr`-spelled values for the finite and infinite values outside that range (few in practice). Float32 is cast to double first, as Python widens it. Per owner decision of 2026-11-25 in epic 125 Design.

## Alternatives Considered

A Python UDF per row for the spelling: slower and opaque to the optimizer. Collecting every distinct value of the segment column: unbounded driver memory on a high-cardinality column.

## Open Decisions

- none — the owner decided the approach on 2026-11-25 (epic 125 Design).

## Risks

The in-range cast relies on Java `Double.toString` matching `repr` there (true on current JDKs, which use the shortest representation); the parity test covers 0.5 and 2.0. A column with many distinct out-of-range values grows the `when` chain.
