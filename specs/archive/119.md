## Problem

A rules file path is used as given: `load_rules_file` does `Path(path)` (`src/bricksmith/monitor/rules.py:232`), parsed at plan build (`stability/config.py:465` via `plan/build.py:93`) and again in the worker (`stability/hook.py:114`). mlops declarations instead resolve against `find_project_root` (`src/bricksmith/mlops/spec.py:415`, `mlops/tasks.py:110`).

Consequence: the documented `"rules": "monitoring/rules.toml"` (`docs/how-to/stability.md:201`) works only when the process runs from the project root. Reproduced on e2716ad: from `/tmp`, `parse_config({'period':'p','rules':'monitoring/rules.toml'})` raises "cannot be read"; from the project dir it loads 1 rule. Plan build with `--project other/dir` fails `invalid_stability`; a worker whose cwd differs (job on a cluster) raises inside `run_stability`, and with the default `on_error: warn` the task succeeds unchecked (inferred from code); a same-named file in the cwd is silently used.

Done when relative rules paths resolve against the project root in plan build and worker (every caller of `load_rules_file`, model monitoring included), absolute paths keep working, a test runs from another cwd, and the doc states the resolution base.

## Proposal

- A relative rules file path in a `stability` or `model_monitoring` declaration resolves against the project root, never the working directory.
- Plan build (`--project other/dir`) and the worker (any cwd) load the same file; an absolute path is used as given.
- With no project root known (the standalone `stability`/`model` CLIs and direct `parse_config` calls) the path keeps resolving against the working directory.
- `docs/how-to/stability.md` and `docs/how-to/model-monitoring.md` state the resolution base.

## Out of Scope

- Walking up to `bricksmith.toml` to find a root: the plan builder and the worker already know the project root they were given, so they pass it on.
- Adding the rules file content to the plan fingerprint: a separate concern, not part of path resolution.
- Reading rules from a Delta table (already a captured follow-up).

## Impact

### Product code this spec expects to touch

- `src/bricksmith/monitor/rules.py` — `load_rules_file` and `parse_rules` take an optional root.
- `src/bricksmith/monitor/stability/config.py`, `src/bricksmith/monitor/model/config.py` — pass the root to `parse_rules`.
- `src/bricksmith/monitor/stability/hook.py`, `src/bricksmith/monitor/model/hook.py` — pass the root through `resolve`, targets and `declarations`.
- `src/bricksmith/graph/model.py`, `src/bricksmith/graph/build.py`, `src/bricksmith/plan/build.py`, `src/bricksmith/runner/execute.py` — carry the project root to plan build and the worker.

## Validation

- `uv run pytest tests/unit/monitor tests/unit/graph tests/unit/execution -q` passes, including a test that loads a relative rules path from another cwd through `parse_config` with a root, through plan build and through `run_plan`.
- The existing cwd-relative behaviour without a root is unchanged.
- `uv run ruff check && uv run pyright` pass.

## Design

- **A root parameter, not a global.** `load_rules_file(path, *, root=None)` and `parse_rules(..., root=None)` resolve a relative path as `root / path` when `root` is given, else as given (cwd). The root is threaded explicitly because workers run in threads, where a context variable would not follow. Alternatives: `find_project_root(cwd)` (wrong when cwd is not under the project, the very bug), a context variable (lost in threads).
- **Plan build learns the root from the graph.** `TaskGraph` gains an optional `root` set by `build_graph` from `project.root`; `_stability_targets` and `_model_monitoring_targets` pass it. Without a graph root (hand-built graphs) behaviour is unchanged.
- **The worker passes its own `root`** (`_Worker.root`, the `project_root` of `run_plan`) to `run_stability` and `run_model_monitoring`, which pass it to `declarations`.
- Absolute paths are unaffected (`Path.__truediv__` with an absolute right side yields it).

## Alternatives Considered

- Resolve inside `load_rules_file` by walking up from the cwd to `bricksmith.toml`: fails from `/tmp` or on a cluster, the reported case.

## Open Decisions

- none — the owner decision in epic 121 fixes the base as the project root.

## Risks

- A hand-built graph without a root keeps cwd resolution: ACCEPTED — only `build_graph` output is the supported source of plans.
- A TaskGraph equality or serialization consumer sees the new field: mitigated by a default value and the full unit suite in the task's verify.
