## Problem

Model alert actions are ordered by `created_at` compared as raw text with no format check: `src/bricksmith/monitor/model/actions.py:89-91` (`latest_actions`), `action_row` never validates it (:51, :78), the column is STRING (`monitor/model/tables.py:74`), the SQL latest-action view sorts the same way (`tables.py:244`), and `act --created-at` is free text (`monitor/model/cli.py:187`).

Repro (round-7 scout ses_def3167b8ffeJSJxTB27yHVF2q): a `risk_accepted` at `2026-11-25T01:00:00+00:00` followed by an `analysis` at `2026-11-24T23:00:00-03:00` (02:00 UTC, later) leaves the alert `accepted`; `created_at="not a time"` is accepted.

Consequence: docs/how-to/model-monitoring.md:360-361 promise "the latest action of an alert (by created_at) decides, so a later analysis re-opens an accepted alert". With a manual `--created-at` carrying a non-UTC offset the re-open is ignored and the alert keeps bypassing the gate until `valid_until`; garbage timestamps are stored and sort arbitrarily. The default created_at (UTC seconds) orders correctly, so only manual timestamps are affected.

## Proposal

`action_row` parses `created_at` as ISO-8601 (`datetime.fromisoformat`), refuses an unparsable value with a `MonitorError`, reads a naive timestamp as UTC, and stores the instant normalized to UTC in the default's form (`YYYY-MM-DDTHH:MM:SS+00:00`, sub-second digits kept only when present). The `action_id` hashes the normalized value, so one instant written with two offsets is one row. `latest_actions` orders by the parsed UTC instant (then `action_id`), parsing stored rows on read; a stored value that does not parse keeps working and sorts before every parsable one, by raw text among themselves. `act --created-at` inherits the check and refuses garbage. The model-monitoring how-to gains a note on the rule and on rows stored before it.

## Out of Scope

- The SQL `actions_latest` view (`monitor/model/tables.py`) keeps ordering by the STRING column: rows written from now on are normalized UTC, so text order equals time order for them; reordering stored legacy rows in SQL needs a remote proof this spec does not run.
- No migration rewrites stored rows; the column stays STRING.
- Alert `created_at` (run timestamps, not human input) is untouched.

## Design

- Parser: one private helper `_utc_instant(value) -> datetime | None` (`datetime.fromisoformat`; naive → `tzinfo=UTC`; `astimezone(UTC)`); `action_row` refuses on `None`, `latest_actions` falls back to raw text on `None`.
- Storage form: `isoformat()` of the UTC instant, `timespec="seconds"` when there are no microseconds, which is exactly the CLI default's form.
- Ordering key in `latest_actions`: `(1, instant, action_id)` for parsable values, `(0, raw text, action_id)` otherwise — tuples never compare a datetime with a string because the first element differs.
- Owner decisions: epic 136 `## Design`, bullet "2026-11-25 — Map kept 134 …" (135 part).

### Assumptions

- A date-only value (`2026-01-01`) is a valid ISO-8601 timestamp at midnight UTC (Python 3.11+ `fromisoformat`) — affects `## Tasks` 1.1 tests.
- Unparsable legacy values sorting before parsable ones is the least surprising "keeps working": a real timestamp is never beaten by garbage — affects 1.1.

## Alternatives Considered

- Order by raw text but refuse non-UTC offsets: rejected by the owner decision (normalize, don't refuse valid offsets).
- Store the original text and parse only on read: keeps garbage in the table and the SQL view order wrong; rejected.

## Open Decisions

- none — the owner settled every behavior in epic 136 `## Design`.

## Risks

- A caller passing a non-ISO placeholder (`"t1"`) to `action_row` now gets an error; only unit tests did this, and they move to ISO values in 1.1.
- `action_id` of a manual non-UTC timestamp changes versus a row written before; stored rows keep their stored id, so only a re-write of the same old decision would duplicate it.
