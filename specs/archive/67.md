## Problem

Stability is a property of a series: each period (month, day, cohort) of a table compared with a baseline. Recomputing every period from raw data on each run is wasteful, and storing only an index (PSI) loses the information needed to change the baseline, explain a jump bin by bin, or compute other metrics later. The reviewed prototypes stored per-period bin counts ("observations") apart from frozen bins and computed indices on demand against fixed or moving references; that separation is the core idea to keep.

## Proposal

Add `bricksmith.monitor.stability` with:

- `StabilityConfig` parsed and validated from task metadata (period column, columns or `auto`, exclusions, segments, weight, baseline, limits, trend, persistence, gate, caps).
- `profile(binning, data, periods, segments, weight)` producing long profile rows per period, segment, column and bin with `count`, `weight`, `value_sum` and `value_sum_sq`; a pure engine for row lists and a Spark engine with one grouped aggregation per segment set, giving identical rows.
- Baselines from stored profiles of the same binning version: `fixed` (a period range, default the binning fit window), `previous` (lag N) and `rolling` (previous N periods).
- `compute_results(...)`: per period, segment and column the metrics `psi`, `null_rate_delta`, `unseen_rate_delta`, `mean_shift` (numeric), and per period and segment `row_count`, `volume_change` and `weight_change` (when weighted), each classified with `limits`, checked with `trend`, and replayed with `persistence` into alerts.

## Out of Scope

- Discrimination or calibration metrics (they belong to model monitoring).
- Cross-version comparison (results compare within one binning version).

## Impact

- `src/bricksmith/monitor/stability/{__init__,config,profile,spark,metrics,engine,tables}.py` — new.
- `tests/unit/monitor/stability/` — new.

## Validation

- Hand-derived fixtures: PSI of a period equals `stats.psi` over its bins against the baseline aggregate; weighted PSI uses weight shares; `mean_shift = (mean_c - mean_b) / std_b` from per-bin moments; `volume_change = rows / (baseline rows per period) - 1`.
- Baselines: `fixed` aggregates the range; `previous` is `no_baseline` for the first period; `rolling` uses only prior periods; a segment absent from the baseline is `no_baseline`.
- Periods with fewer than `min_rows` rows are `insufficient_volume` for distribution metrics; volume metrics still classify.
- Results and profiles are deterministic and identical between the pure and the Spark engines (remote test).

## Design

- Period values are compared as text (`str(value)`; dates as ISO). `period_date` is derived when the text starts with `YYYY-MM-DD` or `YYYY-MM` (first day).
- Segments: `segments` lists columns or column lists; each entry yields a segment set (cross product inside a list); the overall population is always computed with segment `""`. Segment keys are canonical text `col=value` joined by `,` (`(null)` for null); `max_segments` (default 50) keeps the most frequent values per set and records the truncation.
- Profile row key: `(dataset, version, period, segment, column, bin)`; carries `bin_order` and a readable `bin_label` (`[a, b]`, `(a, b]`, `< a`, `> b`, `0`, `null`, category text, `(other)`).
- Baseline aggregate per segment and column = sum of profile counts over baseline periods; `baseline_rows` per period = mean rows over those periods.
- Default limits: `psi` higher 0.10/0.25; `null_rate_delta` higher 0.05/0.15; `unseen_rate_delta` higher 0.05/0.15; `mean_shift` both 0.25/0.50; `volume_change` both 0.20/0.50; `weight_change` both 0.20/0.50; `row_count` and raw rates have no rule. Overrides per metric, and per column through `column_limits`.
- Trend applies to `psi` and `volume_change` by default, on the series of earlier usable values of the same key.
- Alerts are replayed for each `(segment, column, metric)` series over every stored period of the version: persistence alerts from the main status, trend alerts from the trend status (red opens, `close_after` greens close). `alert_id` is a hash of dataset, version, key, kind and opening period, so replays are stable.
- Caps: `max_periods` (default 36) most recent periods are kept in the computation window.

## Alternatives Considered

- Store only PSI per period. Rejected: no bin explanation, no baseline change without reprocessing.
- One wide row per period with a map of columns (the reviewed prototype). Rejected: long rows are what BI tools and SQL filters consume directly.

## Discoveries

- Segment columns are excluded from column metrics by design (they are the split, not the subject); their shift shows as segment volume_change.
- flagged_periods counts the non-green periods from the alert's opening on, not the run that led to it.
