## Problem

Found by the epic-161 correctness review (2026-11-25), reproduced:

- `tests/unit/monitor/stability/test_stability_spark_parity.py:21` sets `TOLERANCE = 0.12` for the approximate metrics. `:99` asserts `high - low <= TOLERANCE * max(1.0, abs(high))`. For a rate in [0, 1] that is a 0.12 absolute gap, six times the default red limit of `DUPLICATE_KEY_RATE` (`src/bricksmith/monitor/stability/config.py:109`, green 0.01, red 0.02).
- `:100` `continue` skips the `status` and reason assertions (`:101-102`) for those metrics, so the light is never compared.
- Spark computes keys as `min(approx_count_distinct(keys), rows)` (`src/bricksmith/monitor/stability/spark.py:306,313`), while the pure engine counts exactly. A table of 120 unique keys estimated at 118 gives a rate of 0.0167 (yellow) on Spark and 0 (green) on pure. The test still passes, and a Spark user gets a duplicate-key alert on clean data.

Consequence: a user-visible engine divergence in an alerting metric is invisible to the gate. Options: exact `count(distinct)` for the key count on Spark (or `approx_count_distinct` with a tighter rsd), and a parity test that compares status with a tolerance tied to the metric's limits. Whether HLL++ undercounts at this size was not confirmed: the reviewer host had no Java.

## Proposal

- Count the keys exactly on Spark (`countDistinct` instead of `approx_count_distinct`), so `duplicate_key_rate` equals the pure engine, and make the parity test compare `status` and `reason` for every metric, bounding only the remaining approximate metrics by limits-derived tolerances.

## Out of Scope

- Making `distinct_count` and `distinct_change` exact: they stay `approx_count_distinct` (cost on wide columns); the parity test bounds them instead.
- Changing any default limit.

## Impact

### Product code this spec expects to touch

- `src/bricksmith/monitor/stability/spark.py` — exact key count in `_scan_spark`
- `tests/unit/monitor/stability/test_stability_spark_parity.py` — compare status for all metrics, derived bounds

## Validation

- `python scripts/local_spark_check.py tests/unit/monitor/stability/test_stability_spark_parity.py` passes with 4 passed and 0 skipped, on a local pyspark.
- `uv run pytest tests/unit/monitor -q`, `uv run ruff check`, `uv run ruff format --check` and `uv run pyright` are clean.

## Design

- Measured at baseline (local Spark 4.0.1): in the drifted month Spark's `duplicate_key_rate` is 0.0417 against 0.0917 exact, a 0.05 gap, 2.5x the red limit (0.02); the old test passed because of `TOLERANCE = 0.12` and a `continue` that skipped the status assertions. No flat tolerance derived from the limits can absorb that gap, so the key count becomes exact and the rate is compared exactly.
- Remaining approximate metrics: `distinct_change` is bounded by its green limit (`SHAPE_LIMITS`, 0.20), so a gap never moves a value across a limit unnoticed; `distinct_count` has no limits and keeps a relative bound of three times the 5% relative standard deviation. Status and reason are asserted for every metric.

## Alternatives Considered

- Keep `approx_count_distinct` with a tighter `rsd`: rejected; it still estimates, and a clean table could still read yellow.
- Test-only change: rejected; the bound would have to be about 0.05, above the red limit, which the epic forbids.

## Open Decisions

- none — the epic decision fixes the gate and the test change; the measured gap settles the exact count.

## Risks

- `countDistinct` is costlier than HLL on very high-cardinality keys; ACCEPTED, the key count is one aggregate per period and correctness of an alerting metric outweighs it.

## Handoff

- Java is required locally for the proof: a JRE 21 on `PATH`/`JAVA_HOME`.
