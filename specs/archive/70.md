## Problem

Model monitoring (BS-13) still decides with single-threshold rules, while data stability gets traffic lights, trend checks and persistence alerts from the shared core. Model metrics need the same decision layer plus limit families common in model governance: relative deterioration against development (for example KS falling more than 15% is a warning, more than 30% critical), control-chart limits from a baseline mean and standard deviation of monthly point values (z beyond 2/3 or 2.5/3.5), and calibration ratio bands (observed/expected within 0.7–1.3 green, 0.5–1.5 yellow).

## Proposal

- Let a `Reference` alert policy declare `Limits` per metric (with the new limit kinds `relative` and `control` computing the compared value from a baseline) and classify BS-13 measurements into lights, trend and persistence alerts with the shared core.
- Persist the classified results in the BS-13 tables with additive columns, or a dedicated results table mirroring `stability_results`.
- Compute control-chart baselines from monthly values over the development plus out-of-time window, not the development window alone, which underestimates variance.

## Out of Scope

- The legacy `AlertRule` threshold policy of `bricksmith.monitor.fit` / `monitor evaluate` (the project-free `Reference` pipeline): it keeps its single-threshold rules. Since spec 81 the `model_monitoring` declaration is the model decision surface; the legacy pipeline is not extended twice.
- Data stability adopting the `relative` and `control` limit kinds: stability has its own baselines (fixed, previous, rolling); its parser refuses the new kinds with a clear message. A later spec may open them.
- Human alert actions, risk acceptance and governance views (spec 71), the maturation lag between monitoring and data periods beyond the existing `label_lag` (spec 72), limit selectors and specificity (spec 73), per-grade calibration tests (spec 82).
- A dedicated results table mirroring `stability_results`: rejected in `## Design` in favour of additive columns.
- Performance estimation before labels mature (epic 85 design: out of scope this epic).

## Design

- 2026-11-23 — **Decision surface.** The `model_monitoring` declaration's `limits` is the alert policy of the model binning `Reference` since spec 81 (merged after this spec was captured). This spec extends that declaration; the Proposal's "`Reference` alert policy" is read as it. Evidence: `src/bricksmith/monitor/model/config.py` builds the binning `Reference` and carries `limits: dict[str, Limits | None]`.
- 2026-11-23 — **Limit kinds live in the shared core.** `Limits` gains `kind` (`absolute` default, `relative`, `control`) and `reference` (the named baseline of a `relative` limit). `compared_value(limits, value, *, baseline, spread)` returns the number the bands judge: the value itself (`absolute`), `(value - baseline) / |baseline|` (`relative`; `None` when the baseline is missing or zero), `(value - mean) / sd` (`control`; `0` or `±inf` when `sd` is zero, as the trend check does). A `None` compared value with a value present classifies as `no_baseline`. `to_dict` omits `kind` and `reference` at their defaults, so stored stability fingerprints do not change.
- 2026-11-23 — **Relative limits.** `reference` is `development` (default) or `out_of_time`; the baseline is the metric measured on that reference sample (the `development_value` / `out_of_time_value` already stored per result). Direction keeps its meaning on the relative change: KS falling more than 15% yellow, 30% red is `{"kind": "relative", "green": -0.15, "red": -0.30, "direction": "lower"}`.
- 2026-11-23 — **Control-chart baselines** are the mean and sample standard deviation (n-1) of the metric measured per observed period over the development **plus** out-of-time reference rows, never development alone, which underestimates variance (Proposal). Computed only for metrics whose limits are `control`, at least `control_min_points` (default 3) finite period values or `no_baseline`. Stored per result as `baseline_mean`, `baseline_sd`, `baseline_points`.
- 2026-11-23 — **Calibration ratio band default.** `calibration_ratio` defaults to `Limits(0.3, 0.5, both, center=1.0)` (green 0.7–1.3, yellow 0.5–1.5, red beyond), the band named in the Problem; overridable or `null`.
- 2026-11-23 — **Trend and persistence reuse the shared core unchanged.** Model monitoring recomputes its whole monitoring window each run, so trend history and persistence series come from the same run's results per `(segment, column, metric)` (ordered by monitoring period), judged on the compared value with the limit direction. `trend` (`TrendPolicy`, default on) applies to `trend_metrics` (default `psi`, `ks`, `auc`, `calibration_ratio`); `persistence` (`PersistencePolicy`) replays the light series. Trend alerts use the stability rule (one red trend opens critical).
- 2026-11-23 — **Additive columns, not a new table.** Results gain `limit_kind`, `limit_reference`, `compared_value`, `baseline_mean`, `baseline_sd`, `baseline_points`, `trend_status`, `trend_expected`, `trend_deviation`. Alerts gain `kind` (`light`, `persistence`, `trend`), `state`, `opened_period`, `escalated_period`, `closed_period`, `last_period`, `flagged_periods`, `recurrence`; light alerts keep their identity and get `kind = light`, `state = open`. Persistence and trend alert ids hash model, version, segment, column, metric, kind and opened period; their `monitoring_period` is the span's last period so the trusted views keep working. Tables created by spec 81 gain the columns through the write option `evolution: {}` (compatible additions only; `docs/how-to/schema-evolution.md`).
- 2026-11-23 — **Gate.** `fail_on` also takes `critical` (an open critical persistence or trend alert) and `alert` (any open one), as in data stability; the outcome and run record carry `open_alerts` and `critical_alerts`.
- Binding contracts: AGENTS.md (English, lightweight imports — no new import at the root, Spark only lazily), decision 0010 (synthetic tests, generic vocabulary), decision 0012 (run-keyed tables, run record last, finished-run views), epic 85 design (bricksmith stores its own monitoring tables).

### Assumptions

- Default `trend_metrics` (`psi`, `ks`, `auc`, `calibration_ratio`) — lands in `## Design`; a metric with no direction (no rule) gets no trend either way.
- `control_min_points` default 3 — the smallest sample with a meaningful sample standard deviation beyond two points; lands in `## Design`.

## Alternatives Considered

- **A dedicated model results table mirroring `stability_results`.** Lost: a second table doubles the trusted views and the replay, and every new field is a nullable addition to the existing run-keyed results.
- **Compute relative and control values inside model monitoring only.** Lost: the Problem asks for the shared decision layer; keeping the kinds in `monitor.limits` lets stability or the legacy pipeline adopt them later without a second implementation.
- **Control baselines from the development window alone.** Lost: the Proposal names it as underestimating variance.
- **Persist trend and persistence history across runs (incremental, as stability does).** Lost: model monitoring already recomputes its whole window (`max_periods`) every run, so the series is complete within one run and replay stays pure.

## Open Decisions

- none — every shape question is answered by the Proposal, the spec 81 code or the stability precedent; defaults are recorded under `### Assumptions`.

## Risks

- Existing model monitoring tables (spec 81) lack the new columns → the merge would fail. Mitigation: `evolution: {}` in the write options and a remote test over a table created with the old schema.
- The new default `calibration_ratio` band turns a `no_rule` into colors and may fail a `fail_on: red` gate after upgrade. ACCEPTED — the band is the governance default the Problem names; it is documented and `null` restores `no_rule`.
- Control baselines over few reference periods give unstable limits. Mitigation: `control_min_points` floor and `baseline_points` stored on every row.
- Measuring each control metric per reference period multiplies reference passes. Mitigation: only metrics with `control` limits are measured per period; documented.
- Stability fingerprints drifting because `Limits.to_dict` changed. Mitigation: defaults omitted; a unit test pins an existing stability judgment fingerprint.
