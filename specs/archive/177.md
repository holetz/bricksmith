## Problem

Regression from #174 (PR #122), reproduced by the round-4 reviewer on 2026-11-26 (main ac0a964 vs base ad054ad):

```
'postgresql://app:Pa@ss!@%2Fvar%2Frun%2Fpostgresql/app'
  new : postgresql://app:<redacted>@ss!@%2Fvar%2Frun%2Fpostgresql/app
  base: postgresql://app:<redacted>@%2Fvar%2Frun%2Fpostgresql/app
'postgresql://admin:Adm1n@2024!@%2Fcloudsql%2Fproj%3Aregion%3Ainst/db'
  new : postgresql://admin:<redacted>@2024!@%2Fcloudsql%2Fproj%3Aregion%3Ainst/db
'postgres://u:p@ss!w@[fe80::1%25eth0]:5432/db'
  new : postgres://u:<redacted>@ss!w@[fe80::1%25eth0]:5432/db
'sftp://deploy:p@ss!@files.example.com:/srv/data'
  new : sftp://deploy:<redacted>@ss!@files.example.com:/srv/data
```

`src/bricksmith/ops/redact.py:270` walks back from the last `@` and stops at the first one whose suffix matches `_HOST_AFTER_AT` (`:62`); percent-encoded socket hosts, IPv6 zone ids and `host:/path` do not match, so an `@` inside the password is chosen. Consequence: realistic Postgres socket / Cloud SQL connection strings leak password tails. Any host-shape guess can be wrong; fail closed instead.

## Proposal

- In a `scheme://user:` URL token, the userinfo separator is the rightmost `@` of the token (up to whitespace or the next `://`), with no host-shape test.
- Remove `_HOST_AFTER_AT` and the reverse walk.

## Out of Scope

- URLs without `user:` credentials, including the `host:port` branch (`https://host:8080/api?e=a@b.com`): unchanged.

## Design

- Rule: `_credential_separator` returns the rightmost `@` of the token; the `host:port` guard (a leading `digits` then `/ ? # end` with only path handles or address tails) is kept so credential-less port URLs stay unchanged.
- Decision (epic 178 `## Design`): fail closed; over-masking a credentialed URL's path or query is accepted.

## Alternatives Considered

- Widen `_HOST_AFTER_AT` to socket, zone and `host:/path` shapes: rejected, any host-shape guess can be wrong.
