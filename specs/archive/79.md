## Problem

A model's data stages (population, ABT for training and for scoring, label/performance, prediction) must behave the same in development and production. Common failures: out-of-time windows that overlap the training window, excluded rows silently dropped (so exclusion composition cannot be monitored), training reading frozen snapshots while scoring reads live sources through per-task branching, and labels computed without declaring their forward window and maturity. `bricksmith.mlops` has `Sample`/`Split`/`Rule` (`mlops/spec.py:134-179`) and builders, but no window validation, no exclusion cascade and no feature-store spine.

## Proposal

- Named samples with closing windows and roles (train, test, out-of-time, through-the-door, prediction, monitoring); validation refuses an out-of-time window overlapping the training window, and labels whose forward window has not matured at the sample's upper closing.
- An exclusion cascade: ordered rules evaluated per row; every row keeps all rules it meets, the first rule it meets, and an excluded flag; excluded rows are kept in the population and filtered only when building the training ABT. The cascade is reusable by monitoring to recompute exclusion composition on scored populations.
- The population is the spine of the feature store training-set builder (spec FS); the ABT for training = spine (not excluded) + features + label; the ABT for scoring = spine + the same lookups; one code path, the sample type only selects closings. Optional stratified sampling by label with a deterministic hash.
- Labels declared with forward window (periods) and definition; maturity checked against the closing.
- Prediction output contract: entity keys, closing, model name/version/alias, score, grade/band, and the sample role, so monitoring can read it directly.

## Out of Scope

- Model-specific segment logic beyond declared slices.

## Design

- 2026-11-23 — **Binding context.** Epic 85 `## Design` (private-source rule, feature-store design of 76, monitoring decisions) governs; this spec only adds what it leaves open. Synthetic data and generic vocabulary only.
- **Declaration.** A plain mapping (inline, TOML or JSON) parsed by `parse_development` into `Development`: `model`, `entity_keys`, `closing` (default `closing_date`), `frequency` (feature-store frequencies), `samples` (mapping name → `{role, start, end}`; closings inclusive, each a closing of the frequency, `start <= end`), `label` (`{name, horizon, definition, type}`; `horizon` = forward window in periods), `as_of` (the latest closing whose performance is observed), `exclusions` (ordered list of `{name, where}` with the existing predicate grammar), `stratify` (`{seed, fractions: {label value: fraction}}`, optional), `bands` (ordered `[{name, upper}]`, optional), `lookups` (feature-store lookups, optional). Standard library only.
- **Roles.** `train`, `test`, `out_of_time`, `through_the_door`, `prediction`, `monitoring`. Labelled roles: `train`, `test`, `out_of_time`. Validation refuses: an `out_of_time` window that overlaps or precedes the end of any `train` window (OOT starts strictly after the last train closing); a labelled sample whose upper closing plus `horizon` periods is after `as_of` (label immature); `as_of` missing when a labelled sample exists. `train` and `test` may share closings (test is then drawn by stratified hash, see below) — overlap is refused only for `out_of_time`.
- **Exclusion cascade.** Rules evaluated in order on each population row; output columns `exclusion_rules` (array<string>, every rule met, in cascade order, empty when none), `exclusion_first` (string or null), `excluded` (boolean). Excluded rows stay in the population; the training ABT filters `excluded = false`; the scoring ABT keeps every row with its flags so the prediction table carries them and monitoring can recompute exclusion composition. `composition(rows)` returns per closing: total, excluded, count per first rule and count per rule met (dashboard-ready rows).
- **Spine and ABT.** Population rows (entity keys + closing + cascade flags + extra columns) are the feature-store spine. `build_abt(development, population, sample, purpose, ...)` selects the sample's closings, applies (training only) the exclusion filter, optional stratification and the label join, then calls the feature store's `build_training_set` with the same lookups for both purposes. Training ABT = spine (not excluded) + features + label; scoring ABT = spine + the same lookups. One code path; the sample only selects closings; a `sample` column carries the sample name and a `sample_role` column its role.
- **Labels.** Label rows are keyed by entity keys + observation closing and carry the label value computed over the declared forward window; joined by exact closing. For labelled samples a row with no label is refused (training) — never silently dropped — reported with counts. Maturity per row: `shift(closing, horizon) <= as_of`.
- **Stratified sampling.** Deterministic: keep a row when `sample_fraction(seed, key_text(entity keys + closing))` is below the fraction declared for its label value (labels absent from `fractions` keep fraction 1). Same hash as the existing `reference.sample_fraction` / `spark.sample_column` (sha256 first 32 bits), so the Spark engine is a built-in expression.
- **Prediction contract.** Columns: entity keys, closing, `model_name`, `model_version`, `model_alias` (nullable), `score` (double), `grade` (from declared `bands` when given, else supplied or null), `sample`, `sample_role`, plus the cascade flags. `prediction_rows(...)` / Spark `prediction_frame(...)` build it from the scoring ABT and scores; `check_prediction` refuses missing columns, a null score or key, and a duplicated (entity, closing, model_version). The `sample` column is what a `model_monitoring` declaration's `sample` and `references` read.
- **Engines.** Row engine is the oracle; Spark engine uses only built-in functions (Free Edition refuses Python UDFs, see epic 85) and is proved equal remotely on `free`.

### Assumptions

- `as_of` is declared explicitly rather than derived from the label table; derivation would read data at parse time — affects `## Design` validation rules.
- Scoring keeps excluded rows (flagged) so monitoring sees exclusion composition; a project that scores only eligible rows filters `excluded` itself — affects the prediction contract.

### Mapa de dependências

- 2026-11-23 — New package `bricksmith.mlops.stages` depends on `bricksmith.mlops.featurestore` (config calendar, `Lookup`, `rows.build_training_set`, `spark.build_training_set`), `bricksmith.mlops.spec.check_predicate`, `bricksmith.mlops.reference` (`matches`, `sample_fraction`, `key_text`), `bricksmith.mlops.spark.predicate_column`, `bricksmith.mlops.errors`. ## Alternatives Considered

- **Extend `ModelSpec` (BS-11) in place.** Rejected: it is keyed by snapshot dates and days-based maturity, drops excluded rows into a separate list and has its own feature join; folding closings and the cascade in would change a public contract other tasks use. A new package on the feature-store spine leaves BS-11 intact; consolidation is a follow-up.
- **Drop excluded rows at population time.** Rejected by the Problem: composition could not be monitored.
- **Random (non-hash) sampling.** Rejected: not reproducible across engines and reruns.
- **Python UDF for the cascade in Spark.** Rejected: Free Edition refuses Python UDFs; built-in `array`/`filter`/`coalesce` suffice.
