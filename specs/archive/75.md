## Problem

Regulatory reliability asks a different question from drift: did the same period change between revisions of the same table? Re-published history (late loads, corrections) silently changes reported numbers.

## Proposal

- A revision check comparing a period's profile at the current table version with the profile stored at its first publication (Delta version or the stored profile of an earlier run), reporting changed rows, PSI between revisions and value deltas.
- Results in the same tables with metric names `revision_*`, gated like stability.

## Out of Scope

- Reading the Delta table history (`VERSION AS OF`, time travel) of the monitored table: the first publication is the profile stored by an earlier run, which works on every engine and in memory.
- Revision of the rows themselves (which keys changed): only the period's profile (bins, rows, means) is compared; row-level diffs need keys the framework does not know.
- Notifications for revision alerts beyond what the existing `notify` policy already delivers for any stability alert.
- Reconstructing the profile at publication for periods stored before revision tracking was enabled: the first observed profile becomes the reference.

## Validation

- `uv run pytest tests/unit/monitor/stability -q` passes, including the new `test_stability_revision.py`.
- A period re-published with changed rows yields `revision_row_change`, `revision_psi` and `revision_mean_shift` results with a non-green status; an unchanged period yields green zeros; an unrevised table without `revision` produces no `revision_*` row and no `revisions` table.
- `uv run ruff check && uv run ruff format --check && uv run pyright` pass; the full gate runs in conclude.

## Design

- Declaration: `revision: true` (or `false`). Off by default, so existing declarations, tables, fingerprints and tests are unchanged; `to_dict` and the judgment fingerprint carry `revision` only when set.
- Storage: one optional table `<prefix>revisions` (same keys as profiles: dataset, version, period, segment, column, bin; same count, weight and moment columns plus `published_at`). It is written only for periods absent from it, so the first observed profile is never overwritten. When revision is first enabled, periods already holding stored profiles are snapshotted from those stored rows; periods profiled for the first time snapshot their fresh rows.
- Compare: for each window period that already had a snapshot before this run, the current profile (stored or refreshed) is compared with the snapshot per segment: `revision_row_change` (rows now / rows at publication - 1, table level, column empty), `revision_psi` per column (shares over the same fitted bins, floored at `epsilon`, weights when declared) and `revision_mean_shift` per numeric column ((mean - first mean) / first std). Results land in the existing results table with `baseline_kind = revision` and `baseline_label = first publication`, judged by `limits`, `column_limits`, rules, `min_rows` and persistence like any metric, so alerts and the gate apply unchanged.
- Default limits (applied only when `revision` is on, override through `limits`): `revision_row_change` 0.01 / 0.05 both directions, `revision_psi` 0.05 / 0.10 higher, `revision_mean_shift` 0.10 / 0.25 both directions: a period of history that changed at all is already notable.
- A revision is only visible while the period is re-profiled: `refresh_periods` must cover the span in which history can be republished; the guide says so.
- Binding contracts: root import stays light; pure engine (no Spark import in `revision.py`); English only; synthetic tests (decision 0010).

### Assumptions

- First publication means first observation by the monitor, not the table's own Delta version (Out of Scope; Design).

## Alternatives Considered

- Read the table at an earlier Delta version: rejected, it ties the check to Delta and to retention of old versions, and needs a second scan of the table per period.
- Store a second profile column set in the profiles table: rejected, changing its key breaks stored Delta merges; a separate append-once table is additive.

## Open Decisions

- none — the shape is decided; Delta time travel is out of scope.

## Risks

- A late revision of a period older than `refresh_periods` is not re-profiled and goes unseen: documented, with `refresh_periods` as the control; ACCEPTED because widening the default would re-scan more history on every run.
- Reduced signal when a binning is refit: snapshots belong to one binning version, so a new version compares from its own first observation. ACCEPTED, consistent with how profiles are versioned.

## Discoveries

- decision: first publication is the stored profile of the earlier run, not Delta time travel — works on every engine and in memory; recorded in Design/Out of Scope
- decision: no remote proof — behavior is pure in-memory engine logic; Spark path reuses existing profile/table writers (Free-first, no workspace execution needed)
- decision: repo has no scripts/verify_repo.sh; the gate was ruff check, ruff format --check, pyright and pytest from AGENTS.md, exit 0, plus scripts/leak_check.py --push exit 0
## Outcome

Shipped `stability.revision: true`: each period is compared with its first publication, the profile the monitor stored the first time it saw the period. Results `revision_row_change`, `revision_psi` and `revision_mean_shift` join `stability_results` (`baseline_kind = revision`, `baseline_label = first publication`), judged by limits, rules, `min_rows`, persistence alerts and the gate. The first publication lives in the optional `stability_revisions` table, written once per period and never rewritten; periods with stored profiles when revision is switched on are snapshotted from those rows. Pure engine in `monitor/stability/revision.py`; the engine, hook and `bricksmith stability check` write and read the table only when declared, so existing declarations, tables and fingerprints are unchanged. Documented in `docs/how-to/stability.md`.

Left out: Delta time travel as the source of the first publication, row-level (key) diffs, reconstructing a profile that predates tracking. A revision of a period older than `refresh_periods` goes unseen; the guide says so. No remote proof: the behavior is pure in-memory engine logic and the Spark path only reuses the existing profile and table writers with the new schema.
