## Problem

Found by the correctness review of epic 109 (autopilot 2026-11-24 round 2), reproduced on main 73c8775 with the data of `test_a_lagged_period_scored_by_two_versions_is_stamped_with_both` (`predictions()` with 2025-07 rows alternating versions "1" and "2", `label_lag=1`):

```
run model_version: '1,1,2,2'
['1', '1,2', '2']
```

Spec 108 added `out.versions.update(measured.split(","))` for lagged rows (`src/bricksmith/monitor/model/engine.py:1041`), but the monitoring-period version is still added unsplit by `out.versions.add(version)` (`engine.py:1063`), so the set holds `{"1","2","1,2"}` and the join at `engine.py:1119` yields `1,1,2,2`.

Consequence: the run record's `model_version` contradicts `docs/how-to/model-monitoring.md` ("The run's `model_version` lists every version its results carry") and repeats versions, misleading governance reads and any filter on the run's versions.

Proposal: split the monitoring version too (or normalize the set to atomic versions before the join); add a test asserting `model_version == "1,2"` for the case above.

## Proposal

- The run record's `model_version` lists each model version exactly once, sorted, when a monitoring period is scored by several versions (`1,2`, never `1,1,2,2`).
- A test pins `model_version == "1,2"` for the mixed lagged period of `test_a_lagged_period_scored_by_two_versions_is_stamped_with_both`.

## Out of Scope

- Per-result `model_version` stamping: already correct and documented.
- Changing the version separator or the sort order: the documented `1,2` shape stays.

## Impact

### Product code this spec expects to touch

- `src/bricksmith/monitor/model/engine.py` — split the monitoring-period version before adding it to the run's set
- `tests/unit/monitor/model/test_model_engine.py` — assert the run's `model_version`

## Validation

- `uv run pytest tests/unit/monitor/model/test_model_engine.py` passes; the new assertion fails on main (`'1,1,2,2'`) and passes after the fix.
- `uv run ruff check` and `uv run pyright` stay clean.

## Design

- Decision: split `version` on `","` at the single point where the monitoring period's version enters `out.versions` (`_measure_window`), mirroring the lagged branch that already splits. Durable rule: the run's version set holds atomic versions only. Alternative: normalize inside the join at the outcome; rejected because the set would still carry composite members and any other reader of it would repeat the bug.
- Binding contracts: `docs/how-to/model-monitoring.md` ("the run's `model_version` lists every version its results carry") is already the documented behavior; no doc change needed. Free-first: pure unit test, no remote proof.

## Alternatives Considered

- Deduplicating at the join (`sorted(set(...))` over split parts): rejected, same reason as above, it hides the composite member instead of removing it.

## Open Decisions

- none — the fix and the test are fully determined by the reproduced output.

## Risks

- A version string containing a comma would now be split: ACCEPTED — the lagged branch already splits on the comma, and `_version` itself joins versions with it, so a comma is already the separator.
