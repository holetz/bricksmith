## Problem

Alerts replayed from status history open and close automatically, but teams also need to record what they did: an alert under analysis, closed with a reason, or a risk accepted until a date. Without that, the same alert is re-discussed every run and governance cannot measure response times.

## Proposal

- An append-only `stability_alert_actions` table written by people (or a CLI verb) with `alert_id`, action (`analysis`, `closed`, `risk_accepted`), reason, author, valid-until.
- Replays apply the latest action to the alert state; a risk acceptance suppresses gating until it expires.
- Governance views: monitoring coverage and timeliness, mean time to resolve, active and expired acceptances.

## Out of Scope

- Data stability alert actions: the stability alert tables keep their automatic lifecycle; the shared action rules (`monitor/model/actions.py` is model-specific) may be lifted into the shared core by a later spec.
- A web or notebook UI to register actions: people write through a CLI verb that emits the row and an `INSERT` statement, or through any SQL client.
- Notifications (spec 74 is loose) and approval chains (two-person rules).
- Maturation lag and limit selectors (specs 72 and 73); the monitoring report document (spec 83), which will consume the views added here.
- Editing or deleting an action: the table is append-only; a later action supersedes an earlier one.

## Validation

- `uv run pytest tests/unit/monitor/model -q` passes, including new tests that assert:
  - an action row needs a known action (`analysis`, `closed`, `risk_accepted`), a non-empty reason and author; `risk_accepted` requires a `valid_until` ISO date and the other actions refuse one; ids are deterministic.
  - `apply_actions` takes the latest action per alert (by `created_at`): `closed` sets state `closed`; `analysis` keeps it `open` with the action recorded; `risk_accepted` sets `accepted` through its `valid_until` date inclusive and returns the alert to its automatic state the next day with the action still shown.
  - a later `analysis` supersedes an earlier acceptance; an action for another model or an unknown alert id changes nothing.
  - an open critical persistence alert with an active acceptance does not fail `fail_on: ["critical"]`, and neither does a red light with an accepted light alert under `fail_on: ["red"]`; once the acceptance expires the same stored data fails the gate again.
  - `replay_alerts` with actions and `--as-of` rebuilds the same states from stored rows; the `act` verb prints a valid row and an `INSERT` statement for the declared actions table.
  - the governance view statements reference the trusted alerts and the actions table (coverage, timeliness, response times, acceptances).
- `uv run pytest tests/remote/test_model_monitoring.py -q` on the free profile: a declared task creates the actions table, an inserted acceptance suppresses the gate on the next run, and the governance views return rows.

## Design

- 2026-11-23 — **Scope: model monitoring.** The epic places this spec after 70 (model monitoring shared limits); alerts that exist as run-keyed rows with span states are the model monitoring ones, so the action workflow lands there. Evidence: epic 85 task S7, `monitor/model/alerts.py`.
- 2026-11-23 — **A sixth table, `actions`, append-only, written by people.** Columns: `action_id`, `model`, `alert_id`, `action`, `reason`, `author`, `valid_until` (DATE), `created_at`. `action_id` hashes model, alert, action, author and creation time, so replaying the same insert is idempotent. The run never writes rows to it (it only creates it empty so the table exists); it is not run-keyed because an action outlives the run that raised the alert. Alert ids are stable across runs for the same series and opened period, which is what lets an action attach.
- 2026-11-23 — **Fold rule.** The latest action per alert (max `created_at`, then `action_id`) decides, at an evaluation date (`started` date in a run, `--as-of` or the replay date otherwise): `closed` → state `closed`; `risk_accepted` with `valid_until >= date` → state `accepted`, past it → the automatic state, the action columns still shown so governance can list expired acceptances; `analysis` → state unchanged (`open`) with the action recorded. State values stay a closed set: `open`, `closed`, `accepted`.
- 2026-11-23 — **Alert columns.** Alerts gain `action`, `action_reason`, `action_author`, `action_at`, `valid_until`; empty without an action. The `open_alerts` view keeps filtering `state = 'open'`, so accepted and closed alerts leave it.
- 2026-11-23 — **Gating.** Persistence and trend spans count in `open_alerts` and `critical_alerts` only while `open`, so closed and accepted spans stop failing `fail_on: critical|alert`. A red or yellow light is counted per result, so a light alert with an active acceptance is excluded from the `red`/`yellow` counts of the latest period; a human `closed` on a light alert is bookkeeping only and does not hide the result from the gate. The run message names the number of accepted alerts.
- 2026-11-23 — **Writing an action.** `model-monitoring act` builds the validated row, prints it as JSON and, with `--scope`/`--prefix`, the `INSERT INTO <prefix>actions` statement a person runs in any SQL client; with `--state` it appends to the state file's `actions` list for pure replay. No Spark in the CLI.
- 2026-11-23 — **Governance views** (SQL from `view_statements`, over trusted rows): `<prefix>actions_latest` (the latest action per alert), `<prefix>acceptances` (every acceptance with `status` active or expired by `current_date()` and days left), `<prefix>coverage` (per model and version: periods measured, first and latest period, last finished run, days since it ran — the timeliness), `<prefix>alert_response` (per alert: first seen = earliest alert row, first action time and resolution time, in days) and `<prefix>response_summary` (per model: alerts, acted, resolved, mean days to first action and to resolve).
- Binding contracts: AGENTS.md (English, lightweight imports, no generated YAML), decision 0010 (synthetic tests, generic vocabulary), decision 0012 (run-keyed tables, run record last), decision 0016 (alert spans), decision numbered at commit time.

### Assumptions

- Evaluation date for runs is the date of `started` (UTC) — lands in `## Design`; `valid_until` is inclusive.
- Time units in the response views are whole days (`datediff`) — a finer unit would not help governance reporting.

## Alternatives Considered

- **Mutable alert state in the alerts table.** Lost: alerts are rebuilt each run, and an in-place edit would be overwritten and unauditable.
- **A single `status` field edited on the actions table.** Lost: history (who analysed, who accepted, when) is the governance value; append-only keeps it.
- **A shared-core action module for stability too.** Deferred: stability alerts persist differently (incremental); the fold rule can be lifted later without changing this surface.

## Open Decisions

- none — the Proposal fixes the action vocabulary and suppression semantics; the rest is recorded in `## Design` and `### Assumptions`.

## Risks

- Adding `actions` to the declared targets changes the plan of every model monitoring task. Mitigation: it is created empty with `on_empty: allow_empty` and existing tests are updated; the guide notes the new table.
- An acceptance hides a real problem. Mitigation: `valid_until` is required, expired acceptances are listed in a view, and the run message counts accepted alerts.
- People insert actions for a wrong alert id. Mitigation: unknown ids change nothing and the `act` verb prints the id it targets; ACCEPTED otherwise (no join check at insert time).
