## Problem

Found by the autopilot 2026-11-24 round 3 map (model scout), reproduced on main 73c8775: `predictions(drifted=('2025-08','2025-09'))` with `persistence={'yellow':4,'red':4}`:

```
run: persistence alerts []  open_alerts 0
report: open_alerts 9, critical 9 (kinds light+persistence)
```

The review report calls `replay_alerts(results, runs, created_at=..., actions=..., as_of=...)` without a config (`src/bricksmith/monitor/model/report.py:206`), so the alerts are replayed with the default `PersistencePolicy` (yellow=3, red=2; `src/bricksmith/monitor/persistence.py:36-37`, `src/bricksmith/monitor/model/alerts.py:122-123`). The report has no way to receive the model's config.

Consequence: the report (`docs/how-to/model-monitoring.md:391-412`) lists open critical alerts the run and its gate never opened, with ids absent from the alerts table, so no analysis, closure or risk acceptance can be recorded against them; a policy stricter than the default hides alerts the run did open. The guide does not mention the difference.

Proposal: let the report take the model's config (Python and CLI) and replay with its persistence policy — or read the stored alerts of the run instead of replaying — so the report's alerts and counts match the run's; add a regression test for the case above.

## Proposal

The model monitoring report shows the alerts and counts of the run that wrote the stored rows. When the stored rows carry the run's `alerts` table, the report reads those alerts (of the model's latest finished run), applies the stored human actions on the evaluation date and counts them, so it never re-derives alerts with a policy the run did not use. When the state has no stored alerts (an older export), the report replays them, with the persistence policy of an optional model config (`build_report(..., config=)`, `report --config`), else the default policy as before.

## Out of Scope

- Changing how a run opens, escalates or closes alerts.
- A new table column or table-contract change.
- Recoloring report lights with a config (the series keep the stored lights).

- `uv run ruff check`, `uv run ruff format --check` and `uv run pyright` stay clean.

## Design

- Decision: owner choice between passing the config and reading the run's stored alerts — both, in order. Stored alerts are the run's own truth (counts equal `runs.open_alerts`/`critical_alerts` by construction), need no declaration file, and work from `--scope`. The config path covers exported states that predate the alerts table or omit it, and mirrors `alerts --config`. Evidence: `engine.py` writes `ALERTS` rows with every run (`tables.py:63`); the report previously read only `results`, `runs`, `actions`.
- Decision: alerts are taken from the model's latest finished run (the run the report header names), because an alert id is keyed by run and the run's counts describe that run. Human actions are applied with `apply_actions` as of the report date, as before.
- Free-first: pure unit tests, no remote proof.

## Alternatives Considered

- Config only: rejected, the default `report` call would stay wrong unless every caller supplies the declaration.
- Stored alerts only: rejected, exported states without an `alerts` list would lose alerts entirely.

## Open Decisions

- none — the epic left the choice to the worker; decided in Design.

## Risks

- An exported state with a stale `alerts` list wins over replay: ACCEPTED, it is the run's own record, documented.
