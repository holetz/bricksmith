## Problem

Monitoring results live in tables; reviewers need a per-model report and governance needs coverage and response measures. Hard-coded period axes and charts without development references make reports misleading.

## Proposal

- A self-contained HTML (and Markdown) monitoring report per model rendered from the monitoring tables: one tab or section per metric family, every series showing the development and out-of-time reference values beside the monitored periods, lights, open alerts and their human status, with period axes derived from data.
- Governance views: coverage and timeliness (share of declared models monitored for the latest closing), open alerts by severity, time to resolve, recurrence, active and expired risk acceptances (fed by spec 71).
- A CLI verb to render the report offline from tables or from exported files.

## Out of Scope

- A hosted dashboard product; views stay SQL for any BI tool.

## Impact

### Product code this spec expects to touch

- `src/bricksmith/monitor/model/report.py` (new) — pure report model from stored rows (`results`, `runs`, `alerts`, `actions`, optional `details`): period axes derived from data, one section per metric family, development and out-of-time reference values beside each series, lights, open alerts with their human status; HTML (self-contained, inline SVG, no scripts or external assets) and Markdown renderers
- `src/bricksmith/monitor/model/tables.py` — governance views over the existing tables: declared-model coverage and timeliness for the latest closing, open alerts by severity, time to resolve, recurrence, acceptance summary; `view_statements` gains an optional `declared` model list
- `src/bricksmith/monitor/model/cli.py` — the `model-monitoring report` verb (offline from an exported state file, or from tables through Spark) and `views --declared`
- `tests/unit/monitor/model/test_model_report.py` (new), `tests/unit/monitor/model/test_model_tables.py`, `tests/unit/monitor/model/test_model_cli.py`
- `tests/remote/test_model_report.py` (new) — the report and governance views on the free context
- `docs/how-to/model-monitoring.md`, `docs/decisions/0023-model-monitoring-report-and-governance-views.md` (new), `docs/decisions/index.md`, `docs/project/evidence/model-report-free.md` (new), `docs/project/evidence/index.md`

Builds on specs 71 (alert actions and acceptances) and 82 (credit families, whose per-grade series appear in the report). No table schema changes: the report and views read what runs already write.

## Design

- 2026-11-24 — **Report model.** `build_report(state, model)` takes the stored rows (`results`, `runs`, `alerts`, `actions`, `details`), keeps the trusted rows (latest finished run per model, model version and period, the rule of `alerts.trusted`) and returns plain data: header (model, versions, latest period, gate counts), periods (sorted union of `monitoring_period` found in the data, never a fixed list), sections (one per family, in `FAMILIES` order, then unknown families by name), series (`column`, `segment`, `metric`) with one point per period (value, light, reason) and the `development_value` and `out_of_time_value` of the series, and the alerts with their action state. Pure and engine-free.
- **Renderers.** The HTML is one self-contained file: a sticky tab bar built from `<input type=radio>` + CSS (no JavaScript), per-series inline SVG line charts with the development and out-of-time values as horizontal reference lines on the same scale, a table of points beneath each chart, light colour chips with a text label (not colour alone). Markdown carries the same sections as tables with `dev` and `oot` columns. Every data value is escaped.
- **Governance views.** `view_statements(scope, prefix, declared=())`: `declared` is a list of model names fixed when the statements are generated; the declared set is those names plus every model with a run (any status). New views: `<prefix>coverage_latest` (per declared model: monitored for the latest closing — the greatest `monitoring_period` of any model — plus its latest period and days since run), `<prefix>coverage_summary` (declared, monitored, share monitored), `<prefix>open_alerts_by_severity`, `<prefix>alert_recurrence` (alerts per model and metric, recurring count), `<prefix>acceptance_summary` (active, expired, superseded per model). Time to resolve stays in `alert_response`/`response_summary` (spec 71).
- **CLI.** `model-monitoring report --model m (--state exported.json | --scope catalog.schema [--prefix p]) --out dir [--format html|md|both]`; `--scope` reads the tables through the selected context's Spark session. `views` gains `--declared a,b`.

### Assumptions

- "Declared models" means the names given at view-generation time plus models that have a run: no registry table is introduced (Design).
- The latest closing is the greatest monitoring period across models; ISO-like period strings sort lexicographically (Design).
- The report needs no JavaScript; navigation by CSS radio tabs keeps it viewable in any browser and in review panes (Design).

## Alternatives Considered

| Approach | Cost | Buys | Forecloses |
| --- | --- | --- | --- |
| Self-contained HTML with CSS tabs and inline SVG (chosen) | hand-written SVG | offline, no dependencies, safe to share | rich interactivity |
| A plotting library (matplotlib/plotly) | heavy dependency in the import path | polished charts | the light import and offline-by-default report |
| A hosted dashboard | infra, auth | live views | the epic's non-goal; views stay SQL |
| A declared-models registry table | schema, migration | exact denominator | simplicity; `declared` list plus runs is enough now |

## Risks

- A model that never ran is only counted when listed in `declared` — documented.
- Views must run on Spark SQL and on the SQL test engine — kept to portable functions already used by existing views.
- Large series make large HTML — the report prints periods found in the data only; documented.
