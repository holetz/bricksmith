## Problem

Reproduced by the epic 132 correctness review (autopilot 2026-11-24, round 6) on origin/main 159451a, edge of spec 130 (PR #82). Before 130 (393db9e) `category_text` was plain `str`, so a fit on data with both zero signs stored two categories, and `fit_bins` ranks by count then text, so `"-0.0"` can precede `"0.0"`. With a stored fit `BinSpec("x", "categorical", categories=("-0.0", "0.0", "1.5"))`: pure `assign(-0.0)`, `assign(0.0)` → `cat:0.0 cat:0.0` (fallback to `-0.0` only when `0.0` is absent, `src/bricksmith/monitor/bins.py:69`); Spark `bin_expression(spec, "double"|"float")` on [-0.0, 0.0] → `['cat:-0.0', 'cat:-0.0']` (first numerically equal category wins, `src/bricksmith/monitor/spark.py:77`).

Repro: `uv run --isolated --no-project --with pyspark==4.0.1 --with-editable . python` with the snippet above (DOUBLE and FLOAT identical).

Consequence: pure and Spark runs of the same data against such a stored fit put the zeros in different bins (PSI, unseen_rate diverge), contrary to the epic 132 owner rule "-0.0 and 0.0 are one category in both engines"; the stability and model Spark paths both go through `bin_expression`. The parity test stores only one spelling at a time.

Done when: both engines map both zeros to the same bin when a stored fit carries both spellings (one documented rule, e.g. prefer `0.0`), covered in the local-pyspark parity suite for DOUBLE and FLOAT.

## Outcome

Abandoned 2026-11-25 (autopilot round 7, stale — the premise is not reproducible). The pure/Spark divergence exists only for a stored fit holding both "-0.0" and "0.0" (bins.py:69 vs spark.py:73-77), but no fit path ever produced one: the pure fit counts in a Counter keyed by the raw value (fit.py:61-64), where -0.0 and 0.0 are one key (`Counter([-0.0,0.0,0.0])` → `Counter({-0.0: 3})`); the Spark fit groups with groupBy(c).count() (spark.py:109), which merges both zeros (pyspark 4.0.1: `double [(0.0, 3), (1.5, 1)]`); the current fit also merges them via category_text (bins.py:36-37). docs/how-to/monitoring.md:96-98 already covers the real legacy case (one spelling), which works on both engines. Only a hand-authored reference JSON could hold both; supporting that is not a current requirement. Evidence: round-7 scout ses_def3167b8ffeJSJxTB27yHVF2q.
