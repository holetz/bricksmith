## Problem

Found by the autopilot round 2 stability scout (2026-11-24), reproduced on main e564870 with a synthetic MemoryStore run (helpers of `tests/unit/monitor/stability/test_stability_metrics.py`): `max_periods=5`, fixed baseline 2026-01..04, drift 2026-05..06 and again 2027-02..03, default persistence. Alert rows (opened, state, closed, recurrence) after each run:

```
2026-09 ('2026-06','closed','2026-09',False)
2026-10 ('2026-06','superseded','2026-09',False)
2027-03 ('2026-06','superseded','2026-09',False), ('2027-03','open','',False)
```

Causes: `src/bricksmith/monitor/stability/engine.py:297` (`_superseded`) supersedes stored CLOSED rows as well as OPEN ones; `src/bricksmith/monitor/stability/metrics.py:437-439` carries only OPEN rows; `src/bricksmith/monitor/persistence.py:140` computes recurrence only from a close inside the replayed series.

Consequence: a real drift episode that closed normally leaves the "Open and closed alerts" read (`docs/how-to/stability.md:268`) one run after closing, and the 2027-03 re-opening, within `recurrence=12` periods of the 2026-09 close, is reported `opened` instead of `recurred` — wrong notifications (spec 74) and governance history.

Proposal: a stored CLOSED alert is final (never superseded by a window that no longer replays it); recurrence considers the last stored close of the same alert identity; add the sequence above as a regression test (pure engine; keep Spark parity). Lands after spec 104 (same functions).

## Proposal

- A stored `closed` stability alert of the active binning version whose opening period is at or before the window's first period stays `closed` on every later run; it is never rewritten as `superseded` because the window no longer replays it.
- An alert that opens within `recurrence` periods of the last stored close of the same alert key (segment, column, metric, kind, version) is flagged `recurrence = true` even when that close lies before the window, so the notification is `recurred`, not `opened`.
- A regression test reproduces the Problem's sequence (fixed baseline 2026-01..04, drift 2026-05..06 and 2027-02..03, `max_periods=5`) and asserts the 2026-06 alert stays closed and the 2027-03 alert is a recurrence.

## Out of Scope

- An alert whose opening lies inside the window but whose triggering run of yellows started before it — the replay may open it one period later or not at all, for open and closed alerts alike. Not reproduced here; parked as a discovery.
- Alerts of a previous binning version: still `superseded`, as documented ("Alerts of the previous version are marked `superseded`").
- A closed alert whose opening is inside the window and that the replay no longer produces (changed judgment or restated data): still `superseded`, because the replay re-judged its whole span.
- The model-monitoring alerts (`monitor/model/engine.py`): they replay their own series without a window carry; not touched.

## Design

- **A closed alert is final once its opening leaves the replay.** `_superseded` skips a stored `closed` row whose `version` equals the active version and whose `opened_period` is at or before the window's first period. This mirrors spec 104's carry criterion for open alerts (`opened_period <= first period` → carried), so open and closed alerts that started before the window are treated alike: the window cannot re-judge them. Rows of another version and closed rows opened inside the window keep the current `superseded` behavior.
- **Recurrence reads the last stored close.** `alert_spans(series, policy, *, carry=None, since_close=None)`: `since_close` is the number of periods strictly between a close that precedes the series and the series' first period. The replay then behaves as if that close sat at index `-since_close`, so an opening at series index `i` is a recurrence when `i + since_close <= recurrence`. A close inside the replay still overrides it, as today.
- **The distance is counted in known periods.** `alerts(..., periods=())` takes the distinct periods of the checked data (`check` passes its `periods`); the distance is the count of known periods strictly after the stored `closed_period` and before the key's first series period. Only stored closes before that first period are used (a close inside the window is replayed or belongs to a superseded re-judgment). Without `periods` the distance is 0, the in-window count alone.
- **Notifications follow the flag.** `alert_events` already emits `recurred` for a new open row with `recurrence = true`; nothing changes there.
- Binding contracts: `docs/how-to/stability.md` Persistence and Alerts steps; decision 0010 (synthetic tests); `alert_id` unchanged.

### Assumptions

- Data passed to `check` carries the periods between a past close and the window (the full table, as the how-to describes); when it does not, the distance undercounts and may over-flag a recurrence — `## Risks`.

## Alternatives Considered

- **Never supersede a closed alert at all.** Rejected: a changed judgment (limits, persistence) re-judges the whole window, and a closed alert inside it that the new judgment does not produce must leave the open/closed read.
- **Store a period index on the alert row to measure recurrence.** Rejected: a schema change of `stability_alerts` for a count the known periods already give.

## Open Decisions

- none — the Problem's proposal and spec 104's carry criterion settle every decision.

## Risks

- A table passed without its older periods undercounts the distance and may flag a recurrence that is further away than `recurrence` periods. ACCEPTED — the how-to reads the whole table; the in-window count is a lower bound and the flag errs toward notifying.
- A kept closed alert could coexist with a replayed alert of the same opening: impossible, both have the same `alert_id` and the fresh row wins the merge.
