## Problem

Changing limits, trend, baseline, rules or persistence rewrites the judgment of the whole window on the next
run (`stability/engine.py:516-520`) and can fail the gate in production; there is no way to see beforehand how many
reds, alerts and notifications a new configuration would produce. The judgment is pure over stored profiles
(`stability/metrics.py:1-4`), so a replay is cheap and needs no table scan, but no command exposes it. Every
statistical change of this epic needs exactly this to be tuned safely.

## Proposal

- `bricksmith stability backtest --config new.json --dataset <d> [--periods ...]` (and an API) that reads the stored
  binnings, profiles, marks and actions, runs `compute` and the alert replay with the candidate configuration and
  reports, per metric and series, the color and alert counts before/after, the alerts that would open or close and
  the gate outcome per period; it never writes.
- A `--json` report for CI so a configuration change can be reviewed in a PR.
- A synthetic-noise mode that estimates the false-alarm rate of a configuration on the dataset's own series sizes.

## Out of Scope

- Re-profiling (the backtest reads stored profiles only); binning changes need a new fit and are reported as
  "requires refit".

## Design

- 2026-11-25 — A replay reads only a `Store` (binnings, profiles, results, alerts, actions, runs) and never calls
  `write`: the module has no write path at all, so "never writes" holds by construction. The API is
  `backtest(config, store, *, dataset, periods=(), noise=None) -> BacktestReport`; the CLI wraps it over a `--state`
  JSON file, and any `Store` (Delta-backed included) works through the API.
- 2026-11-25 — The replay mirrors the engine: window = last `max_periods` stored profile periods; the candidate binning
  must match a stored binning by `binning_fingerprint`, else the report says `requires_refit` and compares nothing
  (re-profiling is out of scope); `compute` runs with the same trend seed; alerts replay with the stored alerts
  carried and `keep_inside = not rewrite_all`, where `rewrite_all` is "judgment fingerprint differs from the last
  run's"; human actions fold in as in `check`. Reusing `compute`, `alerts`, `apply_actions` and `_gate` is what makes
  "backtest the current configuration" report zero differences.
- 2026-11-25 — "Before" is what is stored (results, alerts of the last real runs); "after" is the replay. Differences are
  keyed by (period, segment, column, metric) for colors and by `alert_id` for alerts; the per-period gate outcome
  applies the candidate's gate to both sides, with alerts open as of that period.
- 2026-11-25 — Noise mode simulates, per stored trend-eligible series, Gaussian iid series with that series' own length,
  mean and standard deviation, runs the candidate `trend_check` over a rolling history exactly as the engine does and
  reports yellow/red false-alarm rates per series and overall, from a seeded `random.Random` (pure Python).
- 2026-11-25 — Report is a dict-serializable dataclass; `--json` prints it whole, the text form prints the summary.
  The command exits 0 (it never gates): a change that fails the gate is reported, not a CLI failure.

### Assumptions

- Stored results of the window were produced by the stored configuration's judgment (depends on: Validation).

## Alternatives Considered

- **Run `check` against a copy of the data.** Rejected: needs the source table scan and rewrites profiles; the judgment
  is pure over stored profiles, so a replay is cheaper and cannot write.
- **Diff two config fingerprints only.** Rejected: says something changed, not how many reds or alerts it produces.

## Open Decisions

- none — every decision above is settled by the epic's design policy and the engine's existing contracts.

## Risks

- Store reads over many periods; bound by `max_periods` and the selected datasets.

## Outcome

Shipped `bricksmith stability backtest` and the `bricksmith.monitor.stability.backtest` API: a pure replay of a candidate
configuration over the stored binnings, profiles, results, alerts, actions and runs, reading through any `Store` and
with no write path. The report gives, per metric and series, the red/yellow and open-alert counts before and after, every
result whose color or trend color changes, the alerts that would open or close and the gate outcome per period, as text
or `--json` (the command exits 0). Backtesting the current configuration reports zero differences; tightening a limit
reports exactly the results the next real run moves. A change of bins is reported as `requires refit`. A seeded
synthetic-noise mode (`--noise RUNS --seed S`) estimates the trend false-alarm rate on the dataset's own series sizes.
Documented in `docs/how-to/stability.md`. 4/4 tasks, 12 tests.

Left out: re-profiling (by design) and a Spark/Delta CLI source for the state; the API accepts any `Store`. The replay
imports two private engine helpers (`_gate`, `_trend_seed`) so the gate and the trend seed cannot drift from a real run.
