## Problem

Monitoring that runs somewhere else, later, is easy to forget and cannot stop bad data from flowing downstream. The reviewed reference had empty post-run hooks in its task `run()` and a telemetry wrapper that observed every task without failing it, but nothing connected stability to the run. Teams need to declare, next to the code that produces a table, that the table is watched, and decide per task whether instability only warns or fails the task.

## Proposal

- A `stability` key in `@task(metadata=...)` (a mapping, or a list of mappings with `output` naming the target) validated by `StabilityConfig`.
- The plan builder adds declared targets for the stability tables of the entry (`stability_binnings`, `stability_profiles`, `stability_results`, `stability_alerts`, `stability_runs`) in the output's scope (or a declared `scope`), so plan review and dry runs list them.
- The runner's worker calls the stability hook after the task function returns: it reads the written output through the run's `TableIO`, profiles new and refreshed periods, computes results and alerts, writes them through the declared targets, and applies the gate.
- `TaskResult` carries an optional `stability` summary; `task_finished` events include it; the text summary prints one line per checked output.
- `bricksmith stability check` runs the same engine on any table outside a project; `bricksmith stability views` prints the dashboard views (member 5).

## Out of Scope

- Pre-write checks (stability is a property of the published table).
- Notifications (follow-up spec).

## Impact

- `src/bricksmith/plan/build.py` (targets for `stability`), `src/bricksmith/runner/execute.py` (hook call), `src/bricksmith/runner/report.py` (summary field), `src/bricksmith/runner/service.py` (summary line).
- `src/bricksmith/monitor/stability/hook.py`, `src/bricksmith/monitor/stability/cli.py` — new; `src/bricksmith/cli/groups.py` registers the group.
- `tests/unit/monitor/stability/test_run_integration.py` — new.

## Validation

- A task with `stability` in a plan lists the five stability targets with `merge` and the documented keys; dry run lists them as effects; a task without it is unchanged (plan fingerprints of existing projects unchanged).
- With the in-memory `TableIO`: first run fits binning version 1 and profiles every period up to `max_periods`; a second identical run writes the same rows (idempotent keys); a drifted latest period yields red results.
- Gate: `fail_on: ["red"]` fails the task with error code `stability_gate` and blocks dependents; the output write stays recorded; default `warn` keeps the task succeeded with the summary `warned`; `on_error: "warn"` turns an engine failure into summary `error` with a succeeded task, `on_error: "fail"` fails it.
- Old run reports (without `stability`) still load; reports without stability serialize exactly as before.

## Design

- Config keys: `output`, `period` (required), `columns` (`"auto"` default, or mapping column → bin config), `exclude`, `segments`, `weight`, `baseline` (`{"kind": "fixed"|"previous"|"rolling", ...}`), `fit_periods` (default 1; periods used to fit when no fixed range), `limits`, `column_limits`, `trend`, `persistence`, `gate` (`{"fail_on": [...], "on_error": "warn"|"fail"}`), `min_rows` (30), `refresh_periods` (1), `max_periods` (36), `max_segments` (50), `scope`, `prefix` (`"stability_"`).
- `fail_on` conditions, evaluated on the latest period only: `red` (any red result), `yellow` (any yellow or red), `critical` (an open critical alert), `alert` (any open alert). Empty list (default) never fails.
- Periods to profile: periods present in the output that have no profile for the active version, plus the latest `refresh_periods`, limited to the latest `max_periods`.
- Version: the active binning is the highest version whose stored `config_fingerprint` equals the fingerprint of the binning-relevant config; otherwise a new version is fitted from the fixed baseline range, or the earliest `fit_periods` periods.
- Writes go through `TaskContext.write` on the declared targets, serialized per physical table in the process and retried on concurrent-modification errors (3 attempts).
- Previously stored alerts of the dataset that a replay no longer produces are rewritten with state `superseded`.
- The hook is skipped in dry runs and for failed tasks.

## Alternatives Considered

- A generated companion task per monitored output. Rejected: it cannot gate the producer without changing the dependency graph semantics.
- Hidden writes from the runner. Rejected by decision 0009.

## Open Decisions

- Default gate: warn (never fail) — chosen so that adding observation never breaks an existing pipeline; failing is an explicit per-task choice.

## Risks

- A failing gate runs after the write: the table is already published. The guide states this and recommends `fail_on` for blocking dependents, not for rollback.

## Handoff

Keep `TaskContext` and the plan model backward compatible; add `stability` to the plan's non-write metadata keys.
