## Problem

Regression from #60 (PR #110), reproduced by the round-1 reviewer on 2026-11-26 (main 48f4a94):

```
.venv/bin/python -I -c 'import sys; sys.path.insert(0,"src"); from bricksmith.ops.redact import redact_text as r; print(r("postgresql://admin:p@ss@db.example.com")); print(r("smtp://user:P@ss.w0rd@mail.example.com"))'
postgresql://admin:<redacted>@ss@db.example.com
smtp://user:<redacted>@ss.w0rd@mail.example.com
```

Base 4b334fe masked both whole (`admin:<redacted>@db.example.com`). At `src/bricksmith/ops/redact.py:236` the trailing `@host` is taken as a path address although no `/` precedes it, so the first `@` becomes the separator and the password tail leaks. `tests/unit/ops/test_ops.py:532,538` always carry a `/x` path, so no test covers a bare host. Consequence: database and SMTP passwords with `@` appear in logs. Keep the #41 linear-time bound and the #60 cases green.

## Proposal

- In `_credential_separator`, pop a trailing address-looking `@host` only when a `/`, `?` or `#` precedes it (it is then a path/query address). With no path before it, the last `@` is the credential separator, so a password holding `@` is masked whole.
- Add the reviewer reproductions as regression cases; keep the #41 linear-time bound and the #60 cases green.

## Out of Scope

- none — only the bare-host `@` separator choice changes; other credential shapes are untouched.

## Design

## Risks

- A bare-host URL whose password is followed by a dotted address with no path is read as a password containing `@`; that errs toward not leaking.
