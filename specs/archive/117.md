## Problem

The model `open_alerts` view is `_trusted(ALERTS)` filtered to `state = 'open'` (`src/bricksmith/monitor/model/tables.py:332-335`); `_trusted` keeps the latest finished run per model, model_version and monitoring_period (`tables.py:157-170`). A persistence/trend span alert carries `monitoring_period = span.last_period` (`src/bricksmith/monitor/model/engine.py:950`), which moves forward each run (`src/bricksmith/monitor/persistence.py:160`), with a stable `alert_id` (`engine.py:942`).

Consequence: when a later run moves a span to a newer period (or closes it), the earlier runs' rows remain the "latest" for their older periods, so the same alert stays listed as open once per earlier run, forever. `<prefix>open_alerts` and `open_alerts_by_severity` (`docs/how-to/model-monitoring.md:305-306`, `:380`) overcount and disagree with the run's `open_alerts`/`critical_alerts`. Reproduced on e2716ad: three `engine.check` runs on a MemoryStore — r0 open 2025-04, r1 open 2025-05, r2 closed 2025-06 (r2 open_alerts=0) — while `alerts.trusted` (same key as the view) still returns r0 and r1 open rows. The report is unaffected (reads the latest run's stored alerts).

Done when: the view (and the pure `trusted` helper it mirrors, if used for alerts) returns each alert_id at most once, in its latest state, a regression test covers the repro, and the doc describes the view accurately. Check whether the stability open-alert view has the same keying; fix it in the same spec if so.

## Proposal

- `<prefix>open_alerts` lists each `alert_id` at most once, in the state its latest finished run stored, so a span that moved to a newer period or closed no longer leaves rows open for the earlier runs.
- `<prefix>open_alerts_by_severity` and `<prefix>alert_recurrence`, which read the same alert selection, count each alert once and agree with the run's `open_alerts` and `critical_alerts`.
- A regression test reproduces the three-run case (open 2025-04, open 2025-05, closed 2025-06) against the views and passes.
- `docs/how-to/model-monitoring.md` describes the views as "the latest stored state of each alert".

## Out of Scope

- The stability `open_alerts` view: its alerts table is keyed `(dataset, alert_id)` (`src/bricksmith/monitor/stability/tables.py:75`), so each alert is already one row; there is nothing to fix there.
- The pure `trusted` helper: it only handles result rows (`report.py`, `alerts.py replay_alerts`), never alerts, so it does not carry this keying.
- Light alerts whose period was recomputed green by a later run keep their older stored row; that is a separate finding parked in `## Discoveries`.

## Design

- Decision: alerts get their own selection, `_latest_alerts`, keyed `(model, alert_id)` and picking the row of the latest finished run that stored that id. Alternatives weighed: keep `_trusted` and add a `NOT EXISTS` newer-row filter (more SQL for the same result); key `_trusted` itself by `alert_id` for every table (results and details legitimately key by period). Chosen because the alert id is the stable identity of a span and light alert ids already carry the period, so per-id latest keeps light alerts unchanged and fixes spans.
- Decision: `alert_recurrence` switches to the same selection, since it counts distinct alert ids and its `recurrence` flag should be the latest stored.
- Contract: SQL must run on Spark and on the sqlite used by `test_model_tables.py` (plain joins and `max`, no dialect-specific functions), as `_trusted` does.
- Contract: names go through `table_name`; `# noqa: S608` stays as in `_trusted`.
- Contract: English only, nothing organization-specific, no generated YAML.

### Assumptions

- A run that closes a span stores the closed row under the same `alert_id` (shown by the repro: r2 stores the closed state) — Validation depends on it.

## Alternatives Considered

- Fixing it in the engine by rewriting earlier runs' rows: rejected; run rows are an append-only record of what each run saw.
- Adding a dedicated "current alerts" table: rejected; a view over the stored rows is enough and needs no new write path.

## Open Decisions

- none — the keying, the recurrence view and the stability check are settled above.

## Risks

- A light alert whose period a later run recomputed to green stays open (no later row exists for its id): ACCEPTED — same as before this change, parked as a discovery.
- SQL dialect drift between Spark and sqlite: mitigated by testing the view on sqlite with plain joins.
