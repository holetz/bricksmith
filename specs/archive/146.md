## Problem

Only periods without a stored profile plus the latest `refresh_periods` are profiled again
(`stability/engine.py:281-289`). A backfill or correction of an older period is invisible: its stored profile,
results and alerts stay stale, and the only remedy is to raise `refresh_periods` for every run, which rescans
the table each time. The runner already supports inspectable reprocessing (BS-03), but it does not tell the
stability hook which periods were rewritten. The gate also judges only the latest period
(`stability/engine.py:534-538`), so a reprocessed older period that turns red never gates.

## Proposal

- `bricksmith stability reprocess --dataset <d> --periods <p1..p2|list>` (and the `check(...,
  reprocess=[...])` API) that re-profiles exactly those periods, re-judges the window and replays alerts.
- When a run reprocesses a period range through the runner, pass it to the stability hook so the same periods
  are re-profiled automatically (`refresh` = declared refresh ∪ reprocessed periods).
- `gate.periods: latest | profiled` (default `latest`): with `profiled`, red results of any period profiled in
  this run count.
- Record the reprocessed periods on the run row (`periods_reprocessed`), and with `revision` on, report the
  revision of each reprocessed period against its first publication.

## Out of Scope

- Row-level diffs of what changed (still profile-level, as decided in spec 75).
- Reading Delta history.

## Validation

- A changed older period outside `refresh_periods` is re-profiled with `reprocess` and its results and alerts
  reflect the new data.
- A runner reprocess of a range re-profiles the same periods without the explicit command.
- With `gate.periods: profiled`, a red reprocessed period fails the gate.

## Design

**Decision 1 — one engine input, three entry points.** `check(..., reprocess=[...])` takes explicit periods.
The `stability reprocess` command and the runner both end in that input, so the three paths cannot diverge.
Alternative: a separate `reprocess()` function duplicating the plan; rejected, the plan (`_plan_periods`) is the
one place that decides what is profiled.

**Decision 2 — refresh set.** `refresh = declared refresh_periods ∪ reprocess`. A reprocessed period must exist
in the data and lie inside the `max_periods` window; otherwise `MonitorError` names it. This is the bound
that keeps the rescan cost limited (the Risks line); the run message reports how many periods were profiled.

**Decision 3 — a reprocess rewrites the judgment of the whole window.** The engine already rewrites every
result and replays all alerts when the judgment fingerprint changes (`rewrite_all`). A reprocess sets the same
flag: results of every window period are re-emitted and stored alerts that the replay no longer produces become
`superseded`, so an older period's alert reflects the new data and not the stale one. Alerts are replayed
through the existing `alert_events` comparison, so only real transitions notify.

**Decision 4 — `gate.periods`.** `latest` (default, unchanged) counts the latest period only; `profiled` counts
red and yellow results of every period profiled in this run that lies in the window (plus vanished periods).
It is emitted by `Gate.to_dict` only when not default so existing fingerprints stay. Open-alert and critical
conditions are unchanged.

**Decision 5 — runner contract.** `run_plan(..., reprocess=...)` takes a list of periods or ranges
(`"2026-01..2026-03"`, `"2026-05"`); `TaskContext.reprocess` carries them; the stability hook resolves
ranges against the data's periods (inclusive, string order, as periods already sort) and passes the result to
`check`. The runner never needs to know a period column: only declaring tasks use it.

**Decision 6 — record.** `stability_runs.periods_reprocessed` holds the comma-joined reprocessed periods (empty
when none). With `revision` on, the existing revision comparison already covers every re-profiled window
period against its first publication, so reprocessed periods are reported without new metrics.

Binding contracts: no generated YAML, lightweight imports (the hook stays the only importer), existing stored
rows keep their meaning (default `gate.periods` and empty `periods_reprocessed`).

### Assumptions

- The runner has no existing period-range concept; Decision 5 defines the minimal one (Decision 5 depends on it).

## Alternatives Considered

- Raising `refresh_periods` per run: the status quo; rescans the table every run, rejected by the Problem.
- Detecting rewritten periods from Delta history: out of scope (Out of Scope) and engine-specific.
- A per-period gate list in the declaration: more surface than `gate.periods`, with the same effect.

## Open Decisions

- none — every decision is settled by Design; a `run` CLI flag for `reprocess` is deferred and costs one
  argument once a user asks for it.

## Risks

- Reprocessing a long range rescans a large table; bound it by `max_periods` and report the cost in the
  run summary.

## Outcome

Shipped, reviewed and ready for merge: `check(..., reprocess=[...])` re-profiles exactly the named periods (a list or `first..last` ranges) on top of the refresh range, re-judges the whole window, replays the alerts and records `periods_reprocessed` on the run row; a period outside the data or the `max_periods` window is an error. The runner takes `reprocess` and hands it to every stability-declaring task, which ignores periods it lacks. `gate.periods: profiled` makes the gate count every period profiled in the run, and `bricksmith stability reprocess` is the command. With `revision` on, reprocessed periods are compared with their first publication. The how-to guide documents all of it.

Left out: a `reprocess` flag on the `run` command (library only, one argument once asked for), row-level diffs and Delta history, as stated in Out of Scope. Task 2.4 was appended during the build to carry ranges and `skip_unknown` in the engine.
