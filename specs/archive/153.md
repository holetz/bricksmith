## Problem

The tables are dashboard-ready, but the dashboard is not: views are only printed by
`bricksmith stability views` (`stability/cli.py:56-59`) and must be created by hand; there is no dataset
dimension (owner, task, physical table, last run, binning version), the trend band cannot be drawn because only
`trend_expected` and `trend_deviation` are stored (`stability/tables.py:47`), and marks and actions will live in
separate tables. Epic 64 left the dashboard file out of scope, so each project rebuilds the same pages.

## Proposal

- Views created by the run (opt-in `views: true`) and by the CLI: `stability_datasets` (dimension),
  `stability_series` (one row per series and period with value, limits, band, light, trend status, mark, action),
  `stability_incidents`, plus the existing three.
- A generated Lakeview (AI/BI) dashboard definition (`.lvdash.json`, not YAML) for the views: overview by dataset
  and period, series chart with limits and trend band, PSI bin contributions, alerts and actions queue, runs and
  cost; delivered as a native Python bundle resource (decision 0002) and through the Copier template.
- Document the star model update.
- Build the dashboard with `databricks.bundles` Python resources, parameterized by `dataset_catalog` /
  `dataset_schema`, so the same definition deploys to every target.
- Optionally emit SQL alert (v2) resources on the views for teams that want native alerting next to the run gate.
## Out of Scope

- Third-party BI files.

## Design

- **The dashboard is data, generated by a pure function.** `dashboard_definition(prefix, scope)` returns the
  Lakeview (`.lvdash.json`) structure as a plain dict; nothing is committed as JSON. The bundle resource passes the
  dict as `serialized_dashboard` of a native `Dashboard` (decision 0002: Python resources, no generated YAML).
- **Parameterized by the bundle, not by the file.** Datasets query unqualified view names; the resource sets
  `dataset_catalog` / `dataset_schema` (and `warehouse_id`) on the `Dashboard`, as literals or `${var.*}` references,
  so one definition deploys to every target.
- **One contract for views and dashboard.** `VIEW_COLUMNS` in `tables.py` names the columns each dashboard view
  exposes; dashboard datasets select only columns of that contract or of a stability table's `SCHEMAS`, and a test
  fails when a widget reads a field no dataset carries.
- **Views.** `stability_series` joins each result with the alert of its series that was last seen in that period and
  that alert's latest action, and carries the stored trend band (`trend_lower`, `trend_upper`), the limits, the
  light (`status`), the period mark and the action. `stability_datasets` is one row per dataset with the latest
  binning version, the last run, its gate and the latest period's status. `stability_incidents` groups alerts per
  dataset and opening period (incidents are derived, never stored). Existing views keep their names and columns.
- **Opt-in creation.** `views: true` in the declaration makes the run execute the view statements after its writes
  (`CREATE OR REPLACE VIEW`, idempotent); a failure to create a view is reported but never fails the check, since
  the rows are already stored. Off by default; `bricksmith stability views` stays the manual route.
- **Pinned format.** `LVDASH_VERSION` records the widget spec versions used; a structural test pins the page and
  widget shape so a format change is a visible diff.

### Assumptions

- No dataset owner is stored in any stability table, so `stability_datasets` has no `owner` column; adding one needs
  a declared field first (depends on `## Proposal` dimension list).
- The pre-existing `trend_lower` / `trend_upper` columns are the band (depends on `## Problem`).

## Alternatives Considered

- A committed `.lvdash.json` per project: rejected, it is the intermediate generated artifact decision 0002 removed.
- Defining the dashboard through the SDK's Lakeview API at run time: rejected, it bypasses bundle deploy and drift
  control.

## Open Decisions

- SQL alert (v2) resources on the views are optional in the proposal: deferred to a follow-up spec, decided when a
  team asks for native alerting next to the run gate.
- Live Free Edition proof of the deployed dashboard needs workspace credentials absent from this run: it is recorded
  as pending evidence, decided at the next remote proof round.

## Risks

- The Lakeview JSON format evolves; pin a version and cover it with a structural test plus the Free Edition
  proof.

## Outcome

contract; the opt-in `views: true` declaration key that makes a run create every view (failures reported, never failing

(`bricksmith.monitor.stability.bundle:load_resources`, parameterized by `dataset_catalog` / `dataset_schema` /
`warehouse_id` bundle variables, plus `stability_dashboard(...)` for custom choices); and the how-to update with the star
model and deployment guide.

Left out: SQL alert (v2) resources, an owner column (no stability table stores one), delivery through the Copier template
(it does not exist in this repository) and the live Free Edition proof of the deployed dashboard (no workspace
credentials in the run); each is a `decision:` line in `## Discoveries`.
