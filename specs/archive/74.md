## Problem

Stability alerts are stored and can fail a run, but nobody is told when a warning opens. Operations already have `bricksmith.ops.AlertNotifier`.

## Proposal

- Emit an `AlertEvent` (class `statistical_alert`) for each alert that opens, escalates or recurs in a run, with dedup keys stable across replays, and deliver them through the configured notifier.
- Configuration per task (`stability.notify`) and per project; never notify on replays of unchanged alerts.

## Out of Scope

- New notification adapters or transports: delivery stays with `bricksmith.ops.AlertNotifier` and its adapters.
- Notifying on `closed` or `superseded` transitions: only opens, escalations and recurrences are actionable; resolution notices are deferred.
- Notifying from `bricksmith stability check` (the pure CLI has no notifier); only the task hook delivers.
- Model-monitoring alerts (`monitor/model`): a separate epic member owns them.

## Impact

### Product code this spec expects to touch

- `src/bricksmith/monitor/stability/config.py` — the `notify` declaration key and its policy.
- `src/bricksmith/monitor/stability/engine.py` — alert transitions turned into `AlertEvent`s.
- `src/bricksmith/monitor/stability/hook.py` — delivery after the rows are written.
- `src/bricksmith/runner/execute.py` — the run-level notifier and default policy.
- `docs/how-to/stability.md` — the user guide for `notify`.

### Process surface this spec expects to touch

- none — no workflow, skill or reference changes.

## Validation

- `uv run pytest tests/unit/monitor/stability -q` passes, including the new `test_stability_notify.py`.
- Replaying a run over unchanged data delivers nothing; a sliding window that drops the opening period of an open alert delivers nothing (identity carried by the stored alert id).
- `uv run ruff check && uv run ruff format --check && uv run pyright` pass.

## Design

- Transitions are derived by comparing the freshly replayed `open` alert rows with the rows stored before the run (`stored_alerts`, keyed by `alert_id`). `opened`: no stored row with that id. `escalated`: stored severity `warning`, fresh `critical`. `recurred`: fresh `recurrence` true and the stored row (or none) false. An unchanged alert yields no event, so replays are silent by construction; because spec 99 makes a carried alert adopt its stored id, a sliding window never looks like a new opening.
- The event is `AlertEvent(kind="statistical_alert", error_class="statistical_alert")` with an explicit `key` of `stability:<dataset>:<alert_id>:<transition>`, stable across replays and independent of run id and time; `details` carry metric, column, segment, opened and last period.
- Delivery happens in the hook only after every table write succeeded, so a failed write retries the notification on the next run rather than losing it. `AlertNotifier.notify` never raises, so delivery cannot fail a task or touch the gate.
- Configuration: `stability.notify` is `true`, `false` or `{on: [opened, escalated, recurred], min_severity: warning|critical}`. The project default is the `notify` keyword of `run_plan` (same shapes); a declared value overrides it, `false` disables. Without a notifier nothing is delivered. `notify` is outside the judgment and binning fingerprints.
- Binding contracts: root import stays light (no new top-level imports of heavy modules); English only; no `dataclass` field affects existing serialized outcomes.

### Assumptions

- The project-level configuration is a `run_plan` keyword rather than a file, because the notifier itself is injected there; no project config file for the runner exists (Design, Open Decisions).

## Alternatives Considered

- Notify inside `check` through an injected notifier: rejected, it would couple the pure engine to delivery and fire before the rows are stored.
- Notify from stored alert rows after the fact (a separate command): rejected, it needs its own cursor to avoid replays.

## Open Decisions

- none — the shapes above are decided; resolution notices are out of scope.

## Risks

- A notification delivered but the run crashing before the next merge could resend: mitigated by the notifier's dedup window and the stable key. ACCEPTED for a crash between write and delivery order is write first, so at worst a missed (not duplicated) notice is retried next run.
- Policy drift between project default and task value: mitigated by one parser shared by both.

## Outcome

Shipped `stability.notify` (true, false or `{on, min_severity}`) and a project default through the `notify` keyword of `run_plan`. Alerts that open, escalate or recur become `statistical_alert` events with stable keys `stability:<dataset>:<alert_id>:<transition>`, delivered through the injected `AlertNotifier` after the stability rows are stored. Transitions come from comparing replayed alerts with the stored open alerts, so replays and sliding windows (carried alert ids from spec 99) send nothing. Delivery never raises and never touches the gate. Documented in `docs/how-to/stability.md`.

Left out: resolution (closed) notices, new adapters, delivery from `bricksmith stability check`, model-monitoring alerts. Full gate on the branch: ruff, format, pyright and 1466 tests green; remote proof was not needed (pure in-memory behavior, no Databricks surface).
