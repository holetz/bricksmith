## Problem

bricksmith knows the dependency graph between tasks (`graph/model.py:182`), but stability
judges each output in isolation: a broken source table turns every derived table red, each with its own alerts
and notifications, and nothing points to the origin. Alerts also carry no owner or criticality, so notifications
cannot be routed and the dashboard cannot be filtered by responsibility, although governance declarations exist
(BS-15).

## Proposal

- When an upstream output of the same run has an open red incident for a period, downstream incidents for
  the same period are labeled `upstream:<dataset>` and their notifications suppressed (configurable), while results
  stay stored.
- `owner`, `domain` and `criticality` read from task/governance metadata into the run rows and a dataset
  dimension; the notifier routes by owner and criticality.
- Severity score for ranking: exceedance size (prediction-interval normalized) × persistence × dataset
  criticality × number of correlated columns, stored on the incident.
- The pattern follows alert inhibition (Prometheus Alertmanager) and lineage-based root cause in Databricks data
  quality monitoring.
## Out of Scope

- Cross-run lineage (only tasks of the same plan).

## Impact

## Validation

- A broken source in an example plan yields one notified incident on the source and labeled, silent incidents
  downstream.

## Design

- **Declaration.** `owner` and `domain` are free text, `criticality` is `low`, `medium` (default), `high` or `critical` with weights 1, 2, 3, 4, and `suppress_downstream` is a boolean (default `true`). All four serialize and enter the judgment fingerprint only when they differ from the defaults, so existing declarations are unchanged. They are read from the task's own `stability` metadata, the declaration that already describes the dataset; governance resource owners are not consulted (see `## Discoveries`).
- **Same-run upstream register.** The runner keeps, per run, the incident each task left: `(dataset, period, origin)`, recorded only when the task has an open incident with a red result in its latest period. `origin` is the task's own dataset when it has no upstream incident of that period, else the origin it inherited. A task inherits through its direct `depends_on`, so the lookup is transitive because each task carries the origins it inherited. Only tasks of the same plan and run are known; nothing is read across runs.
- **Matching.** The check receives the upstream records of its direct dependencies. A record whose period equals the check's latest period marks the new incident `upstream:<origin>` (first origin by name when several). With `suppress_downstream` the per-alert and digest notifications of that run are dropped; results, alerts and the incident stay stored and visible, and the outcome counts them as suppressed upstream. The gate is unchanged.
- **Ownership on rows.** The runs table gains `owner`, `domain`, `criticality`, `severity_score`, `upstream`; the alerts table gains `upstream`; a `<prefix>datasets` view exposes the latest owner, domain and criticality per dataset as the filterable dimension. New columns are added through the tables' existing evolution option.
- **Severity score.** `severity_score = sum(cause scores) × max(flagged_periods) × criticality weight × number of distinct alerted columns`, rounded to 6 digits, stored on the incident and the run row. Cause scores are the existing prediction-interval normalized exceedance; persistence is the largest `flagged_periods` among the open alerts; the column count is at least 1.
- **Routing.** `AlertRoute(adapter, owners, domains, min_criticality)` plus an optional `routes` list on `AlertNotifier`: an adapter with at least one route receives only events matching one of them (owner and domain taken from `details`), adapters without a route keep receiving everything, so default delivery is unchanged. Alert and digest events carry `owner`, `domain`, `criticality` and `upstream` in `details`.
- Contracts: pure Python, root import stays light, no generated YAML (decision 0002), declarations and rows without the new keys keep their old fingerprints.

### Assumptions

- A red incident means an open alert exists and the latest period has a red result (`Outcome.red > 0`); stated by the epic's wording. Depends on: Design / Same-run upstream register.
- Suppression is the default because the proposal makes it configurable and silent downstream incidents are the point; `suppress_downstream: false` restores per-incident delivery. Depends on: Design / Matching.

## Alternatives Considered

- Read lineage from the stored tables across runs: rejected, out of scope; the run-level register needs no storage.
- Drop downstream alerts instead of silencing notifications: rejected, the risk section requires labeling, never dropping.
- A new owner table: rejected, flat columns on existing tables and one view keep the star model.

## Open Decisions

- none — every decision is settled by the proposal, the epic's design policy and the contracts above.

## Risks

- Suppression can hide independent downstream issues; label, never drop, and keep the gate unchanged.

## Discoveries

- governance resource owners (BS-15) are not consulted: owner, domain and criticality come from the stability declaration; a governance fallback is a follow-up
- decision: owner/domain/criticality declared on the stability metadata, no governance lookup — governance resources are per object and the stability declaration already binds one dataset
- decision: task 3.1 had a verify path that does not exist (tests/unit/runner); descoped and replaced by 3.3 over tests/unit/execution — the check is not weakened
- decision: a red incident for suppression is an open incident with red>0 in the latest period (as the Design assumption states); ownership keys are not in the judgment fingerprint — an owner or suppression change must not re-judge the whole window, and Design's wording was too broad
## Outcome

Downstream stability incidents are now labeled and silenced, and every incident carries ownership and a score:

- A task whose upstream task of the same run left a red incident for the same period gets its incident labeled `upstream:<origin>` (transitive through the run) and, with `suppress_downstream` (default `true`), its per-alert and digest notifications are silenced; results, alerts and the incident stay stored and the gate is unchanged.
- `owner`, `domain`, `criticality` are declared on the stability metadata and stamped on the run rows (with `severity_score` and `upstream`), on the alert rows (`upstream`) and on every alert and digest event; a `stability_datasets` view is the filterable dimension.
- The severity score is exceedance x persistence x criticality weight x correlated columns, stored on the incident and the run row.
- `AlertRoute` plus `AlertNotifier(routes=...)` route events to adapters by owner, domain and minimum criticality; adapters without a route keep receiving everything.
- Left out: governance resource owners are not consulted (a follow-up), and nothing is read across runs. The ownership keys stay out of the judgment fingerprint, so changing an owner never re-judges a window. Task 3.1 was descoped and replaced by 3.3 because its verify named a path that does not exist.
