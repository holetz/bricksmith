## Problem

- Fit: `src/bricksmith/monitor/stability/spark.py:107-117` runs `scoped.groupBy(name).count().collect()` in a loop over columns, plus another scan in `_with_counts` (line 115); `scoped` is never cached. A table with N columns costs N+ full scans and N collects of up to 100k rows.
- Profile: `spark.py:156` (null-period count), `:169` (`scoped.count()`), `:173` and `:184` (per segment set) scan the input 2 + 2×(segment sets) times with nothing persisted; three segment sets cost eight full scans per run.

Consequence: fitting or profiling a wide or segmented table is slow at volume; numbers are correct.

## Proposal

- Fit counts every column that needs exact counts in a number of Spark jobs that depends on the number of distinct column types, never on the number of columns; the fitted binning equals the one the pure engine fits on the same rows.
- Profiling runs a fixed number of Spark jobs (null-period/row totals, segment ranking, cell totals) independent of both the number of segment sets and the number of columns; the profile rows equal the pure engine's.
- A test measures the Spark actions issued for a narrow and a wide, multi-segment table and proves the count is the same for both.

## Out of Scope

- Persisting or caching the input frame: serverless Spark Connect does not guarantee `cache()`/`persist()`, so the bound comes from fewer jobs instead.
- Changing bin fitting, the large-numeric percentile path or the profile row contract: numbers stay identical.
- The engine's other reads (`periods_spark`, `engine.py`): not part of the reported scans.

## Design

- **Fit: one job per column type.** Columns that need exact counts are grouped by Spark dtype; each group builds `explode(array(struct(lit(name) AS c, col AS v)))` over the scoped frame and runs one `groupBy(c, v).count()`; each group's rows are split into per-column count dicts. Same dtype keeps the struct type uniform and keeps value types (ints stay ints, booleans stay booleans), so `fit_bins` sees the same keys as before. Null and NaN group like in `groupBy(name)`. Jobs scale with distinct dtypes, a small bounded set.
- **Large-numeric columns** keep their remote percentile job; `_with_counts` counts are folded into the same grouped pass rule per column only where unavoidable (one job per such column); they are the rare path above 100k distinct values.
- **Profile: three jobs.** (1) one `agg` yields rows in `periods` and rows with a null period; (2) one job ranks every non-empty segment set at once via `explode(array(struct(set index, key)))` and `groupBy(i, key).count()`; (3) the cell totals explode the cells and the segment keys and group by `(set index, period, segment, column, bin)`; segments beyond `max_segments` are dropped in Spark with a condition over the ranked keys. Truncation info and totals are rebuilt in Python from the collected rows.
- Binding contracts: results equal `profile_rows`/`fit_rows_binning` (`tests/remote/test_stability.py`); no persisted state; heavy imports stay inside functions; synthetic data only (decision 0010).

### Assumptions

- The Free Edition serverless session accepts `explode` over arrays of structs (already used by the profile) — `## Design` fit grouping relies on it.

## Alternatives Considered

- Cache the scoped frame and keep the loops: fewer scans but the same job count and cache support differs on Spark Connect serverless; rejected.
- Unpivot every column to string and cast back: one job for everything but loses numeric key types and risks parity; rejected for one job per dtype.

## Open Decisions

- none — the job bounds are fixed by Design; the action-count test pins them.

## Risks

- Parity drift on type keys (float vs int, NaN, boolean): mitigated by grouping per dtype and the existing pure-vs-Spark parity test.
- The segment-set explode multiplies rows before the group: ACCEPTED — the total rows processed equal the previous per-set work, in one job.

## Outcome

Stability fit counts every monitored column in one Spark job per column type, and profiling runs three jobs (row totals, segment ranking, cell totals) whatever the number of columns or segment sets. Parity with the pure engine holds: the existing Spark-equals-pure test and a new narrow-versus-wide test (3 and 12 value columns, 1 and 3 segment sets) passed on the Free Edition with an explicit profile, and the new test pins the action counts. Left out: caching the frame and the large-numeric path (one extra job per such column). Reviewed and ready for merge.
