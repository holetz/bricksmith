## Problem

`stability_results` and `stability_alerts` are merged on their keys (`stability/tables.py:71-78`): a
reprocess, a refresh or a judgment change overwrites what was reported before, and the runs table keeps only
counts (`stability/tables.py:64-69`). After a backfill or a limits change nobody can answer "what did the
monitor say about 2026-03 when we published it?", which governance and incident reviews need. Delta time travel
is bounded by retention and is not available on every engine.

## Proposal

- Optional `history: true` adds `stability_results_history` (append-only, keyed by run_id) holding the
  results each run emitted, plus `judged_at`; a view `stability_results_as_of(date)` pattern documented as SQL.
- Alert state transitions appended to `stability_alert_events` (opened, escalated, closed, superseded,
  action applied), which also feeds response-time measures.
- Retention option (`history_periods`) to bound growth.
- Each history row carries the judgment fingerprint and the Delta version of the monitored table read by the
  run, so a judgment is keyed by (period, run, judgment version, data version) and backfills add evaluations
  instead of replacing them.
## Out of Scope

- Profile history (profiles stay current; revision snapshots already keep first publication).

## Validation

- After a reprocess that turns a period red, the history table still holds the earlier green judgment with its
  run_id, and the as-of query returns it.

## Design

**Decision 1 — two optional tables, off by default.** `history: true` adds `stability_results_history` and
`stability_alert_events`, the same way `revision: true` adds `stability_revisions`: kinds `results_history` and
`alert_events`, created only when declared, so existing projects and fingerprints are untouched. `history` is
serialized by `StabilityConfig.to_dict` only when true and is deliberately **not** part of the judgment fingerprint:
recording a judgment never changes it.

**Decision 2 — history rows.** Each run appends the results it emitted (`results` rows of the run) plus
`judged_at` (the run's start), `judgment_fingerprint` (the run's judgment hash, the judgment version) and
`data_version` (Delta version of the monitored table read by the run; `NULL` when the engine cannot tell, as for
in-memory tables). The key is `(dataset, run_id, version, period, segment, column, metric)`: a run never overwrites
another run's row, so a reprocess adds an evaluation instead of replacing one.

**Decision 3 — as-of read.** `results_as_of(rows, as_of)` (pure, in-memory) and `as_of_statement(scope, prefix,
as_of)` (SQL text) return, per `(dataset, period, segment, column, metric)`, the row with the greatest `judged_at`
not after `as_of`. A parameterless SQL view cannot take a date, so the SQL is a documented pattern generated on
demand, not one of `view_statements`.

**Decision 4 — alert events.** Per run, `alert_events` rows record transitions of an alert against the stored open
rows: `opened`, `escalated`, `closed`, `superseded` and `action_applied` (one per human action not yet recorded for
that alert). Key `(dataset, alert_id, event, run_id)`; columns `dataset, alert_id, event, run_id, period, severity,
state, resolution, action_id, message, occurred_at`. `recurred` is recorded as `opened` with the existing
`recurrence` carried in the alert row, not a new event, keeping the vocabulary the proposal names.

**Decision 5 — retention.** `history_periods` (int ≥ 0, default 0 = every emitted period) limits each run to
appending history of the most recent N periods of its window. It bounds the growth per run; nothing already
written is deleted (append-only is the contract), and the guide says so.

**Decision 6 — Delta version.** The hook reads the latest version of the monitored table with
`DESCRIBE HISTORY <table> LIMIT 1` when a Spark session exists, inside a guard: any failure yields `NULL` and never
fails the check.

Binding contracts: no generated YAML, lightweight imports (Spark stays in the hook), existing rows keep their
meaning.

### Assumptions

- A run's emitted `results` are what "the results each run emitted" means (Decision 2 depends on it).
- Human action events are derived from the actions table at run time, not written by the `action` command
  (Decision 4 depends on it).

## Alternatives Considered

- Delta time travel only: bounded by retention and unavailable on some engines (the Problem), rejected.
- Making `stability_results` itself append-only: breaks the merge key every dashboard view relies on, rejected.
- Deleting history older than `history_periods`: contradicts append-only and needs a destructive write path; left out.

## Open Decisions

- none — every decision is settled by Design; a retention that deletes is deferred until a user asks.

## Risks

- History grows by the emitted results of every run, a reprocess of a wide window especially; bounded per run by
  `history_periods` and documented.

## Outcome

Shipped the optional judgment history for stability monitoring, reviewed and ready for merge.

- `history: true` (and `history_periods`) in the stability declaration adds two append-only tables:
  `stability_results_history` (the results each run emitted, with `judged_at`, the judgment fingerprint and the
  Delta version of the monitored table, keyed by run) and `stability_alert_events` (`opened`, `escalated`,
  `closed`, `superseded`, `action_applied`).
- `results_as_of` and `as_of_statement` return the judgment that stood at a date; a reprocess that turns a period
  red leaves the earlier green judgment in the history.
- The hook reads the Delta version best-effort (`DESCRIBE HISTORY`), never failing the check.
- The stability guide documents the tables, retention and the as-of query.

Left out: deleting history older than `history_periods` (it only bounds what each run appends), profile history,
and a CLI command for the as-of query.
