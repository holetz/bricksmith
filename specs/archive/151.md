## Problem

Every (segment, column, metric, kind) series opens its own alert and its own notification
(`stability/engine.py:348-400`). One bad load typically turns many columns and segments red at once, so people
receive dozens of messages for one cause, and with `max_segments` 50 and tens of columns the number of judged
series per period is in the thousands, where even the nominal false-alarm rate produces alerts every run. The
bin contributions that explain a PSI jump are stored (`stability_profiles.contribution`) but nothing ranks them.

## Proposal

- An incident per dataset and period groups the alerts opened in the same run, with a ranked list of the
  top contributing segments, columns and bins (from `contribution`, `volume_change` and the deviation sizes).
- Notifications in `digest` mode: one message per dataset run listing the incident and its top causes, keeping
  the per-alert dedup keys for idempotence.
- An optional noise budget: `max_alerts_per_run` and a false-discovery control (Benjamini–Hochberg over the
  trend p-values of the run) to decide which yellow series open alerts.
- Re-notification policy: notify again only on escalation, on a material value change, or after a reminder
  interval (`remind_after`), never on every run of an unchanged open alert.
- A false-positive rate per rule (from typed resolutions) reported in the run summary to drive tuning.

- Lineage-aware suppression (separate spec).

## Design

- **Incidents are derived, not stored.** An incident is computed at each check from the run's open alerts, results and fresh profile rows and returned on `CheckResult.incident` and in the run summary. No new table, so no schema, view or remote-test change; the per-alert rows stay the source of truth. Id: hash of dataset and latest period.
- **Ranking.** Each open alert active in the latest period gets a score: `|value| / red_limit` when its metric has a red limit, else `|trend_deviation| / trend.red`; ordered by severity then score. Segments, columns and bins are ranked by summed alert score (segments, columns) and by stored `contribution` of the latest period (bins). Deterministic ties by key.
- **Digest is opt-in** (`notify: {digest: true}`); the default stays one event per alert. The digest is one event per dataset run; its dedup key hashes the sorted per-alert keys it carries (`details.alert_keys`), so a replay that yields no per-alert events yields no digest.
- **Re-notification.** Transitions gain `reminded` (open alert whose `flagged_periods` grew to a multiple of `remind_after`) and `changed` (relative change of the last value >= `material_change` since the stored open row). Both are inactive unless declared; unchanged open alerts never notify.
- **Noise budget** (`noise: {max_alerts_per_run, fdr}`) applies only to alerts new in this run, never to stored ones: with `fdr`, a new warning-severity trend alert survives only if Benjamini–Hochberg at that level, over the two-sided normal p-values of every trend deviation of the latest period, rejects its series; critical alerts are never filtered by FDR. `max_alerts_per_run` then keeps the highest severity/score alerts. Suppressed counts are reported. `noise` enters the judgment fingerprint only when declared.
- **False positives per rule**: closed actions with resolution `false_positive` over all closed actions, grouped by the `rule_id` of the alert's series, reported in the incident summary.
- Contracts: root import stays light (pure Python, stdlib `math`); declarations without the new keys serialize and fingerprint exactly as before (decision 0002 unaffected, no YAML).

## Alternatives Considered

- Persist incidents in a sixth stability table: rejected, it adds schema, merge keys, views and remote proof for data derivable from existing rows.
- Suppress alerts at the metric-judging layer: rejected, it would hide results; only alert opening is budgeted.

## Open Decisions

- none — every decision above is settled by the proposal and existing contracts.

## Risks

- Grouping changes notification contracts; keep the per-alert mode as default and the digest opt-in.
