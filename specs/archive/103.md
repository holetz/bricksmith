## Problem

`tests/remote/test_model_flow.py:181-183` records a 300-character summary and asserts only that `model_monitoring_results` and `model_monitoring_binnings` exist. A run where every label-based metric is `partial` or `unavailable`, or where alerts, runs and governance/dashboard views are missing, still passes.

Consequence: the only end-to-end remote proof of model monitoring does not prove it measured anything.

Proposal: assert in the remote test that matured periods carry KS/AUC/Gini values, that per-grade calibration rows exist (after spec 102 enables them), and that the runs/alerts tables and the governance views exist and are readable. Run the proof on the Free Edition with an explicit profile; anything Free cannot run is recorded as Unsupported with its reason.

## Proposal

- The remote model flow proof asserts that matured periods carry non-null KS, AUC and Gini values in `model_monitoring_results`, not only that the table exists.
- It asserts per-grade calibration rows (`grade_oe`, Jeffreys and binomial p-values) for each declared grade A–D, and the grade order metric, with values.
- It asserts the runs table holds a finished run for the model and that the alerts table is readable.
- It creates the dashboard and governance views through `view_statements` and asserts the views the guide names (`latest`, `model_status`, `open_alerts`, `coverage`, `response_summary`) are readable.
- A capability the workspace refuses stays recorded as Unsupported with its reason, never a silent pass.

## Out of Scope

- Estimating performance before labels mature: ruled out by the round guidance, it goes to the human's epic.
- Corporate-workspace execution: the proof runs on the Free Edition with an explicit profile; anything only corporate is recorded Unsupported.
- Changing monitoring behavior or the example declaration (spec 102 owns it).

## Design

- Rule: the proof reads the persisted tables and views, so it proves the example measured something end to end; assertions name the metric and require a non-null value, never only a row count.
- Matured periods are those whose label lag has passed (`label_lag: 3`); the test asserts at least one such period carries each label-based metric value, and does not assert on the immature tail.
- Views are created with `view_statements(f"{catalog}.{test_schema}")`, the same call as `tests/remote/test_model_monitoring.py`.
- Free-first: explicit profile, `.env` copied from the main checkout for the remote run; Scala kernel engine through `auto` with the fallback reason already recorded by the existing stage lines.
- Synthetic data only (decision 0010); nothing organization-specific.

### Assumptions

- Scores carry the label for every sample, so some periods are matured (assertions section Proposal).

## Alternatives Considered

- Assert only that the tables exist (status quo): rejected, a run with every metric unavailable still passes.
- A separate remote test for the views: rejected, it would rerun the whole flow for a handful of reads.

## Open Decisions

- none — the metric names and views are fixed by `monitor/model/config.py` and `tables.py`.

## Risks

- The Free Edition may leave a label metric unavailable at the example's size: mitigated by running the proof and recording any such outcome with its reason instead of loosening silently.
- Views created in the test schema: the schema fixture verifies teardown.
