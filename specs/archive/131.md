## Problem

Reproduced by the epic 125 correctness review (autopilot 2026-11-24, round 5) on origin/main 393db9e, edge of spec 123 (PR #77). The model open-alerts filter treats any results row of a finished run as coverage of the alert's monitoring period (`src/bricksmith/monitor/model/tables.py:194`), and `FINISHED = (SUCCESS, PARTIAL)` (`tables.py:37`). A PARTIAL rerun whose family errored at that period stores an error row, no alert, and the still-red alert disappears.

Repro (synthetic sqlite, SCHEMAS + `view_statements`): r0 success, psi red at 2025-05, alert L stored; r1 partial, psi at 2025-05 an error row, no alert → `SELECT ... FROM model_monitoring_open_alerts` → `OPEN []`.

Consequence: a failed measurement silently clears a red alert from `open_alerts`, `open_alerts_by_severity` and `alert_recurrence`, contrary to the docstring and `docs/how-to/model-monitoring.md`, which say the alert clears because the rerun no longer raised it.

Done when: only a rerun that actually measured the alert's metric (non-error result row) at that period clears it; an error row keeps the alert open; regression test for the partial case; docstring and how-to state the rule; spec 117 and 123 tests still pass.

## Proposal

The model open-alerts filter clears an alert only when a newer finished run measured the alert's metric at that monitoring period: a non-error result row for the same model version, period, metric, segment and column. An error row, or no row for the metric, keeps the alert open. The spec 117 rule (a rerun that measured and raised no alert clears it) stays.

## Out of Scope

Changing how runs write error rows, alert replay, and the stability alerts.

## Impact

`src/bricksmith/monitor/model/tables.py` (`_latest_alerts`, which feeds `open_alerts`, `open_alerts_by_severity` and `alert_recurrence`), its tests and `docs/how-to/model-monitoring.md`.

## Validation

Regression tests on synthetic sqlite: errored rerun keeps the alert, a rerun without the metric keeps it, a measured green rerun clears it; spec 117 and 123 tests pass.

## Design

In the NOT EXISTS subquery, the covering result row must match the alert's metric, and its segment and column when the alert carries them, and its reason must not start with `error:` (the marker `engine.py` writes). Owner decision (epic 132): follow it, not re-decided.

## Alternatives Considered

Treating any non-error row of the period as coverage was rejected: it would clear an alert whose own metric was never measured.

## Open Decisions

None; decided by the owner in epic 132.

## Risks

Alerts with a NULL segment or column (older rows) match on metric only; real alerts always carry both.
