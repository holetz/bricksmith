## Problem

1. `src/bricksmith/monitor/stability/hook.py:128-129` filters the stored rows only by `dataset` and then `collect()`s every binning version and every period; version and window filtering happen afterwards in Python (`engine.py:283`), and alerts and runs are read the same way (`engine.py:291,303`). `docs/how-to/stability.md:221` claims only the window's profiles are collected. Consequence: driver memory grows without bound with history and binning versions, until it fails.
2. `docs/how-to/stability.md:223-224` says a new binning version's history starts at the next run, but `_active_binning` fits it (`engine.py:184-198`) and `_plan_periods` profiles every loaded period without a stored profile (`engine.py:226-227`), so the whole window is profiled and judged in the same run. Consequence: users expect a quiet first run and the gate can fail immediately.

Proposal: push the version/period/open-state filters into `Store.rows` (so the read is bounded by the window), and correct the guide to state the real behavior (code unchanged for item 2 unless the guide's behavior is chosen; record the choice).

## Proposal

Push the version, period and alert-state filters into `Store.rows` so the stored read is bounded by the window (the active binning version's profiles for the window and its baseline history, open and closed alerts, the active version's runs). Item 2 is resolved by correcting the guide: a new binning version profiles and judges the whole window in its first run, so the guide stops promising a quiet first run. Code behavior for item 2 is unchanged.

## Out of Scope

- Reading only the latest run row or bounding the binnings table (small rows, one per version).
- A quiet first run for a new binning version (decided against; see Design).
- Notification delivery (spec 74).

## Impact

- `src/bricksmith/monitor/stability/engine.py` (`Store` protocol, `MemoryStore`, `check`, period planning), `src/bricksmith/monitor/stability/hook.py` (`_IOStore` Spark and in-memory reads), `docs/how-to/stability.md`, `tests/unit/monitor/stability/test_stability_metrics.py`.
- `Store.rows` gains keyword filters `version`, `periods`, `states`; a custom `Store` must accept them. No table schema change and no result change.

## Validation

- Synthetic unit test with a spying store: an older version's rows and the wider history are never returned; the filters are exactly the active version, the window plus baseline periods, and the open and closed states.
- Synthetic unit test: a refit version profiles and judges both periods of the window in its first run.
- `uv run pytest tests/unit/monitor/stability`, `uv run ruff check`, `uv run pyright`. No remote proof: the filters are plain column predicates over the same tables, with synthetic offline tests (Free-first, decision 0010).

## Design

- `Store.rows(kind, dataset, *, version=None, periods=None, states=None)`; `None` keeps every row. `MemoryStore` filters in Python; `_IOStore` on Spark adds `where` predicates before `collect()`, and on in-memory I/O reuses `MemoryStore`.
- `_loaded_periods` extracts the window-plus-history set from `_plan_periods`, so the profile read asks for exactly the periods a run can use.
- Alerts are read with `states=(open, closed)`, the only states `alerts()` adoption and `_superseded` consume; previous-version alerts stay visible so they are still superseded.
- Item 2 decision: correct the guide; a quiet first run would hide drift already in the window.

## Alternatives Considered

- Make a new version's history start at the next run (skip judging old periods): rejected, it hides existing drift and changes tested behavior.
- Read only a `period >= min` range: rejected, fixed baselines load non-contiguous baseline periods.
