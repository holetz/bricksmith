## Problem

Credit-style features are aggregates of an entity's recent closings (last 3, 6, 12 periods): sums, means, extremes, dispersion, trends, runs and recency. A common approach packs all features and lags into one positional float array and runs a row-at-a-time UDF (or drops to Scala for speed); output columns are unnamed, single precision, recomputed per window, and several statistics are wrong (non-absolute sum of differences, skewness/kurtosis using a stale term, an "R²" that is SSE/SST, tercile splits dividing by zero on short windows, percentiles indexing past the end). bricksmith has no feature-engineering module.

## Proposal

- `bricksmith.features` (new module): a declarative spec of source columns × windows (in periods, cumulative from the current closing) × aggregates → named, typed output columns (`<column>_<aggregate>_<window>p`), plus cross-column ratios/differences and categorical pivots/counts.
- A documented aggregate catalog covering at least: count non-null, null runs (trailing and longest), count positive, sum, mean (non-null and with nulls as zero), min, max, range, percentiles, mode and its count, distinct count, increments/decrements (counts, current and longest runs), last-minus-first and its per-step mean, absolute variation, tercile means and differences, variance/stdev (population and sample), coefficient of variation, RMS, OLS slope/intercept/R²/residual stdev and distance of the last value from the trend, skewness, kurtosis, periods since last positive/max. Each aggregate defines its null semantics and minimum points, returning null below it.
- Input contract: a long table (entity keys, closing date, values) with the lag derived as periods between closings; rows after the target closing are refused (point-in-time). Output: one row per entity and closing, ready for a feature table (the feature store spec).
- Engines: a pure numpy reference (the oracle for golden tests); native Spark (default) generating expressions from the spec with a single WindowSpec per entity ordering and closed-form slopes; an Arrow engine (`applyInArrow`/`mapInArrow` where the runtime has them, else `applyInPandas`) over numpy 2-D blocks for the sequence statistics Spark cannot express cheaply.
- A benchmark harness (synthetic data, configurable entities × closings × columns) that records wall time per engine and aggregate family in a reproducible report; the default engine per aggregate family is chosen from the measurement and recorded in the guide. pyarrow is declared in the extra that needs it, never in the root import.
- Parity tests: every engine equals the numpy reference within tolerance on synthetic data, including nulls, short histories and constant series.

## Out of Scope

- Event-level (sub-period) windows; the source is already one row per entity and closing.
- Automatic feature discovery (deep feature synthesis).

## Design

### Assumptions

- The period unit of a closing history is the calendar month by default; `quarter`, `week` and `day` are also accepted. Lag = whole periods between the target closing and a row's closing (Proposal, Design §Input contract).
- Missing closings inside a window are nulls at their lag, never compressed away (Design §Input contract).
- numpy is a hard requirement of the reference and Arrow engines only; the spec, catalog and native Spark engine need neither numpy nor pyarrow at import (AGENTS.md lightweight imports; Impact `pyproject.toml`).

### Module shape

- `bricksmith.features` is a new package of the one library. `spec.py`, `catalog.py`, `history.py`, `errors.py` are pure Python; `reference.py`/`engine.py` import numpy lazily; `spark.py` imports pyspark lazily (pattern: `src/bricksmith/monitor/stability/spark.py` `_f()`); `arrow.py` imports pyarrow lazily. Importing `bricksmith.features` loads none of numpy, pyarrow, pandas, pyspark.
- Errors subclass the library error base with stable `code`s (`feature_spec`, `point_in_time`, `unsupported_aggregate`).

### Declarative spec and naming

- `FeatureSpec(keys, closing, windows=…, columns=[WindowFeature(columns, windows, aggregates)], ratios=[…], differences=[…], categorical=[CategoricalCount(column, categories, windows)], period="month")`; also built from a plain dict (`parse_spec`) so a task can declare it as a literal.
- Window = number of periods counted from the current closing inclusive (window 3 = lags 0,1,2).
- Output names: `<column>_<aggregate>_<window>p` (e.g. `balance_mean_6p`), lower snake case, validated unique; ratios/differences carry their declared name; categorical counts `<column>_count_<category>_<window>p`, with categories sanitized to identifiers and collisions refused.
- Output types: count-like aggregates are 64-bit integers, everything else double precision (never single precision).
- Ratios and differences are computed over already-named output features or source columns at the current closing; a ratio is null when the denominator is null or zero.

### Aggregate catalog and semantics (binding for every engine)

Per window the engine sees `v[k]`, k = 0 (current closing) … w−1; nulls are missing; n = non-null count; chronological position t = w−1−k (oldest = 0). A "step" is a pair of chronologically adjacent positions both non-null (a null breaks it). Each aggregate returns null below its minimum points.

| Family | Aggregates (min points) |
| --- | --- |
| `basic` | `count` (never null), `count_positive` (never null), `sum`, `mean`, `mean_zero` (sum/w, nulls as zero; null when n=0), `min`, `max`, `range`, `last` (= v[0]) — n≥1 |
| `distribution` | `p<q>` percentiles q∈1..99, linear interpolation over non-null values (index always inside the sorted values); `mode` (most frequent, ties → smallest value), `mode_count`; `distinct` (never null) — n≥1 |
| `sequence` | `null_run_trailing`, `null_run_max` (never null); `increments`, `decrements` (counts of rising/falling steps, never null); `increment_run_current`, `decrement_run_current`, `increment_run_max`, `decrement_run_max` (in steps, never null); `delta` (newest non-null − oldest non-null) and `delta_mean` (delta / periods between them) n≥2; `abs_variation` (Σ |step differences|, at least one step); `since_positive` (periods since the latest positive value, null when none); `since_max` (periods since the latest occurrence of the max) n≥1 |
| `terciles` | positions split chronologically into three parts (`numpy.array_split` sizes, oldest first); `tercile_old_mean`, `tercile_mid_mean`, `tercile_new_mean` (null when the part is empty of values), `tercile_diff` (new − old); all null when w<3 |
| `moments` | `var_pop` n≥1, `var_samp` n≥2, `std_pop`, `std_samp`, `cv` (std_samp/|mean|, null when mean=0) n≥2, `rms` n≥1, `skew` (m3/m2^1.5 about the window's own mean) n≥3, `kurtosis` (m4/m2² − 3) n≥4; skew/kurtosis null when m2=0 |
| `trend` | OLS of value on t over non-null points: `slope`, `intercept` (at t=0) n≥2; `r2` = 1 − SSE/SST, null when SST=0; `resid_std` = √(SSE/(n−2)) n≥3; `trend_distance` = v[0] − (intercept + slope·(w−1)), null when v[0] is null |

### Input contract (point-in-time)

- A long table: entity keys, a closing date (DATE), value columns. The lag is derived as whole periods between the target closing and the row's closing; duplicate (keys, closing) rows are refused.
- Output: one row per entity and target closing; targets default to every closing present for that entity, or an explicit `as_of` closing. With `as_of`, any input row after it is refused (`point_in_time`), never silently dropped.

### Engines

- **numpy reference** (`reference.py`): operates on a 2-D block `(rows × w)` of float64 with NaN for null, vectorized per aggregate; it is the oracle of every golden and parity test. `engine.compute_rows(rows, spec)` wraps it over long Python rows.
- **native Spark** (`spark.py`): one `Window.partitionBy(keys).orderBy(period_index).rangeBetween(-(W−1), 0)` per spec (W = largest window) collecting `(period_index, values…)`; a positional array per column is rebuilt with higher-order functions so gaps become nulls; every aggregate is a generated Spark SQL expression (`aggregate`, `filter`, `transform`, `array_sort`, closed-form OLS from sums), no Python UDF. Aggregates it cannot express are refused `unsupported_aggregate` with the Arrow engine named.
- **Arrow engine** (`arrow.py`): `groupBy(keys).applyInArrow` where the runtime has it (pyspark ≥ 4.0), else `applyInPandas`; each group becomes numpy blocks and runs the reference, so parity is by construction and the engine is measured, not assumed (epic 85 Design, 2026-11-23).
- **Dispatch** (`engines.py`): `compute_spark(df, spec, engine="auto"|"spark"|"arrow")`; `auto` routes each aggregate family to `DEFAULT_ENGINES[family]` and joins the family outputs on keys and closing. `DEFAULT_ENGINES` starts at `spark` for every family Spark supports and is set from the recorded benchmark (task 4.2).

### Benchmark

- `benchmark.py`: seeded synthetic long table (entities × closings × columns, with nulls), `run_benchmark(spark_or_none, sizes, engines, families)` timing each engine × family (count-forced materialization, warm-up excluded), and `render_report` producing a markdown table with sizes, seed, versions and wall times. `scripts/features_benchmark.py` runs it against the selected context only (free first, never switching after a failure).

- AGENTS.md: English, nothing organization-specific, lightweight imports, extras within the one distribution, free-first tests, docs through the OKF bundle.
- Decision 0010 and epic 85 Design (private-source rule): synthetic data only; no vocabulary of any reference implementation.

## Alternatives Considered

- **Positional float array + row-at-a-time UDF (status quo approach)** — rejected: unnamed single-precision outputs, recomputation per window and per-row Python overhead; the known statistical bugs live there.
- **Scala/JVM UDF for speed** — rejected: a second language and build in a Python library, not installable as a wheel extra, and Spark SQL higher-order functions already run in the JVM.
- **Arrow engine only** — rejected as the sole engine: measured, not assumed; it keeps parity by reusing the reference but pays serialization per group. Kept as an engine; the default per family follows the benchmark.
- **Databricks Feature Engineering time-series aggregations** — rejected as a dependency: closings are exact dates, not approximate event time (epic 85 Design, feature store bullet).

## Open Decisions

- Default engine per aggregate family — decided by the recorded benchmark on the free environment (task 4.2), written into `DEFAULT_ENGINES` and the guide.
- Whether the Arrow path uses `applyInArrow` on the free environment's runtime — decided at runtime by capability detection; the evidence page records which path ran.

## Risks

- Generated Spark expressions for many columns × windows × aggregates may produce very large plans — mitigation: one shared window and positional arrays per column; the benchmark includes a wide case; the guide states the limits observed.
- Floating-point differences between engines (summation order) — mitigation: parity tolerance 1e-9 relative, golden values on exact vectors.
- Free Edition timings are noisy and quota-bound — ACCEPTED: the report records sizes, seed and versions so it is reproducible and relative, not absolute.
- Spark percentile/mode semantics diverging from numpy — mitigation: the catalog fixes interpolation and tie rules; parity tests cover ties and short series.
