## Problem

Windowed features over long periodic tables (spec 77) are computed today by one generated Spark expression per aggregate, window and column over a shared window. A supplementary corporate run (2026-11-24, classic standard-access cluster, DBR 19.x, single 8-vCPU node, synthetic data) measured that this design is far slower than a compiled per-entity array kernel for a wide declared output set:

- 20,000 entities × 10 columns × 12 closings, at one closing: a compiled JVM (Scala) scalar UDF over a per-entity array computed ~1,930 outputs in 3.4 s, plus 1.7 s to build its array input from the long table, against 113.4 s for bricksmith's native engine and 98.2 s for a row-at-a-time Python UDF (about 22× faster than native).
- Arithmetic is not the kernel's bottleneck: double accumulators, products instead of `pow` and a single moment pass changed nothing measurable. Emitting only the declared outputs is the dominant gain: 5–8 outputs cost about 1/2.6 of 1,930. The remainder is scan and job overhead.
- The Arrow engine lost at scale (50,000 × 36 × 10: native Spark 1.2–2.0× faster per family, 2.7× on the whole spec) and was 4.7× slower than native when restricted to one closing.
- Every divergence between bricksmith's reference and the measured array kernel traced to kernel bugs (first sorted value counted twice in variance, regression sums and mode count; stale mean in skewness and kurtosis; SSE/SST named R²; signed sum of differences) or to documented bricksmith definitions (an all-null window counts 0; `delta` is null with one value; `delta_mean` divides by periods, not values; slope, delta and intercept are chronological).

The human decided (2026-11-24) that a JVM array kernel written in Scala is the project's definitive default engine for windowed features, with a fallback to another engine only where strictly necessary.

## Proposal

Add a fourth engine, `jvm`: one compiled Scala kernel, shipped as a JAR inside the bricksmith wheel, that receives each entity's closing-ordered history as one array and returns only the declared window outputs for every requested closing. `engine="auto"` routes every window aggregate family to it. When the kernel cannot be registered or run on the current compute, `auto` falls back to native Spark expressions, and the choice and its reason are logged and stored in the run report. `engine="jvm"` never falls back. Arrow leaves `auto` and stays an explicit option.

```
long table ──► period index ──► groupBy(keys): array_sort(collect_list(struct(p, day, values[])))
                                        │
                                        ▼
                     bricksmith_window_kernel(history, plan, target)   ← one Scala call per entity, top level
                                        │  array<struct<p, day, v: array<double>>>
                                        ▼
               explode ──► closing = date_from_unix_date(day), output i = CAST(v[i] AS DOUBLE|BIGINT)
                                        │
               category counts (native) ┴► join on keys + closing ──► ratios / differences ──► spec order
```

The kernel has a fixed SQL signature. The plan string encodes, per output, the column index, the aggregate and the window. The target is the `as_of` period or null for every closing. One registration therefore serves every spec, so a Unity Catalog function needs no per-spec DDL. Two registration paths are built and measured (session-scoped `registerJavaFunction` after adding the JAR to the session, and a Unity Catalog Scala function over the JAR uploaded to a volume). The faster supported path becomes the default probe order.

## Out of Scope

- Moving category counts, ratios or differences into the kernel: they stay native, as `## Design` says.
- Changing any catalog definition (including `kurtosis`, which stays excess kurtosis): the kernel follows the catalog, and the guide only explains how it differs from positional-array code.
- Removing the Arrow engine or its tests: it stays available with `engine="arrow"` and `engines=`.
- Corporate proofs (both registration paths on classic standard access, cold start, S/M benchmark against native): they go to the human's private validation plan.
- Publishing the wheel to a package index, or a separate JAR artifact: the JAR travels only inside the wheel (decision 0009).
- Spec 84's example and guide: spec 84 consumes the engine `auto` resolves to.

## Design

- 2026-11-24 — **Default engine.** A Scala kernel becomes the default for every window aggregate family under `engine="auto"`. It runs one compiled pass per entity over that entity's closing-ordered history and emits only the outputs the spec declares. Native Spark expressions are the fallback, used only when the kernel cannot be registered or run on the current compute. The fallback is never silent: the chosen engine and the reason go to the run record and the log, and `engine="jvm"` asked explicitly fails instead of falling back. The numpy reference stays the oracle (1e-9 relative). The Arrow engine is no longer routed by `auto` and is kept only as an explicit, benchmarked option. Record decision 0019, which supersedes the default-engine clauses of 0014.
- 2026-11-24 — **Independent implementation (decision 0010).** Implement the kernel from bricksmith's own catalog definitions and golden tests. Do not translate, copy or adapt any external array kernel, including the measured one and its optimised variant, or its slot layout. The measurements in `## Problem` are behaviour evidence only.
- 2026-11-24 — **Delivery: how a Python library runs JVM code.** Source lives in one sbt project inside the repository: Scala 2.13.16, JDK 17, Spark dependency `provided`, no third-party runtime dependencies. CI builds the JAR, and the JAR ships as package data in the single bricksmith wheel (one library, decision 0009). Python never needs a JVM locally except to run the JVM unit tests. Two registration paths are measured, and the faster one that is supported becomes the default:
  1. a **Unity Catalog Scala function**: `CREATE FUNCTION … LANGUAGE SCALA ENVIRONMENT (java_dependencies = '["/Volumes/…/bricksmith-<version>-<sha>.jar"]', environment_version = '4') HANDLER '…'`. Docs (docs.databricks.com/udf/scala-java-uc, 2026-11-06) list serverless notebooks and jobs, classic compute on DBR 18.2+ and SQL warehouses as supported. It runs in a sandbox with a per-session cold start, which must be measured.
  2. a **session-scoped JVM function**: the JAR is added to the Spark Connect session and registered with `spark.udf.registerJavaFunction` (classic standard access on DBR 18 LTS+, serverless JAR jobs). Classic standard access needs the JAR's volume path on the metastore allowlist, an admin action that the guide documents.
  A helper uploads the packaged JAR to a configured volume, named by version and content hash, and creates or replaces the function idempotently. It is callable from a bundle task and from the CLI. Capability detection probes once per session and caches the result.
- 2026-11-24 — **Kernel contract.** Input: per entity, a closing-ordered array of structs (closing plus the declared numeric columns), built once with `collect_list` + `array_sort` and grouped by the entity keys. Output: an array of rows, one per requested closing (every closing, or only `as_of`), each holding the declared outputs in spec order. The array is exploded and aliased back to the spec's output names in Python. Null semantics, chronological slope/delta/intercept, period-based `delta_mean`, ANSI-safe division and the five known positional-array mistakes follow the catalog exactly. Category counts, ratios and differences stay as they are today, computed natively after the kernel. Scala UDFs cannot run inside higher-order functions (platform limit), so the kernel is called at the top level.
- 2026-11-24 — **Proof.** Unit level: a Scala test suite runs the shared golden vectors from a language-neutral fixture file that Python also reads, so both sides pin the same numbers. A local Spark session runs JVM/numpy parity in CI with a JDK. Free Edition: try the Unity Catalog function on serverless. If the free tier refuses it (as it refuses Python UDF sandboxes), record **Unsupported** with the exact error and prove that the fallback runs and is recorded. The corporate proof (both registration paths, cold start, benchmark at S and M against native, as_of and all closings) goes to the private validation plan, owned by the human.
- 2026-11-24 — **Migration semantics.** The guide states the definitions that a user coming from a positional-array kernel will see differ: all-null window count 0, `delta` null below two values, `delta_mean` over periods, chronological slope, `kurtosis` non-excess. The five minimal synthetic entities from the corporate correctness run become golden cases: `[3,2,1]`, `[4,null,1]`, `[5,null,null]`, `[null,null,null]`, and a 1-based lag index.
- 2026-11-24 — **Kernel signature (develop, autonomous).** One fixed SQL signature: `kernel(history ARRAY<STRUCT<p INT, d INT, v ARRAY<DOUBLE>>>, plan STRING, target INT) → ARRAY<STRUCT<p INT, d INT, v ARRAY<DOUBLE>>>`. `p` is the period index (`PERIOD_SQL`) and `d` is the closing as `unix_date`, so no date objects cross the boundary. The plan lists the outputs as `column-index:aggregate:window`, and `target` is the `as_of` period, or null for every closing. Evidence: `src/bricksmith/features/spark.py` already derives the period index in SQL, and a fixed signature is what a Unity Catalog function needs.
- 2026-11-24 — CI change (kernel job: JDK 17 + sbt, JAR artifact handed to the checks job, `verify_dist --require-kernel`) is within the Delivery bullet above and the epic 85 autonomy policy; no separate human approval was given.

## Alternatives Considered

| Approach | Cost | Buys | Forecloses |
|---|---|---|---|
| **Scala array kernel, fixed signature, plan string (chosen)** | sbt project, JAR in wheel, JVM test lane in CI | one registration for every spec; UC function possible; compiled speed | per-spec specialised code generation |
| Per-spec registered return type (struct with named fields) | one registration per spec; UC DDL per spec | named struct fields straight from the UDF | a single UC function for all specs |
| Spark Catalyst native expression (custom `Expression` with codegen) | internal APIs that change across DBR releases; no UC path | fastest possible | standard access and serverless (internal APIs are not allowed) |
| Keep native expressions, only emit fewer intermediates | small | some speed | the measured 22× gap stays; the human decided for the JVM kernel |

## Risks

- **Free Edition refuses both registration paths** (as it refuses Python UDF sandboxes). Mitigation: the remote test records Unsupported with the exact error and proves the recorded fallback. The corporate plan carries the positive proof.
- **Java UDF type conversion of nested arrays differs between Spark versions** (`Seq` vs `ArraySeq`, boxed nulls). Mitigation: the kernel reads through `Row`/`scala.collection.Seq` interfaces only, and local Spark 4.0.1 parity tests pin it.
- **Silent divergence from the oracle** on edge cases (all-null windows, single values, constant series). Mitigation: shared golden fixtures run in both languages, plus 1e-9 parity over the whole catalog.
- **CI time and flakiness from sbt and a local Spark JVM lane.** Mitigation: a separate CI job with a cache. The Python `checks` job only needs the JAR artifact.
- **A wheel built without sbt has no JAR.** Mitigation: `auto` falls back with the reason "kernel JAR not packaged", and `verify_dist` fails CI when the JAR is missing from a CI-built wheel.
