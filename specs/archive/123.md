## Problem

Regression from spec 117 (PR #72), reproduced by the epic 121 correctness review on 3d125c7. `_latest_alerts` (`src/bricksmith/monitor/model/tables.py:173-190`, used by `alert_recurrence` at `:309` and `open_alerts` at `:354`) keeps each alert_id's newest stored row. A light alert's id includes the monitoring period (`src/bricksmith/monitor/model/engine.py:973-974`), and `alert_rows` writes a row only while the light is red or yellow (`engine.py:970-971`), never a closing row; the same holds for a persistence/trend span a rerun no longer opens.

Reproduction (synthetic sqlite, tables from SCHEMAS, `view_statements("main")`): finished run r0 (2025-06-01) stores light alerts L (psi) and M (auc) for 2025-05; finished run r1 (2025-06-02) reruns 2025-05 and stores only M (psi green). `SELECT alert_id, run_id FROM main.model_monitoring_open_alerts` → at 3d125c7 `[('L','r0'), ('M','r1')]`; at e2716ad `[('M','r1')]`.

Consequence: after a corrected-data rerun or a replay with relaxed limits, a cleared alert stays in `open_alerts`, `open_alerts_by_severity` and `alert_recurrence` forever. The docstring at `tables.py:327-329` still describes the old rule and disagrees with `docs/how-to/model-monitoring.md:313`.

Done when: an alert absent from a newer finished run that covered its period (rerun) is no longer open in the views, while spec 117's fix (a span moved to a newer period listed once, in its latest state) still holds; regression tests cover both repros; docstring and how-to agree.

## Proposal

- An alert is open in the model views (`open_alerts`, `open_alerts_by_severity`, `alert_recurrence`) only if the newest finished run covering its monitoring period still stored it.
- A light alert or span that a rerun or replay of its period stops raising (corrected data, relaxed limits) leaves those views.
- Spec 117's rule holds: a span moved to a newer period is listed once, in its latest state, and a span a later run closed stays closed.
- The `view_statements` docstring and `docs/how-to/model-monitoring.md` state the same rule.

## Out of Scope

- Writing closing rows for alerts a rerun no longer raises: the views derive the clearing, the stored tables stay append-only per run.
- Changing `alert_response` (first seen, first action, closure times): it reports history, not what is open.
- Estimating coverage by the run record's `periods` or `latest_period`: results rows are the evidence of coverage.

- `uv run ruff check && uv run pyright` pass.

## Design

- **Coverage is stored results.** A finished run covers a monitoring period of a model version when it stored result rows for it. An alert row is dropped from `_latest_alerts` when a finished run newer than the run that stored the alert's latest row (by `finished_at`) covers that period and did not store the alert id (the latest row per id is the one already picked, so a newer storing run would have been picked instead). Failed and unfinished runs never count. Alternatives: the run record's period columns (carry only a count and the latest period), closing rows written by the engine (changes the write contract).
- 2026-11-25 owner decision (epic 125): an alert is open in the model views only if the newest finished run covering its monitoring period still stored it; spec 117's latest-state-per-span rule stays; docstring and how-to state the same rule.
- Applying the filter inside `_latest_alerts` serves `open_alerts`, `open_alerts_by_severity` and `alert_recurrence` with one rule.

## Alternatives Considered

- Filter only `open_alerts`: leaves a cleared alert counted in `alert_recurrence`, which the Problem names.

## Open Decisions

- none — the owner decision in epic 125 fixes the rule.

## Risks

- A row stored with no result rows for its period (hand-built data) is never dropped: ACCEPTED — runs always store results beside alerts.
- A correlated NOT EXISTS per alert row costs on large tables: ACCEPTED — alert tables are small; the filter reads one key.

## Outcome

An alert is now open in the model views only if the newest finished run covering its monitoring period (stored result rows for that model version and period) still stored it. `_latest_alerts` in `src/bricksmith/monitor/model/tables.py` drops a row when a newer finished run covered its period without storing it, so `open_alerts`, `open_alerts_by_severity` and `alert_recurrence` stop listing a light alert or span a rerun cleared.
