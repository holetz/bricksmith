## Problem

Specs 148 and 150 (epic 139) shipped Spark code paths that never ran: the build host has no pyspark, so `missing_column` handling in the Spark profile and the Spark scan of the duplicate-key, distinct-count, vanished-category and quantile metrics (`_scan_spark`) are covered only by pure-engine tests. Parity between the engines is asserted for every earlier stability metric, so a divergence here would silently give different results per engine. Spec 122 (run the local-pyspark parity tests in the gate) is the enabling change.

## Proposal

- Add pure-vs-Spark parity tests for `missing_column`, `schema_change` and every new profile metric of spec 150, on the same synthetic fixtures.
- Run them with local pyspark (spec 122) and in the remote Free Edition proof.

## Out of Scope

- The remote Free Edition proof. No free profile exists on this machine (epic 161 decision "#157 waits for #122 and #160"); recorded as not run, never faked and never run on `DEFAULT`.
- Changing the approximate-distinct design of `_scan_spark`; only its documented error is asserted.
- Parity of metrics that earlier specs already cover.

## Impact

### Product code this spec expects to touch

- `src/bricksmith/monitor/stability/spark.py` — only if a parity test finds a divergence
- `tests/unit/monitor/stability/test_stability_spark_parity.py` — new pure-vs-Spark parity tests of `check`
- `scripts/local_spark_check.py` — run the new file in the local-Spark gate
- `docs/project/databricks-tests.md` — list the new parity file and the remote proof as not run

## Validation

- `uv run pytest tests/unit/monitor -q` still passes (the new file skips without local pyspark).
- `uv run ruff check && uv run ruff format --check && uv run pyright` are clean.
- The remote Free Edition proof is recorded as not run.

## Design

- **Same fixtures, two engines.** One synthetic table is run through `check` as rows and as a local Spark DataFrame, each with its own `MemoryStore`; the results, profiles and alerts are compared by key. Values compare with a tolerance and exact scan counts are exact at this cardinality.
- **Cases.** `missing_column` and `schema_change` (a dropped and an added column, extend and freeze), the duplicate-key and distinct-count scan rows, `vanished_rate`, `js_distance`, the quantile metrics and `wasserstein`, per the shape metrics of spec 150.
- **Approximation.** `approx_count_distinct` is compared exactly on the small fixture, where HLL++ is exact; the test comment names the 5% bound for larger data.
- **Gate.** The file is appended to `TESTS` in `scripts/local_spark_check.py` so the gate fails if it is skipped. It uses the existing `local_spark` fixture.

### Assumptions

- The fixture's cardinality (tens of values) keeps `approx_count_distinct` exact — supports the scan comparison.

## Alternatives Considered

- Assert only within a percentage for every metric: rejected; exact where the engines are exact catches real divergence.
- Test `_scan_spark` directly: rejected; going through `check` also covers the missing-column binning and schema paths.

## Open Decisions

- none — the epic decision settles that parity is proved locally only.

## Risks

- A real divergence is found: the fix goes into `spark.py` in the same task, with the failing test kept as proof.
- Java 17 is absent on the host: a local Temurin 17 from the session scratchpad runs the gate; CI already runs it.

## Discoveries

- decision: key/distinct scans compared within a tolerance, not exactly — approx_count_distinct is not exact even at ~100 distinct values (duplicate_key_rate 0.042 Spark vs 0.092 pure on a 9% duplicate month); documented behaviour of _scan_spark, so no code change
- Spark duplicate_key_rate error is up to ~5% of the distinct count in absolute terms, large against small true rates; a future spec could use exact counts when rows are few
- decision: remote Free Edition proof NOT run — no free profile exists (epic 161 decision); local pyspark 4.0.1 under Temurin 17 only

## Outcome

Shipped `tests/unit/monitor/stability/test_stability_spark_parity.py`: `check` runs on rows and on a local Spark DataFrame and the second-run results agree on `schema_change`, `missing_column` (dropped column), an added column (frozen and extended), the vanished-category, JS-distance, quantile-shift and Wasserstein shape metrics and the duplicate-key and distinct scans. The file is part of `scripts/local_spark_check.py`, so the local-Spark gate fails if it is skipped; `docs/project/databricks-tests.md` documents it. No product divergence was found: the Spark path of `missing_column`, `schema_change` and the shape metrics equals the pure engine exactly.

The key and distinct scans use `approx_count_distinct`, which is not exact even near 100 distinct values (a 9% duplicate month read 4% on Spark), so they are compared within a tolerance. Left out: the remote Free Edition proof — NOT run, no free profile exists on the build host. Local proof used pyspark 4.0.1 under Temurin 17.
