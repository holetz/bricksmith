## Problem

Found by the correctness review of epic 98 (2026-11-24), reproduced on main e564870.

Setup: MemoryStore, one new month per run, `max_periods=3`, fixed baseline 2026-01..04, months 05–07 drifted, 08–12 stable, persistence defaults `red=2`, `close_after=3`, rows merged after each run. Observed alert rows (alert, state, closed, last):

```
2026-06 [('2026-06', 'open', '', '2026-06')] ['opened']
2026-08 [('2026-06', 'open', '', '2026-08')] []
2026-09 [('2026-06', 'superseded', '', '2026-08')] []
2026-12 [('2026-06', 'superseded', '', '2026-08')] []
```

In the 2026-09 run the window is 07 (red), 08, 09 (green): one red is below `red=2`, so the replay builds no span, the stored open alert has nothing to attach to (carry exists only through `enumerate(alert_spans(...))` with number 0, `src/bricksmith/monitor/stability/metrics.py:464-466`), and `_superseded` (`src/bricksmith/monitor/stability/engine.py:290-297`) marks it superseded. Expected: stay open (two greens < `close_after=3`) and close at 2026-10.

Consequence: a real drift episode ends `superseded` with no `closed_period`, disappears from open and closed alert reads, a later re-opening cannot be flagged as a recurrence, and spec 74's notifier never sends the close. The test `test_open_alert_keeps_its_identity_when_its_opening_leaves_the_window` drifts every period and misses this case. Also covers the spec 99 follow-up noted by its runner (a stored open alert whose metric turns all green across the window closes as superseded).

Proposal: carry a stored open alert forward independently of whether the window re-triggers it, apply `close_after` to its trailing greens, and add the synthetic sequence above as a regression test (pure engine; Spark parity unaffected).

## Proposal

- A stored `open` stability alert of the active binning version whose opening period is at or before the start of the window stays `open` across runs whatever the window's statuses are; it is never marked `superseded` because the window alone no longer re-triggers it.
- Such a carried alert closes (`state=closed`, `closed_period` set) once `close_after` consecutive greens are replayed after it, so it appears in closed-alert reads, a later re-opening of the same metric can be flagged as a recurrence, and the close reaches the notifier like any other close.
- The carried alert keeps its `alert_id`, `opened_period`, escalation, recurrence flag and cumulative `flagged_periods`, exactly as the existing carry does when the window re-triggers it.
- The reproduction of `## Problem` (fixed baseline 2026-01..04, drift 2026-05..07, stable 2026-08..12, `max_periods=3`, default persistence) is a regression test: the alert is `open` through 2026-09 and `closed` at 2026-10, and no alert is ever `superseded`.

## Out of Scope

- A stored `closed` alert whose opening leaves the window and is then superseded (recurrence lost across the window) — spec 106, serialized after this one on the same functions.
- Stored alerts of an older binning version: they are still superseded by design (stability guide, versioning).
- A stored open alert whose metric has no judged result at all in the window (column dropped from the declaration): it has no series to carry onto and stays superseded; changing that is a separate decision about removed columns.
- Persisting the trailing green/red streak on the alert row so a carry can resume counters exactly across the window edge (schema change; see `## Alternatives Considered`).
- Model-monitoring alerts (`monitor/model/engine.py`), which use `alert_spans` without a stored carry.

## Design

- **Seed, don't adopt.** `alert_spans(series, policy, *, carry=None)`: when `carry` is an `AlertSpan`, the replay starts with it as the current open span (appended first to the result), counters at zero. Every later status updates it exactly like a span the replay opened itself: escalation on `red` consecutive reds, `close_after` consecutive greens close it, `last_period`/`last_status`/`flagged` advance; after it closes, a new span opening within `recurrence` periods is flagged as a recurrence. Without `carry` the function is unchanged, so model monitoring is unaffected.
- **When the stability replay seeds.** In `metrics.alerts`, a stored `open` alert of the same version and kind whose `opened_period` is at or before the first period of the metric's series is turned into the seed (`opened`, `escalated`, `severity`, `recurrence`, `last_period`, `last_status` from the row; `flagged` empty). A stored open alert that opened inside the window is left to the replay, which reproduces it from its own statuses (today's behaviour). The adoption on span number 0 is then only the seeded span, so the identity, escalation, recurrence and cumulative `flagged_periods` rules stay the existing ones (`flagged_periods` = stored count + flagged periods after the stored `last_period`).
- **Exactness bound.** The replay only sees the window's statuses, so a seeded span counts greens (and reds, for escalation) from the window start. A close or escalation streak no longer than `max_periods` lies wholly inside the window and fires in the same period as an unbounded replay would; a `close_after` (or `red`) larger than `max_periods` can never complete for a carried alert. Documented in the stability guide as a rule: keep `close_after` and `red` at or below `max_periods`.
- **Supersede stays for what the replay truly no longer produces**: another binning version, or a metric with no series in the window. `_superseded` in `engine.py` is not changed: a seeded alert is always in the fresh rows.
- Binding contracts: decision 0010 (synthetic tests, generic contract); the alert identity rule (`alert_id` from dataset, version, key, kind and opening period) is unchanged.

### Assumptions

- The stored row's `last_period`/`last_status` describe the alert as of the previous run, and the window of this run overlaps or follows it — `## Design` (seed fields).

## Alternatives Considered

- **Persist the trailing streak counters on the alert row** (`greens`, `reds`) and resume them exactly: removes the `max_periods` bound but adds columns to a stored table schema and a migration for existing rows; rejected for a correctness fix whose default configuration (`max_periods=36`, `close_after=3`) is inside the bound.
- **Exempt carried alerts from `_superseded` only** (keep them stored as `open` unchanged): stops the supersede but never closes them, so the notifier and recurrence still lose the episode; rejected.
- **Widen the loaded window back to each open alert's opening period**: exact, but makes a run's read cost unbounded by `max_periods` and touches profile planning; rejected.

## Open Decisions

- none — the shape follows the Proposal in `## Problem` and the exactness bound is settled by documenting it (see `## Design`).

## Risks

- A configuration with `close_after` (or `red`) above `max_periods` keeps a carried alert open indefinitely instead of superseding it. ACCEPTED — the defaults are far inside the bound, the guide states the rule, and an open alert is the safer failure than a silently lost episode.
- Escalation of a carried warning needs its run of reds inside the window; a red streak straddling the window start escalates later than an unbounded replay. ACCEPTED — same bound, documented.
- Existing stores already hold episodes marked `superseded` by the old behaviour; they are not revived. ACCEPTED — history rows are not rewritten by a fix.
