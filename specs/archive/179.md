## Problem

Reproduced by the round-5 reviewer on 2026-11-26 (main b7b3f79; unchanged since before #177):

```
redact_text('redis://:S3cretPw@cache.example.com:6379/0') -> 'redis://:S3cretPw@cache.example.com:6379/0'
redact_text('REDIS_URL=redis://:S3cretPw@cache:6379/0')   -> 'REDIS_URL=redis://:S3cretPw@cache:6379/0'
redact_text('rediss://:S3cretPw@cache:6380')              -> 'rediss://:S3cretPw@cache:6380'
```

`src/bricksmith/ops/redact.py:58` (`_URL_USER = re.compile(r"://[^/\s:@]+:")`) needs at least one user character, so `://:` never matches; `REDIS_URL` carries no secret keyword, so the assignment masker misses it too. Consequence: the standard Redis/Celery URL form logs its password in clear — very realistic.

## Proposal

- Accept an empty user in a `scheme://:pw@host` URL token as a credential when an `@` follows in the token, so the password is masked.
- `scheme://:8080`-like text with no `@` stays unchanged.

## Out of Scope

- The `host:port` guard for digit-first passwords (`scheme://u:1234@host`): owned by #180.

## Design

- Rule: `_URL_USER` becomes `://[^/\s:@]*:` so an empty user matches; `_credential_separator` already requires an `@` for a non-port token, and a port-shaped token with no `@` still yields no credential, so `scheme://:8080/x` is unchanged.
- Decision (epic 181 `## Design`): empty user is a credential when an `@` follows in the token.

## Alternatives Considered

- A second regex for the empty-user form: rejected, one pattern with `*` covers both and shares the separator rules.
