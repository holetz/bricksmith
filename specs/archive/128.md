## Problem

Reproduced by the epic 125 correctness review (autopilot 2026-11-24, round 5) on origin/main 393db9e, regression scope of spec 126 (PR #78). After a snapshotted period is deleted from the data, spec 126 zeroes its profile and emits `revision_row_change = -1.0`, but `compute` builds results only for `window`, which never holds the vanished period (`src/bricksmith/monitor/stability/engine.py:517`). The first publication's `row_count` and `volume_change` rows stay in stability results, so `dataset_status` and `latest` (`src/bricksmith/monitor/stability/tables.py:173`) keep showing them.

Repro (synthetic, `_vanish(3, gone, 2)` helper of `tests/unit/monitor/stability/test_stability_revision.py`, 80 rows/month): `GONE 2026-02 row_count rows: [('r1','','',80.0)] volume_change: [('r1',0.0,'green')]`; same for 2026-03 (the latest period), where dataset_status shows red with row_count 80 and green volume_change from r1.

Consequence: spec 126's Problem consequence ("the dashboard keeps the stale count") persists.

Done when: an emptied period's current results report row_count 0 (or no stale count) in `latest` and `dataset_status`, with regression tests for a middle and the latest period.

### Absorbed from spec 129 (autopilot 2026-11-24, round 6)

Reproduced by the epic 125 correctness review (autopilot 2026-11-24, round 5) on origin/main 393db9e, regression from spec 126 (PR #78). With `revision: true`, the zero-count profile written for an emptied period is fed to `compute` with the other profiles (`src/bricksmith/monitor/stability/engine.py:497`, `profiles = ... + fresh + emptied`), and `baseline_periods` uses `history.periods`, so later periods are judged against it.

Repro (3 months × 80 rows, r2 drops 2026-02, refresh_periods 2, revision on vs off): `previous` baseline → 2026-03 `volume_change` `no_data` and `psi` `no_baseline` (off: green 0.0); `rolling` baseline → 2026-03 `volume_change = 1.0` red (off: 0.0 green). The default `fixed` baseline is unaffected.

Consequence: turning revision on changes non-revision metrics; an untouched period gets a false red alert or loses its baseline.

Done when: an emptied period's zero-count profile never serves as a baseline period for other periods under `previous` and `rolling` (or the chosen rule is documented and tested), with regression tests for both baselines; fixed baseline unchanged.

One rule covers both (both fixes change the same `compute(...)` call at `src/bricksmith/monitor/stability/engine.py:497-498` and how `metrics.compute` treats emptied periods; fixing them apart would let one break the other): an emptied period is REPORTED by the revision run (row_count 0, no stale count in `latest` / `dataset_status`) but is NEVER a baseline period for other periods under `previous` and `rolling`; `fixed` unchanged.

## Proposal

With `revision: true`, the revision run computes the full results (row_count 0, volume_change, psi and the other metrics) of an emptied period, so `latest` and `dataset_status` never show the stale first-publication count. The zero-count profile of an emptied period is never a baseline period for another period under the `previous` and `rolling` baselines: they skip it and take the next eligible period. `fixed` and revision off are unchanged.

## Out of Scope

- none — the epic 132 owner decision settles the rule; `fixed` baseline, revision off and spec 126's revision_row_change behavior are untouched.

## Impact

`src/bricksmith/monitor/stability/metrics.py` (`compute`), `src/bricksmith/monitor/stability/engine.py` (the `compute` call), `tests/unit/monitor/stability/test_stability_revision.py` and `docs/how-to/stability.md`. No schema, table or config change.

## Validation

`uv run pytest tests/unit/monitor/stability -q` covers a middle and the latest emptied period (row_count 0 in results), `previous` and `rolling` baselines of the period after an emptied one, `fixed` unchanged, and spec 126's tests. `uv run ruff check`, `uv run ruff format --check` and `uv run pyright` stay green.

## Design

`compute` gains an `emptied` set. Results are built for the window plus the emptied periods. Baseline periods for any period come from the history without emptied periods (for an emptied period itself, the eligible periods before it), so `previous` takes the nearest eligible earlier period and `rolling` the last N eligible ones. The engine passes the vanished periods as `emptied`. `fixed` does not read the periods list and stays as is.

## Alternatives Considered

Dropping the zero profile from `compute`'s input and zeroing only the results: loses the other recomputed metrics and the bin shares written to the profiles table.

## Open Decisions

- none — decided by the owner on 2026-11-25 (epic 132 Design).

## Risks

A skipped emptied period shortens the `rolling` window (fewer than `min_periods` eligible periods gives no baseline for that period, the existing behavior).
