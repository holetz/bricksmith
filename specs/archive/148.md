## Problem

The binning is frozen per configuration fingerprint, which hashes the declared `columns` but not the table
schema (`stability/config.py:253-264`). With `columns: "auto"`, a column added after the first fit is never
profiled (profiling iterates `binning.columns`, `stability/profile.py:316`, `stability/spark.py:252`) and no
signal says so. A dropped column fails the Spark profile at `f.col(...)` (turning the check into an error) and
shows as 100% nulls in the pure engine. A type change is not detected. When the configuration does change, the
new binning version starts every series from zero and supersedes all alerts (`stability/metrics.py:76`,
docs/how-to/stability.md:324-326), although `row_count` and `volume_change` do not depend on bins.

## Proposal

- Store a schema snapshot (column, type, nullable) per run on the binning/run rows; emit table-level
  `schema_change` results and alerts for added, dropped and retyped columns, judged by a configurable gate.
- `auto_columns: freeze | extend` (default `freeze` + alert): with `extend`, new eligible columns are binned in a
  new binning version automatically, with the alert explaining why.
- A dropped monitored column is reported as `missing_column` instead of raising, in both engines.
- Table-level metrics (`row_count`, `volume_change`, `weight_change`) read profiles across binning versions so
  their baseline, trend and alerts survive a refit.

## Out of Scope

- Schema contracts (the governance/registry declarations already own expected schemas).

## Validation

- Adding a column produces a `schema_change` alert; with `extend` the column is profiled from the next run.
- Dropping a monitored column yields `missing_column` in pure and Spark engines with the same rows.
- After a refit, the `row_count` trend continues with the history of the earlier version.

## Design

### Decisions

- **The schema snapshot is a JSON list of `[column, type, nullable]`, sorted by column, in a `schema` STRING column of the
  binnings table (the schema the binning was fitted against) and of the runs table (the schema each run saw).** Both
  tables already evolve their columns on write, so existing tables gain it without a migration. The pure engine reads
  types with `python_type`, Spark reads `df.schema`; only name and type are compared, nullability is recorded.
- **Drift is judged against the active binning's fit schema; the run that fits a new version judges against the schema of
  the binning it replaces.** Without a stored fit schema (tables written before this change) the last run's schema is the
  reference; with neither, nothing is emitted. This keeps a frozen binning alerting while the drift lasts, and makes an
  `extend` refit report exactly what it absorbed.
- **`schema_change` is a table-level metric (column `""`, whole population, latest period of the window)**; its value is
  the number of added, dropped and retyped columns and its `reason` lists them. Defaults `Limits(0, 2, higher)`: one or two
  changed columns are yellow, more are red. It is configurable through `limits` like any metric, and the existing `gate`
  applies. Columns in `exclude` are ignored.
- **`missing_column` is a column-level metric** (value 1 while a monitored column is absent, red by default). A column
  that returned is emitted once more at 0 so the alert closes. Missing columns are removed from the profiling binning
  (`dataclasses.replace` of the `Reference`), so neither engine touches them: the pure engine no longer reports 100%
  nulls and Spark no longer fails on `f.col`. A missing period, weight or segment column still raises, since nothing can be
  judged without it. A table missing every monitored column raises.
- **Schema metrics alert immediately**: their persistence kind replays with `yellow=1, red=1, immediate_red=True`, like the
  trend kind, because a schema change is an event and not a noisy series.
- **`auto_columns: freeze | extend`** (default `freeze`, only with `columns: auto`; `extend` with explicit columns is
  refused). `extend` adds the current non-excluded column names to the binning fingerprint of the run, so a changed column
  set fits a new version from the latest `fit_periods` periods (the earliest ones may predate the new column), unless the
  baseline is a fixed range. It appears in `to_dict` only when `extend`, so existing fingerprints stay.
- **Table-level series continue across versions.** `row_count`, `volume_change` and `weight_change` read, besides the
  active version's profiles, the profiles of earlier binning versions with the same period column (one column's rows each,
  through a new `columns` filter of the store read); a period present in both takes the newer version's rows. Their baselines
  and trend history run over this merged history, and periods that only earlier versions know are judged (not written) so
  the trend and alert replays have them. Table-level alerts get an identity anchored on the first version of the lineage and
  are carried and never superseded across its versions; column-level alerts stay per version.

### Contracts this must not contradict

- Results and alerts are replayable from stored profiles (`metrics.py` module doc); the new reads stay pure.
- `limits` and `to_dict` of declarations that use none of the new keys stay byte-identical (fingerprints, `REVISION_LIMITS`
  precedent): the new default limits live in a separate fallback table.
- Spark and the pure engine produce the same rows (`spark.py` module doc): the schema logic lives in `engine.py` and
  `schema.py`, and only the schema read is engine-specific.

## Alternatives Considered

- **A dedicated `schema` results table or a per-column `schema_change` row per drifted column.** Rejected: one table-level
  result with a readable `reason` keeps the star model unchanged and one alert per drift event.
- **Comparing each run with the previous run only.** Rejected: a frozen binning with a persistently unmonitored new column
  would stop alerting after three runs.
- **Detecting drift through the binning fingerprint (hashing the schema).** Rejected: it would refit on every change and
  remove the `freeze` choice.
- **Storing table-level totals in their own table to survive refits.** Rejected: profiles already hold them, and a second
  source of the same numbers can disagree.

## Discoveries

- decision: schema drift is judged against the binning's fit schema (previous binning's schema on the run that refits, last run's schema for binnings stored before this change) — a frozen binning must keep alerting while an added column stays unmonitored
- decision: schema and table metrics get immediate alerts (yellow=1, red=1, immediate_red) — a schema change is an event, not a noisy series; limits and gate.fail_on stay the configurable gate
- decision: extend refits fit on the latest fit_periods periods (unless the baseline is a fixed range) — the earliest periods may predate the new column
- decision: Spark schema/missing_column parity is proven by engine-independent code plus a stubbed schema_spark test — pyspark is not installed in this environment, so the Spark parity tests were skipped here

## Outcome

Shipped on `plan/148-schema-drift`, reviewed and distilled into `docs/how-to/stability.md`:

- Every run stores the table schema (`schema` on `stability_binnings` and `stability_runs`) and emits a table-level `schema_change` result and alert for added, dropped and retyped columns, judged by configurable limits (default `higher: 0 / 2`) and the existing gate; the alert opens on the first flagged run.
- `auto_columns: freeze | extend` (default `freeze`, `columns: auto` only): `extend` fits a new binning version on the latest `fit_periods` periods when the table's columns or types change.
- A dropped monitored column is reported as `missing_column` (red, closes when the column returns) in both engines instead of raising or profiling nulls; the profile of that run leaves it out.
- `row_count`, `volume_change` and `weight_change` read the totals of earlier binning versions with the same period column, so baseline, trend history and alerts continue after a refit; table-level alerts keep their `alert_id` across versions.

Left out: schema contracts (owned by governance), Spark execution of the new paths (the shared logic is engine-independent and only `schema_spark` is Spark-specific; pyspark is not installed here, so the Spark parity tests were skipped and `schema_spark` is covered by a stub test). One `decision:` line in `## Discoveries` says schema and table metrics alert immediately; only the schema metrics do (`schema_change`, `missing_column`).
