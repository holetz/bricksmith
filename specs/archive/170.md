## Problem

Gap left by #167, reproduced by the round-2 reviewer on 2026-11-26 (main 5a8ed5b; base 48f4a94 identical):

```
redact_text('secrets: [\n  "alpha",\n  it\'s-beta\n]')   -> 'secrets: <redacted>\n  "alpha",\n  it\'s-beta\n]'
redact_text("password: [abc'def,\n ghi]")                 -> 'password: <redacted>\n ghi]'
```

`src/bricksmith/ops/redact.py:159-160`: an apostrophe opens a quote state that never closes, so `_matching_bracket` returns -1 and `:182` falls back to the first line. Consequence: list elements in prose-like or YAML-unquoted values leak. Serialize with the bracket-budget spec filed in the same round (same functions).

## Proposal

- A multi-line bracketed list under a secret key is masked whole when an element carries a lone or word-internal quote character of any kind (`it's`, `abc'def`, `james'`, a lone leading `'`, a lone `"` or backtick such as `say "hi`), exactly as it is when the elements are clean.
- A quote character opens a quoted region in the bracket scan only when it is plausibly a quote: an apostrophe not directly after a letter or digit, and any quote (`'`, `"`, backtick) only with a valid closer somewhere later in the text (for an apostrophe, one not directly followed by a letter or digit). A lone quote is prose, never a string swallowing the rest of the input.
- Ordinary text with quotes (prose `don't`, `2" pipe`, lists with quotes under non-secret keys) is returned byte-for-byte unchanged.
- The new path stays linear in time, proven by wall-clock assertions on inputs of at least 4k and 64k characters for apostrophe, double-quote and backtick worst cases.
## Out of Scope

- Redesigning the bracket scan's budget or the other value shapes (block scalars, URLs): the scan was just rewritten by #169 and only its quote handling changes here.
- Treating a lone quote as an unterminated string that swallows the rest of the text: that is the leak this spec closes.

## Design

- **Rule (durable):** inside a bracketed value the scan treats `'` as a quote only when (a) the previous character is not alphanumeric, (b) a valid closer exists later in the text, and (c) a closer is an apostrophe not directly followed by an alphanumeric; `"` and backtick are unchanged. Apostrophes in contractions and possessives therefore never open a region, and an unmatched leading quote is literal instead of swallowing the rest of the text, so `_matching_bracket` finds the real `]` and the first-line fallback is reached only for genuinely unclosed lists.
- **Linear time:** the last valid closer per quote character is computed once per scan by a backwards `rfind` walk (O(n) total, cached), so the opener test is O(1) and no lookahead is quadratic. #169's rescan budget is untouched.
- **Closing the class (epic 173):** the reviewer's reproductions plus a table of adjacent adversarial variants (lone leading/trailing/mid-word apostrophes, CRLF, nested lists, a second secret list after the first, valid quoted elements) are regression tests; an explicit no-over-redaction test asserts exact unchanged output for ordinary apostrophe text.
- `pytest` runs with `--basetemp` outside the worktree; no new `noqa`.

### Assumptions

- A quote directly after an alphanumeric is never a string opener in real list values (JSON, Python, YAML flow) — the `## Validation` table of valid quoted lists proves it.
## Alternatives Considered

- Limit every quoted region to its own line: rejected, it breaks legitimately multi-line YAML flow scalars and still leaks when the lone quote opens a line.
- Ignore apostrophes entirely in the scan: rejected, `'d]'` style elements containing `]` would end the list early and leak the tail.

## Open Decisions

- none — the rule is decided from the reproductions and the existing quote tests.

## Risks

- A real quoted element directly after a letter (`x'a]'`) now ends a list early: ACCEPTED — not valid in JSON, Python or YAML flow lists, and the failure masks to the end of the bracket rather than leaking more than before.
- Quadratic lookahead: mitigated by the cached backwards closer search and asserted by timing tests at 4k and 64k.

## Discoveries

- decision: quotes open only after a non-alphanumeric with a later valid closer; closers are not followed by an alphanumeric — covers contractions, possessives and unmatched quotes, linear via cached rfind
- decision: rule scoped to the apostrophe only — applying the opener/closer rule to double quote and backtick turns the existing double-quote earlier-unclosed test into a different (still masking) outcome; lone double-quote/backtick in a multi-line secret list remains unchanged behaviour
- follow-up: a lone double quote or backtick in a multi-line secret list still falls back to the first line (same class as this spec, needs a decision on the existing double-quote unclosed-prefix test)

Shipped: lone or word-internal quotes (apostrophe, double quote, backtick) in multi-line bracketed secret lists no longer hide the closing bracket.
