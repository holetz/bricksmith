## Problem

Found by the correctness review of epic 109 (autopilot 2026-11-24 round 2), reproduced on main 73c8775 with a synthetic MemoryStore run (helpers `config`/`results_of`/`rows_of` of `tests/unit/monitor/stability/test_stability_metrics.py`): months 2026-01..10, drift 05–07, `max_periods=3`, fixed baseline 01–04, `persistence={"red":3,"yellow":3}` (red ≤ max_periods, as `docs/how-to/stability.md` asks), one month per run, rows merged after each.

```
2026-07 [... ('2026-07', 'red')] [('2026-07', 'open', '', '2026-07')]
2026-08 [('2026-08', 'green')] [('2026-07', 'superseded', '', '2026-07')]
2026-09 [('2026-09', 'green')] [('2026-07', 'superseded', '', '2026-07')]
2026-10 [('2026-10', 'green')] [('2026-07', 'superseded', '', '2026-07')]
```

In 2026-08 the window 06–08 holds only two reds, so the replay no longer reproduces the alert; it is not carried because its `opened_period` 2026-07 is after the window start (`src/bricksmith/monitor/stability/metrics.py:492`), and `_superseded` spares only CLOSED alerts with `opened_period <= start` (`src/bricksmith/monitor/stability/engine.py:307-313`). The same gap supersedes a closed alert opened inside the window whose run began before it.

Consequence: a real drift alert disappears without ever closing, contradicting spec 104's promise (keeps its `alert_id`, escalates and closes on the window's statuses); no close notification, no closed-alert history, no recurrence.

Proposal: a stored alert (open or closed) is carried regardless of where its opening falls relative to the window start; only a replay that produces a different identity for the same episode may supersede. Add the sequence above as a regression test (pure engine; keep Spark parity).

## Proposal

- A stored open alert is carried regardless of where its opening falls relative to the window start: when the window no longer reproduces it, it keeps its `alert_id`, escalates and closes on the window's statuses instead of being superseded.
- A stored closed alert of the active version stays closed when the window slides past the run that produced it, wherever its opening fell; only a changed judgment (new judgment fingerprint) can still supersede it.
- The `trend` kind follows the same rule as `persistence`.
- The 2026-07..2026-10 sequence of the Problem is a regression test of the pure engine.

## Out of Scope

- Changing the alert identity (`alert_id` stays a hash of dataset, version, key, kind and opening period): re-keying history is a larger change with no evidence it is needed.
- Any change to the Spark path: `alerts` and `_superseded` run over collected rows for both engines.
- Model-monitoring alerts (`monitor/model`): a different replay with its own specs.

## Design

- **Why the stored alert was dropped.** `alerts` discards a stored open alert whose `opened_period` is after the first window period, assuming the replay reproduces it. That is false when its red run began before the window: the replay then yields a different span (or none), and `_superseded` retires it.
- **Rule.** For a stored open alert opened inside the window, replay the series unseeded first; when some span has the same opening period, the replay reproduces it and nothing changes. Otherwise seed `alert_spans` with the stored alert and replay only the series periods at or after its `opened_period`, so earlier greens in the window cannot close it; the existing merge of the stored row (id, opening, escalation, recurrence, `flagged_periods`) applies. The seeded span is the only replayed span of that key and kind in that case.
- **Judgment change still supersedes.** The carry of an in-window alert and the closed-alert exemption apply only when the judgment fingerprint is unchanged (`rewrite_all` false in `check`): a changed judgment legitimately re-judges history (spec 104/106 test). `alerts` takes `keep_inside: bool = True` and `_superseded` takes `keep_closed_inside: bool = False`; `check` passes `not rewrite_all` to both.
- **Closed alerts.** `_superseded` keeps a stored closed row of the active version when its opening is at or before the window start (spec 106) or when the judgment is unchanged.
- Binding contracts: `docs/how-to/stability.md`; decision 0010 (synthetic tests); `alert_id` unchanged.

### Assumptions

- `rewrite_all` equals "the judgment changed or first run of the version" (`engine.py:454`); first runs hold no stored alerts of the version, so the flag is safe to reuse. Depends on: Design.
## Alternatives Considered

- Supersede only when the replay yields a different identity for the same episode: needs episode matching across runs; carrying by stored state is simpler and uses the existing seed.
- Keep every closed alert regardless of judgment: breaks the spec 104/106 guarantee that a changed judgment re-judges history.

## Open Decisions

- none — the choices above follow from the Problem and the existing code.

## Risks

- A carried in-window alert counts statuses only from its opening period, so an escalation needing consecutive reds started before it may be late. ACCEPTED — the stored severity is kept and the same limit already holds for alerts carried from before the window.
- A stale open alert is never superseded by a slide. Mitigation: it closes after `close_after` greens in a later run.
