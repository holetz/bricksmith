## Problem

The stability metrics are PSI, null and unseen rates, mean and mean shift, row count and volume
(`stability/config.py:35-39`). Common reprocessing failures are not covered: partially duplicated keys after a
double load (volume moves only a little), a category that disappears (PSI floors it at epsilon and may stay
green on low-share categories), a collapse in distinct values of an identifier, or a shift in tails that leaves
the mean intact.

## Proposal

- `keys: [...]` declares the grain; profile `duplicate_key_rate` per period (Spark: count vs approx distinct
  count of the key tuple; exact in the pure engine).
- `distinct_count` / `distinct_change` per monitored column (approximate in Spark, documented error).
- `vanished_rate`: share of baseline mass in categories absent from the period, with default limits.
- `p05/p50/p95` shift for numeric columns derived from the stored bins (interpolated), avoiding a new scan.
- Optional distribution distances computed from the stored bins without a new scan: Jensen–Shannon distance for
  categorical columns and an approximate Wasserstein distance for numeric ones, with their own limits, as
  complements to PSI.
## Out of Scope

- Referential integrity across tables (quality module).
- Correlation drift between columns.

## Impact

### Product code this spec expects to touch

- `src/bricksmith/monitor/stability/config.py` — metric names, default limits, the `keys` and `distinct` declarations
- `src/bricksmith/monitor/stability/distribution.py` (new) — vanished rate, quantiles, Jensen–Shannon and Wasserstein from stored bins

- `docs/how-to/stability.md` — document the new metrics and declarations

## Validation

- A synthetic 3% duplicated load turns `duplicate_key_rate` red while `volume_change` stays green.
- Removing a 2% category turns `vanished_rate` yellow/red.

## Design

- **Bin-derived metrics need no new storage.** `vanished_rate`, `p05_shift`/`p50_shift`/`p95_shift`, `js_distance` (categorical columns) and `wasserstein` (numeric columns) are pure functions of the baseline and current bin counts already stored, so they cost no scan. They are computed in `distribution.py` and judged per column like `mean_shift`.
- **Quantiles are interpolated from the bins**: linear inside a bin between its edges; the open outer bins use the stored value sums as their mean. The shift is `(q_now - q_base) / baseline std` like `mean_shift`, so the default limits (0.25/0.50, both directions) match it.
- **Wasserstein** is the 1-D earth mover's distance between the two bin-CDFs evaluated at bin midpoints, divided by the baseline std so it is scale-free.
- **Jensen–Shannon distance** is the square root of the base-2 Jensen–Shannon divergence of the two bin share vectors (0..1).
- **Scan-derived statistics (`keys`, `distinct`) ride in the profiles table** as rows whose column starts with the reserved prefix `~`: `~keys` (count = rows, value_sum = distinct key tuples) and `~distinct:<column>` (count = non-null rows, value_sum = distinct values). A reserved column is skipped by every bin reader (`index_profiles` routes it to `History.extras`; `table_totals` ignores it), so no table schema changes and old stores keep working. They are profiled for the whole population only (segment `""`); this is documented.
- **Exactness**: the pure engine counts exactly; Spark uses `approx_count_distinct` (documented relative error about 5%), so `duplicate_key_rate` has an error floor in Spark that the default limits sit above.
- `duplicate_key_rate = 1 - distinct_keys / rows`; `distinct_change = distinct / baseline_mean_distinct - 1`; `distinct_count` carries no limits (informational, like `row_count`).
- Default limits: `duplicate_key_rate` 0.01/0.02 higher; `vanished_rate` 0.01/0.05 higher; quantile shifts 0.25/0.50 both; `js_distance` 0.10/0.20 higher; `wasserstein` 0.10/0.25 higher; `distinct_change` 0.20/0.50 both. They live in a separate dict used only for these metrics, so declarations that do not use them keep their serialized limits (same technique as the schema metrics).
- Opt-in: bin-derived metrics are always computed (free); scan-derived ones only for declared `keys` and `distinct` columns.

### Assumptions

- A category counts as "vanished" when it has baseline mass and zero current count; the unseen/outside bins are excluded — supports `## Validation`.

## Alternatives Considered

- A dedicated results table for key/distinct statistics: rejected, it adds a table, a migration and a store protocol change for two numbers per period.
- Exact distinct counts in Spark: rejected, a full shuffle per column on wide tables; opt-in plus approximation keeps the cost bounded.

## Open Decisions

- none — every choice above is settled by the spec and the existing code shape.

## Risks

- Distinct counts on wide tables are expensive; opt-in per column.
