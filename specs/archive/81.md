## Problem

Model monitoring (BS-13) runs through ordinary tasks plus `monitor.persist`; it has no declaration on the task, no plan or runner integration, no run record and no dashboard tables, while data stability has all of these (`monitor/stability/hook.py`, `monitor/stability/tables.py`). Each monitored model must be wired by hand, and a failed metric stops the rest.

## Proposal

- A task metadata key declaring model monitoring on the prediction (or monitoring) task: the model, the prediction table roles (score, grade, label, segments, sample role), the development and out-of-time references, the metric set and the gate (warn/fail), mirroring the stability declaration and executed by the shared runner after the write.
- Every result row carries both the monitoring period and the data period (spec 72 refines lags per metric), the model version and the reference used.
- Metrics computed through the existing core (`monitor.measure`, rows and Spark): score PSI, feature CSI (reusing the stability binning so feature drift and data stability share bins), KS/AUC/Gini, calibration; plus volumetry and completeness of critical fields.
- A run record table written last (code version, inputs and their versions, references, status success/partial/failed); a failed metric marks the run partial and does not stop the others; readers trust only finished runs.
- Dashboard-ready tables and views (results, details per bin, alerts, runs) parallel to the stability ones, and a recompute of alerts from stored lights without recomputing metrics.

## Out of Scope

- New limit families (spec 70), selectors (spec 73) and the human alert workflow (spec 71).

## Design

- 2026-11-23 — **Binding context.** Epic 85 `## Design` (private-source rule, monitoring decisions: bricksmith computes and stores its own monitoring tables; Databricks data profiling is not a dependency; feature CSI shares bins with data stability). Everything here is generic, with synthetic tests.
- 2026-11-23 — **Declaration.** `metadata={"model_monitoring": {...}}` on the task that writes predictions (one mapping, or a list with distinct `output`). Keys: `output` (which task output, required only with several outputs), `model` (required name), `model_version` (literal) or `model_version_column`, `period` (required column), `score` (required), `label`, `grade`, `segment` (one column), `sample` (role column), `references` (`development` required, `out_of_time` optional; each `{sample: <value>}` or `{start, end}` period range), `features` (columns for CSI), `feature_binning` (`own` default, or `{stability: <dataset>, prefix?: "stability_"}` to reuse the latest stored stability binning of that dataset in the same scope), `critical_fields` (completeness), `metrics` (subset of the families below, default all applicable), `label_lag` (periods, default 0), `limits` (per metric, shared `Limits`), `gate` (`fail_on` red/yellow, `on_error` warn/fail; default warn), `min_rows`, `max_periods` (default 24), `score_bins` (default 10), `scope`, `prefix` (default `model_monitoring_`). Unknown keys are errors; invalid declarations are plan errors (`invalid_model_monitoring`).
- 2026-11-23 — **Metric families** through the existing core (`monitor.measure`, rows and Spark engines, identical results): `score_psi` (score bins fitted on development), `feature_csi` (per feature; bins from the stability binning when declared, else fitted on development with the same `fit_bins` rules data stability uses), `discrimination` (KS, AUC, Gini), `calibration` (Brier, ECE, observed/expected ratio derived from the ECE bin table), `volumetry` (row count, volume ratio to development), `completeness` (null rate of each critical field). Grade, when declared, is a categorical distribution column judged like a feature (`grade_psi`). Per-grade calibration tests are spec 82's.
- 2026-11-23 — **Periods.** Rows split by the period text of `period` (the stability `period_text` rule). Monitoring periods are the latest `max_periods` periods outside the references. Every result row carries `monitoring_period` and `data_period`: label metrics (discrimination, calibration) use `data_period = monitoring_period - label_lag`, computed calendar-wise for `YYYY-MM` and `YYYY-MM-DD` texts (other period texts refuse a non-zero lag); distribution, volumetry and completeness use lag 0. Spec 72 refines lags per metric.
- 2026-11-23 — **Reference values.** Each result row carries `development_value` and `out_of_time_value` (the same metric measured on the reference samples) and `reference` naming what drift compares with (`development`).
- 2026-11-23 — **Tables** (scope `catalog.schema`, default the output's schema; flat scalar columns, merge keys): `<prefix>binnings` (model, binning version, frozen score and feature bins as JSON body, fingerprint), `<prefix>results` (one row per model, model version, monitoring period, segment, column, metric and run: value, light, limits, data period, reference values, rows), `<prefix>details` (per bin: PSI/CSI contributions and calibration bins), `<prefix>alerts` (one row per red or yellow result of a monitoring period: severity from the light; no lifecycle — spec 70 adds persistence and spec 71 human actions), `<prefix>runs` (run id, model, model version, task, physical input and its table version when Spark reports one, bricksmith version, reference fingerprint, status `success`/`partial`/`failed`, counts, message, started/finished). Results, details and alerts are keyed with the run id; the run row is written last.
- 2026-11-23 — **Trust and partial runs.** Each metric family is computed in isolation: a raising family yields result rows with light `no_data` and reason `error: <type>`, marks the run `partial`, and does not stop the others. Views read only rows of finished runs (`status IN ('success','partial')`) and, per model, model version and monitoring period, the latest finished run: `<prefix>latest`, `<prefix>model_status`, `<prefix>open_alerts`.
- 2026-11-23 — **Alert replay.** `replay_alerts(results, config)` rebuilds alert rows from stored result lights without recomputing metrics; the CLI `bricksmith model-monitoring views` prints the view SQL and `alerts` replays alerts from exported result rows.
- 2026-11-23 — **Runner.** The plan lists the five tables as declared `merge` targets (`on_empty: allow_empty`, so an empty write creates them for dashboards); after a successful task the worker runs data stability and then model monitoring; the gate may fail the task (dependents blocked, the written output stays published); `TaskResult.model_monitoring` carries outcomes and serializes only when present. Spark and the model package load only for declaring tasks.

### Assumptions

- The prediction table carries development and out-of-time scored rows beside production rows, told apart by a sample column or a period range (lands in Design §Declaration).
- A single segment column suffices here; multi-column segments follow selectors (spec 73) (lands in Design §Declaration).

## Alternatives Considered

| Approach | Cost | Buys | Forecloses |
| --- | --- | --- | --- |
| **Declared task metadata with own tables (chosen)** | a new package mirroring stability | same review, gate and dashboards as stability; no hand wiring | — |
| Keep ordinary `monitor` tasks plus `monitor.persist` | none | nothing new | plan integration, run record, partial runs |
| Databricks data profiling (inference profiles) | workspace feature, little code | managed UI | 30-day window too short for 12-period maturation (epic 85 Design); not free-first |
| Extend stability tables with model columns | fewer tables | one star model | mixes data and model grain; stability keys have no model version or run |

Results keyed by run (chosen) versus overwrite by period: run keys let views trust only finished runs and keep history of reprocessing; the cost is growth per run, small because rows are aggregates.

## Risks

- Spark cost: one measure per period and segment issues several small jobs; acceptable for monthly closings, measured in the remote test; a single grouped pass is a later optimisation (discovery if it bites).
- Results keyed by run grow with reruns; views pick the latest finished run, and retention is a project choice.
- The Spark path is only proved remotely; if no Free Edition profile is reachable from the worktree, the pure engine and the shared core parity (already proved for `monitor.measure`) carry the proof until spec 84.
- Reusing a stability binning ties feature bins to a stability dataset's version: the binning fingerprint is stored on every run so a stability refit is visible.

## Discoveries

- decision: label_lag counts observed monitoring periods (ordinal shift over the sorted monitoring period texts), not calendar months — works for month texts and closing dates alike without guessing a calendar step; a gap in the data shifts to the previous observed period, documented in the guide; spec 72 may add calendar lags per metric
- decision: task 2.1 also touches src/bricksmith/monitor/stability/hook.py — its declarations() read every non-stability target as a task output, so a task declaring both stability and model_monitoring would fail to resolve; the fix excludes model monitoring tables there (one condition, covered by a test declaring both)
- decision: the remote test (Spark engine equals pure engine; declared task feeds the views) is written and collected but skipped in this worktree (no BRICKSMITH_RUN_REMOTE_TESTS/profile, and the installed pyspark is Databricks Connect only, so no local Spark session) — the SparkFrame adapter is unproven until the Free Edition run the Validation section assigns to spec 84
- decision: replay_alerts takes (results, runs, config=None) instead of (results, config) — replay must apply the same finished-run filter as the views, which needs the runs rows; the CLI 'alerts' reads both from one exported JSON state file
- decision: PR body omits 'Closes #81' — specs live on the quenching branch with GitHub issue cards disabled (AGENTS.md), and no issue #81 exists
