## Problem

Some metrics are only meaningful after outcomes mature: a default flag or a loss value is revised for months. Monitoring a period as soon as it is loaded mixes immature and mature data, and hiding the lag inside segment keys makes it invisible.

## Proposal

- Distinguish the monitoring period from the data period: a declared `lag` per metric or per check (in periods) maps monitoring period P to data period P - lag; both are stored on result rows.
- Series, persistence and reprocessing are keyed on the monitoring period; dashboards show both.

## Out of Scope

- Estimating performance before labels mature (epic 85 design: out of scope this epic).
- Lags on data stability (`stability` declarations): stability measures the loaded period itself; only `model_monitoring` gains lags.
- Changing the meaning of the existing `label_lag` integer: it keeps counting observed periods, so declarations and stored results from spec 81 read the same.
- Persistence, trend and alert keys by data period: series stay keyed on the monitoring period (this spec's proposal), so alert and replay code is untouched.

## Impact

- `src/bricksmith/monitor/model/engine.py` — resolve the data period per metric (observed or calendar), measure each distinct lag once per family, stamp `lag` and `lag_unit` on result rows.
- `src/bricksmith/monitor/model/tables.py` — additive `lag` and `lag_unit` columns of the results table (migrated through the existing `evolution` option).

## Design

- 2026-11-23 — **Two periods, one key.** `monitoring_period` stays the key of series, persistence, trend, alerts and reprocessing; `data_period` is what was measured. A lag only moves the rows a metric reads, never the row's identity (proposal).
- 2026-11-23 — **Declaration.** `lags` maps a metric (`auc`) or a family (`discrimination`) to a lag; the metric wins over its family, the family over the default. The default is `label_lag` for label families and 0 otherwise, so spec 81 declarations are unchanged. A lag is an integer (observed periods) or `{periods: n}` or `{months: n}`; anything else is refused at parse time. Unknown metrics or families are refused.
- 2026-11-23 — **Observed versus calendar.** An observed lag counts the periods present in the data (spec 81 behaviour, for loads with no gaps in meaning). A calendar lag subtracts `n` months from the monitoring period's date and renders the result in the same text format as the monitoring period; when that period is not in the monitored rows, or the text is not a date format `period_date` understands, the result has no value and reason `data_period_unavailable` — it never silently shifts to the nearest observed period, because that would present immature data as mature. Day-of-month clamps to the month's last day.
- 2026-11-23 — **Measuring per distinct lag.** Within a family, metrics sharing a lag are measured on one data period in one pass; metrics with different lags cause one pass per distinct lag, and only the metrics of that group are kept. A family with no declared lag costs exactly what it did.
- 2026-11-23 — **Stored facts.** Result rows carry `lag` (INT) and `lag_unit` (`periods` or `months`) beside `data_period`, additive columns on the existing table through the `evolution` write option (decision 0012, 0016 pattern). Rows of lag 0 write `lag=0`, `lag_unit=periods`. Views select `t.*`, so dashboards see both without a statement change.
- 2026-11-23 — **Binning fingerprint.** Lags never trigger a refit (the fingerprint already excludes lags); the config `to_dict` includes them so the run is reproducible.
- 2026-11-23 — **Private-source rule.** Only generic behaviour; synthetic data and neutral names (epic 85).

## Alternatives Considered

- Encode the lag in the segment key (what the problem rejects): hides the lag from dashboards and breaks segment joins.
- Replace `label_lag` with `lags` only: breaks spec 81 declarations for no gain; kept as the default for label families.
- Shift a missing calendar month to the nearest observed period: rejected for the maturity reason in `## Design`.
- Key series on the data period: rejected by the proposal; reprocessing and alerts are per monitoring period.

## Open Decisions

- none — every decision above is settled from the spec, spec 81's code and the epic design; a quarter/week lag unit is deferred to a later spec if a project asks.

## Risks

- A calendar lag on a period text that is not a date format yields only `data_period_unavailable` rows: ACCEPTED — the reason is explicit on every row and the guide states which formats work.
- Several distinct lags multiply label-family measurement passes: ACCEPTED — bounded by the number of distinct lags declared (usually one or two); the default path is unchanged.
- A table created before this spec lacks the new columns: mitigated by the `evolution` write option and proved remotely in task 3.1.

## Outcome

Model monitoring now separates the monitoring period from the data period with declared lags. `lags` maps a metric or a family to a lag in observed periods or calendar months (the metric wins over its family, the family over the `label_lag` default). A calendar lag never shifts over a gap: a missing period yields no value with reason `data_period_unavailable`. Metrics sharing a lag are measured in one pass and each distinct lag costs one pass. Result rows carry `lag` and `lag_unit`, added to an existing results table through the `evolution` option. Declarations without `lags` give the same values, lights and data periods as before.

Delivered: `Lag` parsing and resolution in `config.py`, per-metric data periods in `engine.py`, the two table columns in `tables.py`, unit tests, the guide section in `docs/how-to/model-monitoring.md`, and decision 0018. Spark equals the pure engine with lags, and the results table migration is proven on the Free Edition profile.

Left out: forward-looking or per-segment lags, and anything beyond months and observed periods.
