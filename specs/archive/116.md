## Problem

When a segment set has more values than `max_segments`, the kept top-N is ranked only over the rows of the periods profiled in the current run (`src/bricksmith/monitor/stability/profile.py:261-265`; Spark `src/bricksmith/monitor/stability/spark.py:172-178`), and a normal run profiles only the `refresh_periods` latest periods (`src/bricksmith/monitor/stability/engine.py:271`). Neither `max_segments` nor the kept set enters `binning_fingerprint`/`judgment_fingerprint` (`config.py:249-260`, `engine.py:140-148`).

Consequence: a segment whose volume collapses drops out of the latest period's top-N, gets no profile and no result row, so no red `volume_change` is raised and a `fail_on: ["red"]` gate passes; a segment newly in the top-N comes out `no_baseline`. Reproduced on e2716ad (synthetic): segments a/b/c 300/200/100, `max_segments: 2`, fixed baseline 2026-01..03; in 2026-05 b drops 200→5 and c rises to 150 → run 2 has no row for `ch=b`, outcome "0 red, 1 yellow". `docs/how-to/stability.md:62` ("the most frequent segment values kept per segment set") reads as one stable set.

Done when: a segment kept in earlier runs whose volume collapses in the latest period is still judged (volume metrics red), pure and Spark agree, a regression test covers the repro, and stability.md states how the kept set is chosen.

## Proposal

- The segments a stability run keeps per segment set no longer depend on which periods that run profiles: two runs over the same loaded periods keep the same set, whatever `refresh_periods` re-profiles.
- A segment that was profiled in earlier periods of the window and whose volume collapses in the latest period is still profiled and judged there, so its `volume_change` turns red and a `fail_on: ["red"]` gate fails.
- A segment that disappears entirely after having rows is judged with zero rows (`volume_change` = -1) instead of silently vanishing from the results.
- The pure and Spark engines produce the same kept set and the same profile rows, including the zero rows.
- `docs/how-to/stability.md` states how the kept set is chosen and that a kept segment stays judged while its history is in the window.

## Out of Scope

- Storing a frozen kept set on the binning row — rejected in favour of a set derived from loaded data and stored history (see `## Alternatives Considered`).
- Re-profiling older periods for a segment that newly enters the kept set — its earlier periods stay as stored; it starts with `no_baseline` as before.
- Changing `max_segments`, its default or its effect on the binning/judgment fingerprints.
- The rules-path resolution (spec 119) and the Spark spelling parity of categories (specs 118/120).

## Design

- 2026-11-24 — Owner decision (epic 121): the kept segment set must not depend on which periods a run happens to profile. Preferred: rank segments over every period of the computation window loaded in the run, and keep profiling any segment that already has stored profiles in the window even when it falls out of the top-N, so its collapse is judged (zero or low volume → red volume metrics). An equivalent design (frozen kept set stored with the binning) is allowed if it keeps run-to-run stability, pure/Spark agreement and idempotent reruns.
- Choice (recorded per the owner decision): the preferred design, not a frozen set. Rules:
  - **Ranking span.** Per segment set, segments are ranked by row count (ties by key) over every period the run loads — the window plus the baseline history (`_loaded_periods`) — not only the periods it profiles. A first run and a later run over the same loaded periods rank the same rows.
  - **Carried segments.** A segment with stored profile rows of positive count for the active binning version in the loaded periods stays kept even when it falls out of the top `max_segments`; the kept set may then exceed `max_segments`. It ages out on its own once its positive stored rows leave the loaded periods.
  - **Zero rows.** In every profiled period after the first period where a kept or carried segment had rows (in the loaded data or in stored profiles), a segment without rows gets profile rows with every bin at zero count, so `volume_change` is -1 and judged; distribution metrics follow `min_rows` (`insufficient_volume`) as for any thin segment. Before its first period nothing is emitted, so a new segment keeps `no_baseline`.
  - **Truncation report.** `ProfileInfo.truncated` counts the ranked segments that were not kept.
  - **One rule, two engines.** The kept-set and zero-row rules live in `profile.py` helpers that both engines call; the Spark ranking job also collects each key's first period, so profiling stays three Spark jobs.
  - **Fingerprints unchanged.** The kept set is derived deterministically from the loaded data and stored history, so `binning_fingerprint`/`judgment_fingerprint` need not carry it and reruns are idempotent.
- Binding contracts: profile rows stay additive and identical across engines (`profile.py` module doc); decision 0010 — synthetic tests only.

## Alternatives Considered

- Frozen kept set stored on the binning row at fit time: stable, but a segment that grows after the fit is never monitored until a refit, and it adds a schema/body change to stored binnings. Rejected.
- Ranking over the loaded periods only (no carried segments): fixes the reported repro, but a segment that drops out of the top-N over a sliding window would again vanish unjudged. Rejected as incomplete.
- Judging absent segments inside `compute` from the stored history instead of emitting zero rows: `compute` cannot tell a truncated segment from an absent one, so it would raise false reds. Rejected.

## Open Decisions

- none — the owner decision in epic 121 settles the shape; the remaining choices are recorded in `## Design`.

## Risks

- The kept set may exceed `max_segments` while carried segments age out — ACCEPTED: bounded by the loaded periods, and dropping them is exactly the silent failure this spec fixes.
- Zero rows add one profile row per bin for a vanished segment per profiled period — ACCEPTED: same size as any kept segment.
- Spark and pure diverge on the first-period or tie order — mitigated by shared helpers and the remote parity test on Free.
- Existing stored histories written before the fix lack rows for previously dropped segments — ACCEPTED: those segments start their history at the next run; nothing is rewritten.
