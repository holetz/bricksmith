## Problem

Monitoring results are only useful if people look at them. The reviewed reference produced offline HTML reports and had no dashboard model; its stability tables used maps and JSON strings that BI tools cannot slice. A stability capability must leave behind tables that a BI tool can connect to directly, with a documented star model, plus a guide and real-workspace proof.

## Proposal

- Define the five stability tables with flat, typed columns (no maps, no JSON for anything a report filters on), stable keys and dashboard helpers (`status_rank`, `period_date`, readable labels, shares and limits on result rows).
- `bricksmith stability views --scope <catalog.schema>` prints `CREATE OR REPLACE VIEW` statements: `<prefix>latest` (latest period per dataset), `<prefix>dataset_status` (worst status per dataset and period), `<prefix>open_alerts`.
- Guide `docs/how-to/stability.md` with the declaration, gate policy, tables, the BI star model (facts, dimensions, relationships, suggested measures) and limits.
- Example: a monitored table in `examples/shared_schema` with an injected drift.
- Remote proof on Free Edition with evidence.

## Out of Scope

- A dashboard file of any BI vendor.

## Impact

- `src/bricksmith/monitor/stability/tables.py` (schemas, view SQL).
- `docs/how-to/stability.md`, `docs/how-to/index.md`, `docs/how-to/monitoring.md` (cross-link).
- `examples/shared_schema/catalogs/demo/ml/stability.py` — new.
- `tests/remote/test_stability.py`, `docs/project/evidence/stability-free.md` — new.

## Validation

- Unit: every table schema is flat (no MAP/ARRAY/STRUCT types); view SQL references only declared columns; the example graph builds and plans the stability targets.
- Remote on Free Edition: run the example tasks through the shared runner with `SparkTableIO`; assert row counts and statuses, a gated failure that blocks its dependent, an idempotent rerun, pure/Spark parity, views created and queried; test-owned schema removed.

## Design

- `stability_results` key `(dataset, version, period, segment, column, metric)`; columns: `value`, `current`, `baseline`, `status`, `status_rank`, `reason`, `green_limit`, `red_limit`, `direction`, `rows`, `baseline_rows`, `in_baseline`, `baseline_kind`, `baseline_label`, `trend_status`, `trend_expected`, `trend_deviation`, `period_date`, `segment_label`, `run_id`, `computed_at`.
- `stability_profiles` key `(dataset, version, period, segment, column, bin)`; columns `bin_order`, `bin_label`, `count`, `weight`, `value_sum`, `value_sum_sq`, `share`, `baseline_share`, `contribution`, `period_date`, `run_id`.
- `stability_alerts` key `(dataset, alert_id)`; `kind`, `metric`, `column`, `segment`, `severity`, `state`, `opened_period`, `escalated_period`, `closed_period`, `last_period`, `last_status`, `last_value`, `flagged_periods`, `recurrence`, `message`, `run_id`.
- `stability_binnings` key `(dataset, version)`; `config_fingerprint`, `fingerprint`, `fit_periods`, `fit_rows`, `body` (the reference JSON, not filtered on by reports), `created_run_id`.
- `stability_runs` key `(run_id, dataset)`; `task_id`, `physical`, `version`, `latest_period`, `periods_profiled`, `status`, `red`, `yellow`, `open_alerts`, `message`, `started_at`, `finished_at`.
- Star model: dimensions derived from the facts (dataset, column, metric, period, segment); facts results, profiles, alerts, runs.
