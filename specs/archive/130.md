## Problem

Reproduced by the epic 125 correctness review (autopilot 2026-11-24, round 5) on origin/main 393db9e, after spec 127 (PR #79) passed the column dtype to `bin_expression` in the stability Spark profile. For a DOUBLE or FLOAT categorical column holding both -0.0 and 0.0, the fit keeps one category `cat:-0.0`; the pure engine matches by text, so 0.0 goes to `unseen`, while Spark matches by number (`src/bricksmith/monitor/spark.py:62`, reached from `src/bricksmith/monitor/stability/spark.py:252`), so 0.0 goes to `cat:-0.0`.

Repro (local pyspark 4.0.1, `uv run --isolated --no-project --with pyspark==4.0.1 --with-editable . --with pytest`): `DOUBLE DIFF COUNTS [(('2026-01','','rate','cat:-0.0'), 4, 8), (('2026-01','','rate','unseen'), 4, 0)]`; FLOAT the same. Every other edge (±inf, NaN, 1e7, float32, null) matched; segment keys identical.

Consequence: narrow — pure and Spark runs of the same data disagree on unseen_rate and PSI when both zero signs occur.

Done when: both engines put -0.0 and 0.0 in the same bin (one canonical rule, documented), covered in the local-pyspark parity suite.

## Proposal

- `-0.0` and `0.0` are one category in both engines (numeric equality, as Spark already applies).
- The pure engine spells the zero category `0.0` for new fits and no longer distinguishes the sign of zero.
- A stored fit whose category is spelled `-0.0` keeps matching both zeros in both engines.
- The local-pyspark parity suite covers both zero signs for DOUBLE and FLOAT columns.
- The stability how-to documents the rule and the migration note.

## Out of Scope

- Changing any other round-4 canonical spelling (specs 118/120/127): ±inf, NaN, `1e7` and booleans stay as they are.
- Rewriting stored references: a `-0.0` category stays valid and is matched by both zeros instead.

## Impact

### Product code this spec expects to touch

- `src/bricksmith/monitor/bins.py` — `category_text` spells either zero `0.0`; `BinSpec.assign` matches both zeros to a stored `-0.0` category.
- `src/bricksmith/monitor/stability/spark.py` — floating spelling of zero for segment keys.
- `tests/unit/monitor/test_spark_parity.py`, `tests/unit/monitor/test_canonical_spelling.py` — parity and unit proofs.
- `docs/how-to/monitoring.md` — rule and migration note.

## Validation

`uv run pytest tests/unit/monitor` for the pure rule; `uv run --isolated --no-project --with pyspark==4.0.1 --with-editable . --with pytest pytest tests/unit/monitor/test_spark_parity.py -q` proves both engines bin DOUBLE and FLOAT `-0.0`/`0.0` identically, with a fit that spells the category `0.0` and one that stores `-0.0`. `uv run ruff check`, `uv run pyright` and `uv run pytest` stay green.

## Design

Decision (owner, epic 132 Design): one canonical rule — `-0.0` and `0.0` are the same category in both engines. The canonical spelling of the zero category is `0.0`.

- `category_text` returns `0.0` for any float equal to zero; every fit, segment name and selection key that uses it follows.
- `BinSpec.assign` falls back to a stored `-0.0` category when the value's text is `0.0` and `0.0` itself is not a category, so legacy fits keep matching both zeros.
- Spark already matches floating categories by value, so the stored `-0.0` category matches both zeros; the Spark fit and segment spelling normalise zero to `0.0`.

### Assumptions

- Only Python floats carry a negative zero here; ints and strings are unaffected (`## Impact`, bins.py).

## Alternatives Considered

- Make Spark distinguish the sign of zero: rejected, the owner decided numeric equality.

## Open Decisions

- none — the owner settled the rule in the epic Design.

## Risks

- A stored `-0.0` category plus a new `0.0` category in one fit cannot occur from a new fit; if a hand-edited reference holds both, the exact text wins. ACCEPTED — not produced by any fit.
