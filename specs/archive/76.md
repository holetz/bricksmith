## Problem

Model projects rebuild the same features inside each model revision, with no shared rule for which closing of a feature an observation reads. Batch credit-style models run on monthly (or other periodic) closings, so features must be the value as known at a closing, not at an approximate event time. Today `bricksmith.mlops` builds population, features and labels per model (`mlops/reference.py`, `mlops/spark.py`) and checks point-in-time per dataset (`mlops/validate.py:115`), but there is no reusable feature table contract, no availability lag and no training-set builder that joins features by exact closing. Training reading frozen copies while scoring reads live tables invites training/serving skew.

## Proposal

- A feature table declaration on ordinary tasks (metadata key, like `dataset` and `stability`): entity key columns, a closing-date column (DATE, part of the primary key), a closing frequency (monthly by default; any periodic closing), feature columns with description, type and owner, and an `availability_lag` in periods: rows are stamped at the closing at which the source became available, never the closing it describes.
- Wide tables, one row per entity and closing; numeric features as DOUBLE, categorical as STRING, arrays and maps allowed with documented order; model input vectors are never stored.
- A training-set builder: spine (population with entity keys, observation closing and optional label) + feature lookups (table, keys, feature names, closing offset) → one frame, joined by exact closing equality; the same builder serves training and scoring so the only difference is the spine. Pure (row) and Spark engines with parity tests.
- Guards: a lookup whose feature closing is after the observation closing is refused; missing entity rows yield nulls with a declared default per feature; duplicate primary keys fail the load.
- Reproducibility: the builder returns the Delta version (or a fingerprint offline) of every feature table it read, ready to log as MLflow inputs.
- Optional Unity Catalog Feature Engineering adapter, lazily imported behind an extra: publishes the primary key and exposes `FeatureLookup`/`create_training_set`/`log_model` lineage. Exact-closing semantics are documented: a DATE key must be TIMESERIES (as-of join) or stored as STRING for exact match; the adapter chooses explicitly and says so.
- Write strategy: replace by closing (re-running a closing replaces only that closing).

## Out of Scope

- Online serving and millisecond lookups.
- Event-time as-of joins for sub-period sources (the declaration leaves room for a future `timeseries` mode).
- Feature Views as a dependency (public preview; no date entity columns).

## Design

- **Binding context.** Epic 85 `## Design` (2026-11-23): plain Unity Catalog Delta tables written by ordinary tasks; primary key = entity keys + closing date (DATE); exact equality join on closing; rows stamped at the closing the source became available; Databricks Feature Engineering only as an optional lazily imported adapter; Feature Views not a dependency; one builder for training and scoring. Private-source rule: generic behaviours, synthetic tests (decision 0010).
- **Declaration.** Metadata key `feature_table` on an ordinary `@task` (same open-metadata mechanism as `model_dataset` and `stability`): `entity_keys` (list of identifiers), `closing` (DATE column name, default `closing_date`), `frequency` (`monthly` default; `quarterly`, `semiannual`, `annual`, `weekly`, `daily`), `availability_lag` (integer periods ≥ 0, default 0), `features` (mapping name → `{description, type, owner, default?, order?}`), optional `closing_key` (name of a STRING copy of the closing, used only by the adapter's exact mode), optional `output` when the task has several outputs. Unknown keys refuse. Validation lives in `bricksmith.mlops.featurestore.config`, standard library only.
- **Feature types.** `double` for numeric, `string` for categorical, `array<double>`, `array<string>`, `map<string,double>`, `map<string,string>`; arrays and maps must declare `order` (the documented meaning of positions/keys). Model input vectors are never stored: no `vector`/binary type is accepted.
- **Closing calendar.** Closings are period-end dates: month-based frequencies use the last day of the month ending the period (quarters end Mar/Jun/Sep/Dec, semesters Jun/Dec, years Dec); `weekly` closings step 7 days; `daily` every date. `shift(closing, n)` moves n periods; a date that is not a closing of the declared frequency is refused, never silently snapped. The Spark engine uses `last_day(add_months(...))` / `date_add`, proved equal to the pure calendar by the remote parity test.
- **Availability lag.** `stamp_availability(rows|frame, table, described=<column>)` writes `closing = shift(described, availability_lag)`: a row is stored at the closing at which it became known, never the closing it describes. A training set therefore needs no lag arithmetic at read time.
- **Training-set builder.** `Lookup(table, features=(...), keys={spine_col: table_col} or entity order, offset=0, prefix="")`. Feature closing = `shift(observation_closing, -offset)`; `offset < 0` (a closing after the observation) is refused at construction. Join is exact equality on keys and closing; missing entity rows yield the feature's declared `default` (else null); an output column produced twice across lookups (or clashing with a spine column) is refused. The spine carries entity keys, the observation closing and an optional label; training and scoring call the same builder and differ only by the spine. Pure (`rows.build_training_set`) and Spark (`spark.build_training_set`) engines return `TrainingSet(data, reads)`.
- **Guards at load.** `check_rows` / `check_frame` refuse null or duplicate primary keys, closings not aligned to the frequency, and missing or mistyped declared feature columns. The plan derives the write options of a `feature_table` task when absent — `write: replace_partitions`, `partition_by: [closing]`, `keys: entity_keys + [closing]` — and reports a conflicting declaration as `invalid_feature_table`. `replace_partitions` with declared `keys` now runs the storage layer's existing no-null and unique-key input checks, so a duplicate primary key fails the Spark load even when the task skipped the check helper.
- **Reproducibility.** `reads` maps each feature table read to its Delta version (Spark, via `bricksmith.storage.current_version`) or to a SHA-256 fingerprint of its canonical rows (pure), ready to log as MLflow inputs.
- **Adapter.** `featurestore.uc` imports `databricks.feature_engineering` only inside its functions (extra `features`). `publish_primary_key(spark, table)` sets NOT NULL and `PRIMARY KEY (entity..., closing)` (with `TIMESERIES` on the closing only in `timeseries` mode). `feature_lookups(lookups, tables, mode)` requires an explicit `mode`: `exact` looks up on entity keys + the declared STRING `closing_key` (exact match), `timeseries` uses `timestamp_lookup_key` (as-of join, documented as not exact). `create_training_set(client, spine, lookups, tables, mode=..., label=...)` wraps the client so `log_model` lineage works. No Feature Views.
- **Write strategy.** Replace by closing (`replace_partitions` on the closing column): re-running a closing replaces only that closing.

## Alternatives Considered

- **Databricks Feature Engineering as the core store.** Lost: a DATE lookup key must be TIMESERIES (as-of, not exact) or a STRING copy; Feature Views are public preview and refuse date entity columns; it would make a workspace product a requirement for offline tests. Kept as an optional adapter.
- **Event-time as-of joins.** Lost: credit-style batch models read the value known at a closing; as-of over approximate event time is exactly the skew the problem describes. Left as a future `timeseries` mode (Out of Scope).
- **Keep per-model feature construction (`mlops/reference.py`, `mlops/spark.py`).** Lost: no reusable contract, no availability lag, training and scoring diverge.
- **Frozen training copies of feature tables.** Lost: invites training/serving skew; Delta versions in `reads` give reproducibility without copies.

## Open Decisions

- **Live Feature Engineering proof.** Whether the adapter also gets a live remote proof (the client may not be installable or usable on the free workspace). Decided during 4.1: attempt it only when the remote environment can import `databricks.feature_engineering`; otherwise the adapter stays proved by the fake-client unit tests and the evidence page says so.
- **Weekly closing anchor.** Weekly closings currently step 7 days from any declared closing without a weekday anchor; whether a project needs a declared anchor weekday is decided by the first real weekly use (spec 79/84), not here.

## Risks

- Pure and Spark calendars diverge at month ends (e.g. Feb 28/29) → parity test with month-end and leap-year closings on the free workspace.
- Adding key checks to `replace_partitions` with declared `keys` fails runs that previously wrote duplicates silently → intended guard; documented in the guide; only tables that declare `keys` are affected.
- ACCEPTED — the adapter may be proved only against a fake client on the free workspace; a Feature Engineering API change surfaces at the first live use. The adapter is thin and optional.
- `uv.lock` churn from the new extra → lock updated in the same task, gate runs on the lock.
