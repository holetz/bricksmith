## Problem

Unmatched rows with null keys are counted but never sampled in cardinality failures.

Reproduction (2026-10-16): `run_check(Check.cardinality("a", expect="many_to_many",
require_match=True), [{"a":None}], [{"a":None}], sample_limit=5)` fails with `unmatched_rows=1`
but `samples=()`; with mixed rows `unmatched_rows=4` while only `{'a':5,'b':5}` is sampled.
Cause: `src/bricksmith/quality/checks_rows.py:51` adds `lnulls` to the count while the samples at
`:59-61` come from `lcounts`, which excludes null keys; `checks_spark.py:65-66` has the same shape.

Consequence: the failure reports rows it cannot show, so an operator cannot find the offending
null-key rows from the result.

## Proposal

- A cardinality check with `require_match=True` that fails on unmatched rows includes the unmatched null-key rows in `samples`, so every counted unmatched row is representable by a sample.
- Null-key samples are distinct key dicts carrying `None` values; the Python and Spark engines agree on content and ordering (keys with nulls first, per column), bounded by `sample_limit`.
- `observed` counts, problem messages and the no-sample behavior without `require_match` or `sample_limit` are unchanged.

## Out of Scope

- Changing how null keys are counted (`unmatched_rows`, invalid groups): the count was correct, only the samples were incomplete.
- Grain sampling of null-key rows and accepted-values, boolean, freshness corrections: sibling members of epic 47.
- Per-row (non-distinct) samples: existing samples are distinct keys and stay so.

## Design

Rule: the samples of an unmatched-rows failure are the distinct keys of every row counted in `unmatched_rows`, null-containing keys included. The count and the samples must derive from the same population.

- Python engine: `_key_stats` drops null keys from `counts`, so `_cardinality` builds the null-key sample set separately from the rows (distinct tuples with any `None`), and merges it with the unmatched non-null keys. Order: sort by per-column `(value is not None, repr(value))`, which puts nulls first like Spark ascending order.
- Spark engine: `lonly` excludes null-key rows; the sample frame is `lonly` united with `frame.where(_null_any(cols))`, selected on the key columns and distinct, then ordered and limited by `_keys` (ascending sort puts nulls first).
- Alternative weighed: emit one sample per null row instead of distinct keys; rejected, existing samples are distinct and bounded.
- Alternative weighed: drop null rows from the count; rejected, the existing contract (and test) says null data keys fail a required match.

## Alternatives Considered

- Mark null-key rows by a separate `null_key_samples` observed field: rejected, it changes the result shape for a defect fix and splits what an operator reads.

## Open Decisions

- none — sample ordering is settled above (nulls first, per column).

## Risks

- Existing sample ordering for non-null keys shifts from `repr` of the tuple to per-column `repr`: ACCEPTED — both are lexical, only multi-column edge cases may reorder; existing tests guard it.
- Spark path is unverified remotely: ACCEPTED — remote proof is unavailable in this wave and is reported as such.
