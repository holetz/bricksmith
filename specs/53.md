## Problem

The row and Spark quality engines order bounded samples differently, so with a `sample_limit` that truncates they return different rows. Pre-existing on main; reproduced 2026-10-17 by the epic #47 correctness review on PR #20 (spec #46).

Reproduction: `run_check(Check.cardinality('a', expect='many_to_many', require_match=True), …)` with unmatched keys `2` and `10` and `sample_limit=1` returns `({'a': 10},)`; with strings `['apple', "zed's"]` it returns `({'a': "zed's"},)`. Cause: `src/bricksmith/quality/checks_rows.py:63` (PR branch) sorts by `repr(v)`, a text sort (`'10' < '2'`, `"` before `'`), while `checks_spark.py:41` uses `orderBy(*cols)` on the values and would pick `{'a': 2}` and `'apple'` (Spark side read, not run).

Consequence: #46 and #48 promise row/Spark parity on sample content and order; it fails whenever samples are truncated, for numbers and quoted strings alike. Audit every row-engine sample sort (grain, cardinality, comparison). Nulls-first must stay. Also correct #46's `## Outcome`, which says non-null values sort before nulls; the code and test put nulls first. Depends on #46 merging; serialize before #48, which edits the same files.

## Proposal

- Every row-engine quality sample (grain duplicates, cardinality unmatched keys, accepted-values offenders) is ordered by value, nulls first, matching Spark `orderBy` ascending.
- With a truncating `sample_limit`, the row and Spark engines return the same rows for numbers and strings.
- Regression tests pin the numeric (`2` before `10`) and quoted-string (`'apple'` before `"zed's"`) cases for each of the three sorts.

## Out of Scope

- Spark-side code: `checks_spark.py` already orders by value and is not touched.
- Changing nulls-first: it matches Spark ascending and stays.
- Correcting spec #46's `## Outcome` wording (nulls sort first, not last): that is a spec-store edit outside the declared files; parked as a discovery.
- Cross-type total ordering beyond a deterministic fallback: Spark columns are single-typed.

## Design

- Durable rule: a row-engine sample sort uses `_value_key(v)`, never `repr`. The key ranks None first, then numbers (bool, int, float, Decimal) by value, then str by text, then anything else by `(type name, repr)` so the order is deterministic and never raises on mixed types.
- Tuple keys sort column by column, as Spark `orderBy(*cols)` does.
- Accepted-values dedupes by `repr` (kept, so equal-repr values collapse as before) and then sorts the distinct values by `_value_key`.
- Grain sorts the key tuples by the element-wise key instead of `key=repr`.

### Mapa de dependências (2026-10-17)

- `checks_rows.py` is called from `run_check` in the quality package; `checks_spark.py` is the parity reference and is unchanged. Spec #48 edits the same files and is serialized after this one.

## Alternatives Considered

- Sort in Python with `key=lambda v: (v is not None, v)`: raises on mixed types and on None ties; rejected for the ranked key.
- Make Spark sort by `repr`-like text: would degrade Spark and diverge from its natural order; rejected.

## Open Decisions

- none — the nulls-first and by-value order are fixed by Spark ascending semantics; mixed-type columns use the deterministic fallback.

## Risks

- Float NaN compares unordered in Python: ACCEPTED — Spark places NaN last, but NaN keys in quality samples are a rare edge outside this spec.
- Mixed-type columns order differs from Spark: ACCEPTED — Spark columns are single-typed; the fallback only guarantees determinism.
