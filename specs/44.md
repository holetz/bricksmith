## Problem

The catalog guide says "nothing is time dependent", but `src/bricksmith/catalogdocs/cli.py:22`
calls `load_graph(args.project)` without `today`, so graph validation falls back to the current
UTC date (`src/bricksmith/graph/build.py:260`).

Reproduction (synthetic project with one `[[exemptions]]` entry expiring 2026-12-31, 2026-10-16):
with `today=2026-10-16` the catalog carries `('warning','unused_exemption','x:y',…)`; with
`today=2027-01-01` it carries `('error','expired_exemption','x:y','exemption expired on 2026-12-31…')`.

Consequence: the same project renders different bytes on different days, breaking the
deterministic offline catalog contract of spec 3 (diffs and reviews churn without changes).

## Proposal

- `catalog render` output depends only on the project files and the registry, never on the wall clock.
- A project with an `[[exemptions]]` entry renders the same bytes before and after the entry's expiry date.
- The guide's statement that nothing in the catalog is time dependent stays true and says how exemptions are treated.

## Out of Scope

- Changing exemption expiry in `bricksmith graph validate` and other gates: expiry stays enforced there, against the current UTC date or an explicit `today`.
- A `--today` flag on `catalog render`: an explicit date is a second input that would again make bytes vary with the caller; deferred until someone needs a dated catalog.
- The registry `--today` and governance `--today` options: they are explicit, defaulted flags of other commands, not catalog output.

## Validation

- `uv run pytest tests/unit/catalogdocs` passes, including a test that renders one project with an exemption through `catalog render` at two different `today` values of the underlying clock and compares bytes.
- The new test fails on the base commit (exemption expiry makes the rendered bytes differ).
- Full gate: `uv run ruff check && uv run ruff format --check && uv run pyright && uv run pytest` exits 0.

## Design

- Rule: the catalog evaluates the graph at a fixed sentinel date, `date.min`, so every exemption counts as live and none as expired. Expiry is a gate concern (`graph validate`), not a documentation concern; the catalog shows exemptions as the project declares them.
- Consequence: an exemption that matches a finding renders as `exempt`, an unmatched one as the `unused_exemption` warning, on every day. The `expired_exemption` error never appears in a catalog.
- The pin lives in `catalogdocs/cli.py` as a named constant passed as `today=`; `load_graph` and `build_graph` keep their documented default of the current UTC date, which other commands rely on.
- Alternative weighed: a today-free `build_graph` mode. Rejected as a wider API change for one caller.
- Binding contract: spec 3 deterministic offline catalog; `docs/guide/catalog.md` "nothing is time dependent".
- Epic 5 policy (resumed 2026-10-15, billing amendment): the offline fix is in scope; no CI, hook or grant is touched; a PR whose only failing check is the billing-refused job merges on verifier PASS and the local gate.

## Alternatives Considered

- Render with the current date and strip date-dependent diagnostics: rejected, it hides real exemption state and needs a filter that can drift from the graph.
- Add a required `--today` to `catalog render`: rejected, it breaks existing invocations and moves the burden to every caller.

## Open Decisions

- none — the sentinel date is decided here; a dated catalog can be added later behind an explicit flag.

## Risks

- A reader of the catalog may not notice an exemption has expired. Mitigation: `graph validate` still fails on it, and the guide says expiry is enforced there.
- A sentinel date could leak into output. Mitigation: the constant is only used for comparison, and the test compares full rendered bytes.
