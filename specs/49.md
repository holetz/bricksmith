## Problem

Comparison diagnostics report mismatch counts but cannot identify the largest numeric errors. src/bricksmith/quality/report.py:76 stores only name and mismatches; quality/spark.py:108 aggregates counts and :114 orders samples by key. quality/rows.py has the same count-first contract. Operators need a bounded opt-in diagnostic that distinguishes small differences from large deviations without collecting full datasets.

Add a small backward-compatible public option to row and Spark comparison: report the maximum finite absolute deviation among mismatches for each numeric column, and, only with explicit sample_limit, provide bounded samples ordered by largest deviation with deterministic key tie-breaking. Keep existing mismatch verdict/tolerance logic and default serialization/output behavior; old reports remain readable and new opt-in reports round-trip. No raw samples by default and no new heavy root dependency. Public DQX supplies broad inspiration for detailed quality failure information (https://github.com/databrickslabs/dqx); this requirement and implementation are independently derived for Bricksmith.

During development make the numeric contract explicit: exclude null/non-numeric/bool/NaN/infinity pairs and non-finite deviations from the finite maximum/ranking while retaining their existing mismatch counts; no eligible mismatch yields an absent/null metric rather than zero; define exact finite Decimal handling and supported range without silent overflow/precision loss; define stable tie order consistent across row/Spark, including composite keys. Sample only mismatches, not matching pairs inside tolerance. Cover positive/negative finite numbers, zero, Decimal precision, null/NaN/infinity, empty/matching inputs, ties, sample bounds and compatible JSON round-trip with synthetic tests. Preserve default key-ordered sample behavior unless the new option is enabled. No drift policy, new mismatch thresholds, dashboards or storage changes.

Expected files: src/bricksmith/quality/report.py, rows.py, spark.py, public API surface as needed; tests/unit/quality/test_compare.py; tests/remote/test_quality.py; docs/guide/quality.md. Depend on the quality-check fix slice to serialize shared remote tests/docs. Remote aggregation stays on Spark; collect only aggregate scalars and bounded samples. All remote runs coordinate serially with the conductor. Complexity medium is a capture estimate; re-scope explicitly if a fully general Decimal contract exceeds a single independently verifiable PR. This capture does not approve or execute the work.

## Proposal

Add one opt-in keyword, `numeric_severity: bool = False`, to `compare`, `compare_rows` and `compare_frames`. When enabled, each numeric column result carries `max_abs_deviation`: the largest finite absolute deviation among that column's mismatches, or null when none is eligible (never zero for "nothing"). When `sample_limit` is also given, `mismatch:<column>` samples are ordered by largest deviation first, then by key ascending, and each sample carries its `abs_deviation`. Without the flag nothing changes: verdicts, tolerance logic, key-ordered samples and serialized output stay byte-identical, and old reports still load.

## Out of Scope

- none — no drift policy, new thresholds, dashboards or storage changes; mismatch verdicts and tolerances are untouched.

## Design

### Mapa de dependências

- `compare.py` dispatches to `compare_rows` / `compare_frames` and gains the pass-through kwarg. `ColumnResult` and `ComparisonReport` live in `report.py` and are consumed by `rows.py`, `spark.py`, `quality/__init__.py` and the CLI (`cli.py` reads reports; defaults must not change). `regression.py` does not use comparison reports.

Deviation contract (identical on both engines):

- Eligible pair: both values non-null, non-bool numbers, finite (no NaN or infinity float or Decimal), and a mismatch under the existing verdict. Others keep their mismatch count but are excluded from the metric and rank after eligible ones in samples.
- Exact path: when neither side is floating (ints, Decimals), deviation is exact `|l - r|`. Row engine uses a wide Decimal context that traps inexact results (raising `QualityError`); Spark casts both sides to a decimal wide enough for the subtraction and raises `QualityError` at plan time when the column types would need more than 38 digits (integral types count as `decimal(20,0)`), so no silent rounding or overflow.
- Floating path: when either side is float/double, the deviation is the IEEE double `|l - r|`; a non-finite result is excluded.
- Serialization: `max_abs_deviation` and `abs_deviation` are plain-decimal strings with trailing zeros stripped (`normalize`, `format "f"`), so `5.00` and `5` agree. Non-numeric columns carry null.
- Order: deviation descending, then key columns ascending (natural value order, Spark `orderBy`); ineligible mismatches last, by key.
- Serialization is opt-in: the report stores `numeric_severity`; `to_dict` adds `numeric_severity: true` and column `max_abs_deviation` only when enabled, so the default dict is unchanged; `from_dict` defaults both to off/absent.

Spark computes the maximum with one aggregate over the existing join (scalars collected only) and ranks samples with a bounded `orderBy(...).limit(n)`.

## Alternatives Considered

- Always compute the metric: rejected, it would change default output and cost an extra aggregate.
- Floats for all deviations: rejected, loses Decimal precision.
- A separate sampling parameter ordering by severity: rejected, one flag keeps the surface small; samples still need `sample_limit`.

## Open Decisions

- none — every item is decided from the finding evidence; the 38-digit Decimal range is the stated supported range and exceeding it raises rather than degrades.

## Risks

- No local pyspark: Spark code is covered by remote tests only; keep expressions minimal and report unavailable remote proof honestly.
- Medium scope with a general Decimal contract: if the Spark decimal-width check grows beyond a simple precision computation, re-scope instead of widening this PR.
