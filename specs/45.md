## Problem

A wrong `--project` path renders an empty catalog and exits successfully.

Reproduction (2026-10-16): `bricksmith … catalog render --project <scratch>/does-not-exist` exits
0, prints nothing on stderr and outputs `"tables": [], "lineage": [] …`. Cause:
`src/bricksmith/tasks/project.py:94` returns an empty `Project` when `bricksmith.toml` is missing,
and the catalog command does not check for it.

Consequence: a typo in a pipeline publishes an empty catalog as a success. Shares
`catalogdocs/cli.py` with spec 44; serialize after it.

## Proposal

`catalog render` checks that `<project>/bricksmith.toml` is a regular file before loading the graph. When it is not, the command raises a `ConfigError` naming the path and exits with `EXIT_CONFIG`, writing no output file and nothing to stdout.

## Out of Scope

- Changing `load_project` or any other command: the empty-project default stays for them.
- Validating the content of `bricksmith.toml`.

## Validation

- The new test fails on the base commit (exit 0 with an empty catalog).
- Full gate: `uv run ruff check && uv run ruff format --check && uv run pyright && uv run pytest` exits 0.

## Design

The check lives in `catalogdocs/cli.py::_render`, before `load_graph`, per epic 47 ## Design: `load_project` (tasks/project.py) is shared and keeps its empty default. Error type is `ConfigError` (exit `EXIT_CONFIG`), the same family `load_project` already raises for an invalid file. The check runs before any output is opened, so no partial file is written.

## Alternatives Considered

- Fail inside `load_project`: rejected, other commands rely on the default.
- `UsageError`: rejected, the path is valid syntax; the project configuration is what is missing.

## Open Decisions

- none — the error type and location are decided above.

## Risks

- Scripts that relied on rendering an empty catalog from a bare directory now fail. Mitigation: that behavior was the reported bug.
