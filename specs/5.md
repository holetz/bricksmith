> # Epic 0001. Deliver the complete bricksmith data and model workflow
> 
> - Status: proposed development plan
> - Date: 2026-10-13
> - First release: 0.1.0
> - Execution state: package foundation present locally; product capabilities not implemented
> - Inputs: [capability review](../planning/capability-review.md),
>   [single-library decision](../decisions/0009-one-library-shared-task-scopes.md) and
>   [independent-development decision](../decisions/0010-behavior-derived-independent-development.md)
> - Delivery contracts: [library, template and plugin](../planning/delivery-contracts.md)
> - Test configuration: [free and corporate environments](../development/databricks-tests.md)
> 
> ## Problem and outcome
> 
> The initial roadmap described discovery, a registry, MLOps and monitoring, but did not define the
> write, execution, evolution, isolation and lifecycle contracts needed to operate them reliably.
> The private reference review exposed useful capabilities and several failure cases that should
> become independent requirements rather than architectural templates.
> 
> Deliver one Python library, a maintainable project template and an optional-to-install Claude Code
> plugin that take a synthetic data project from
> discovery through deployment, safe writes, model development, prediction, monitoring, change and
> retirement. A user must be able to inspect the plan before running it, understand what produced a
> dataset or model, reproduce an experiment and make changes with an explicit impact report.
> 
> ## Implementation inputs and readiness
> 
> The private reference path is not requested or required by this epic. Implementers use only the
> repository's generic requirements, public dependency documentation and independently authored
> examples/tests. No implementation or release task depends on accessing the private source or
> ignored research notes. An unavailable reference is not a blocker.
> 
> This epic defines complete release scope and behavioral acceptance. It is not a final specification
> of every public API, numerical boundary or platform adapter. Close the listed open decisions in
> each child specification before coding; resolve ambiguities from the stated product goals instead
> of translating private methods. BS-17 proves the three artifacts from a clean checkout without
> the reference project or local research files.
> 
> ## Delivery artifacts
> 
> | Artifact | Home | Required release result |
> |---|---|---|
> | Python library | `src/bricksmith` and root manifest | One installable wheel/source archive, public API/CLI and optional integration extras |
> | Project template | `template/` | Copier initialization/update, synthetic example, configuration, tests, deployment and thin optional agent guidance |
> | Claude Code plugin | `plugins/bricksmith/` | Validated manifest, discoverable namespaced skills, local-load/install proof and documented supported library version |
> 
> The companion artifacts use the same release version initially. The library and generated projects
> work without Claude Code; the plugin is a packaged convenience, not a runtime dependency. Other
> agent adapters may be added separately without delaying the three baseline artifacts.
> 
> ## Product constraints
> 
> 1. One distribution, version and release; add capabilities incrementally. Optional extras install
>    external integrations without creating separately released bricksmith products.
> 2. Data, training, prediction, quality and monitoring tasks share discovery, identity, dependency
>    planning and execution. Catalogs and schemas organize domains and ownership; task type never
>    dictates location. Support both shared and optionally dedicated scopes.
> 3. Define tasks and resources once in Python. Native bundle resources are built at validation time;
>    there is no committed generated job/schema YAML or runtime manifest requiring a second build.
> 4. Metadata discovery, registry checks and planning work without remote access or heavy runtime
>    imports. Remote work starts through explicit execution or enrichment.
> 5. Copy no private implementation, fixtures, models, vocabulary, history or organizational policies.
>    Independent synthetic examples and behavioral tests are the implementation specification.
> 6. Every release-bound capability includes a usable public contract, an example, meaningful tests,
>    documentation and the agent workflow needed to operate it. Pure capabilities need no remote
>    tests; platform-dependent behavior requires functional proof on the supported workspace.
> 7. Free Edition is the primary development/test workspace where feasible. An explicitly selected
>    corporate test environment supplies proof for unavailable capabilities, without automatic
>    fallback, production dependencies or importing corporate data.
> 
> ## Scope
> 
> The release includes task discovery and planning, local/deployed runners, Delta writes and schema
> evolution, native resources and jobs, registry and metadata checks, dataset comparison, bounded
> external I/O, isolated experiments, model dataset construction, model lifecycle, monitoring,
> operational reports, governance visibility, catalog documentation, template and agent skills.
> 
> The first connector proof uses one open-source SQL database; it does not promise every driver.
> The governance proof covers declared/applied/verified state and native metadata/grants. Advanced
> masking and row-filter deployment require their own verified platform support and specifications.
> These boundaries must be visible in user documentation and release criteria.
> 
> Corporate business pipelines, regulation-specific formulas, a universal scheduler, streaming
> ingestion, online serving, branded reports and conversational data applications are out of scope.
> Additional drivers and notification providers are tracked extension candidates after 0.1.0.
> 
> ## Architecture contracts to develop before coding
> 
> | Contract | Required behavior | Owning slices |
> |---|---|---|
> | Execution context | Explicit profile/environment, independent bundle target, logical-to-physical mapping, parameters and connection providers; no machine or private-project defaults | BS-01 |
> | Task identity and outputs | Unique logical scope + task identity + parameter variant; output names and physical destinations are separate; conflicting producers are rejected | BS-02 |
> | Metadata graph | Preserve dependency provenance, explicit dynamic reads, external inputs and temporal state reads; report inference limitations | BS-02 |
> | Plan and report | Deterministic order, target set, operations, skipped/unresolved reasons and result states; serializable without importing task runtime | BS-03 |
> | Write contract | Define idempotence, replacement bounds, protected objects, retries, empty input and pre/postconditions per strategy | BS-04 |
> | Evolution policy | Produce a schema/metadata diff; distinguish compatible, incompatible and destructive operations; reconcile only through a declared policy | BS-05 |
> | Job boundary | Every dependency is satisfied inside the job, by an explicit orchestration contract, or as a validated external input | BS-06 |
> | Semantic registry | Configurable naming and semantic constraints with neutral defaults; avoid global singletons and source-specific exception lists | BS-07 |
> | Experiment and model identity | Pin inputs, features, code and artifact versions independently of task folders, Python class paths and schema names | BS-10, BS-11, BS-12 |
> | Monitoring reference | Version fit data, bins, metric configuration, evaluation window and alert policy; computation and persistence are separate | BS-13 |
> | Governance state | Distinguish declaration from application and verification; project-supplied policies and permission principals | BS-15 |
> | Companion delivery | Template and plugin consume public library contracts; coordinated versions; either agent-free or agent-assisted use | BS-16, BS-18 |
> 
> These are behavioral contracts. Class hierarchies, public function names and serialization formats
> remain subject to the slice specifications. Avoid inventing a reusable abstraction before a
> concrete vertical example establishes its need.
>

> ### BS-00. Packaging and delivery foundation
> 
> Depends on: none. Existing baseline: one package, local lint/type/tests/build and leak gate.
> 
> - [x] BS-00.1 Audit the unified package, extras strategy, private classifier, supported Python
>   version and independent-development guidance.
> - [x] BS-00.2 Make CI verify the built wheel and source archive in clean environments, including
>   imports with heavy integrations absent.
> - [x] BS-00.3 Establish the primary Free Edition workspace and optional corporate test destination,
>   validate authentication and synthetic schema/volume cleanup; do not assume unattended auth works.
> - [x] BS-00.4 Verify a minimal native Python resource deployment and record the supported CLI,
>   bundle package, Connect and runtime version matrix.
> - [x] BS-00.5 Implement explicit test-environment preflight from `.env`/CI configuration: profile,
>   expected host, test catalog, compute and concurrency; reject missing selection or conflicting auth.
> - [ ] BS-00.6 Record separate configuration/authentication/compute/deployment proof and feature
>   coverage per workspace; configure free-first CI and explicit corporate runs after auth is proven.
> 
> Acceptance: the installed wheel exposes all capabilities; a minimal job deploys, runs and is
> destroyed; cleanup succeeds on injected failure. Credentials and private content remain absent
> from versioned artifacts. Remote proof is required before calling the workspace setup complete.
> Only the selected environment requires complete configuration. A missing profile cannot activate
> `DEFAULT`, and a free failure cannot start a corporate run. Record unsupported and not-run states
> separately from passing evidence.
> 
> ### BS-01. Context, parameters and lazy integrations
> 
> Depends on: BS-00.
> 
> - [x] BS-01.1 Specify immutable execution context and target mappings with explicit precedence.
> - [x] BS-01.2 Validate typed dates/windows, dataset selectors, segments and write options; reject
>   ambiguous combinations before execution.
> - [x] BS-01.3 Inject Spark, workspace, model-tracking, secret and I/O clients at their point of use.
> - [x] BS-01.4 Define the common CLI foundation, structured errors, stable exit codes and JSON output.
> - [x] BS-01.5 Implement opt-in dotenv loading and free/corporate context selection with documented
>   precedence and unified-auth mapping; avoid process-global profile/session mutation.
> 
> Acceptance: import, help and metadata planning make no remote calls; invalid inputs fail before
> creating a client. Local and deployed entrypoints resolve the same explicit context, and two
> contexts in one process do not share target or parameter state accidentally. Both profiles may
> exist in `.env`, but only the selected environment becomes active. Importing the library neither
> loads `.env` nor authenticates; bundle target `ci` does not decide the workspace by itself.

> ### BS-02. Discovery, identities and dependency graph
> 
> Depends on: BS-01.
> 
> - [x] BS-02.1 Discover task definitions across ordinary project scopes with configurable exclusions
>   and identical rules for data, model and monitoring behavior.
> - [x] BS-02.2 Define stable logical identities, parameterized variants and explicit output ownership;
>   detect duplicate identities and physical output collisions.
> - [x] BS-02.3 Infer supported reads and merge explicit dependencies, external resources and temporal
>   inputs with provenance and coverage diagnostics.
> - [x] BS-02.4 Validate cycles, missing producers, ambiguous references and expiring exemptions;
>   retain the complete graph for planning, jobs and documentation.
> 
> Acceptance: a single schema containing feature, training, prediction and monitor definitions is
> discoverable offline. Synthetic projects cover a helper read, nested tasks, renamed outputs,
> same local task names in different schemas, dynamic reads, earlier-window state and missing edges.
> No valid edge is resolved by an unrelated object's short name.
> 
> ### BS-03. Inspectable execution and reprocessing
> 
> Depends on: BS-02.
> 
> - [x] BS-03.1 Plan root selection and upstream/downstream closure with deterministic ordering,
>   include/exclude filters and reasons for disabled, static or skipped tasks.
> - [x] BS-03.2 Execute with bounded concurrency, result states, retry policy and dependent-task
>   blocking; preserve successful independent branches when another branch fails.
> - [x] BS-03.3 Add dry-run, validated plan application and failed-subgraph replay through the CLI
>   and the common deployed entrypoint.
> - [x] BS-03.4 Attach mutation authorization to explicit objects and operations in a reviewed plan;
>   reject stale targets or changed scope instead of implicitly widening authorization.
> 
> Acceptance: dry-run makes no writes; invalid or incomplete closure never starts. Injected failure
> blocks dependents and produces a serializable report. Replay selects the intended work, and
> authorizing one protected output does not authorize its upstream graph.
> 
> ### BS-04. Storage and task write strategies
> 
> Depends on: BS-01, BS-03.
> 
> - [x] BS-04.1 Implement table I/O and full/static refresh with explicit empty-input and protection
>   policies; report the operation before mutation.
> - [x] BS-04.2 Implement partition replacement and incremental append/merge with declared keys,
>   temporal windows, late-input policy and repeat-run semantics.
> - [x] BS-04.3 Implement SCD2 behavior with validated grain, tracked columns, current-row and
>   interval invariants; specify corrections and removals before implementing them.
> - [x] BS-04.4 Support views, materialized views where available and functions through the same
>   task lifecycle; expose retention,
>   history/restore and pre/postcondition hooks without hidden writes during reads.
> 
> Acceptance: repeated synthetic runs preserve the documented result for every strategy; partition
> reprocessing leaves neighboring partitions untouched. SCD2 has one current row per key and no
> overlapping valid intervals. Protection is checked before target mutation, and retries after
> partial progress follow a documented recovery path.
> 
> ### BS-05. Schema evolution and maintenance
> 
> Depends on: BS-04, BS-07.
> 
> - [x] BS-05.1 Compare declared and live schema/metadata, including nested types, nullability,
>   comments, checks, keys and physical properties.
> - [x] BS-05.2 Plan add/rename/drop/type changes with independent compatibility and precision rules;

> - [x] BS-05.3 Apply ordered migrations with constraint dependencies and required physical table

> - [x] BS-05.4 Make retention, clustering and optimization configurable maintenance operations;

> 
> Acceptance: schema drift cannot cause silent truncation or unbounded replacement. A synthetic
