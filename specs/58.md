## Problem

Reproduced 2026-10-17 by the epic #47 correctness review on main (6f3ef40), range 77e04d9..6f3ef40.

`compare_rows(..., numeric_severity=True)` on `decimal(38,2)` returns `max_abs_deviation '1.5'` (and `'1'` on `decimal(38,0)`), while `spark.deviation_expression` on the same column pair raises `QualityError ... needs 39 digits ...; the supported maximum is 38` (pure-Python guard reached with a stubbed `pyspark.sql.functions`). Cause: `src/bricksmith/quality/spark.py:109`; also `:91`, where an unparsed numeric type defaults to precision 38, so it always raises.

Consequence: `compare_frames(..., numeric_severity=True)` fails as a whole for any `decimal(38,*)` column regardless of values — a common Databricks aggregate type — and the two engines disagree on the same plan. Spec #49 chose to raise from column types; revisit that choice (e.g. a bounded fallback such as double deviation or per-row overflow reporting) with an explicit contract.

## Proposal

Owner decision (2026-10-23, autopilot conductor as delegated owner; see epic #47 ## Design): keep exact Decimal deviation and #49's raise-rather-than-degrade principle, but move the raise from declared column types to actual values. `decimal(38,s)` pairs and unparsed numeric types compute the deviation instead of refusing at plan time; only a row whose actual deviation does not fit 38 digits raises `QualityError` naming the column, and the row engine raises at the same boundary so both engines agree. No lossy double fallback. Update `docs/guide/quality.md`, keep the remote parity test, and record the contract change in ## Outcome.

## Out of Scope

- A double-precision fallback or any rounding of an exact deviation (owner decision: no lossy fallback).
- Changing floating-column deviation, tolerance matching, the report schema or default (non-severity) output.
- Raising from declared types for any numeric pair: no type-level refusal remains, except a decimal scale above 36, which the wide Spark path cannot subtract exactly.

## Validation

- Unit: `compare_rows` on `decimal(38,2)` and `decimal(38,0)` pairs returns the exact deviation (`1.5`, `1`) with severity on; a row whose exact deviation needs more than 38 digits raises `QualityError` naming the column; a within-limit row beside it does not; digit counting ignores trailing zeros.
- Unit: `deviation_expression` no longer raises at plan time for `decimal(38,*)` or an unparsed numeric type (pure-Python guard with a stubbed `pyspark.sql.functions`).
- Remote parity (explicit Free profile, serial, never DEFAULT; reported unavailable if it cannot run): Spark equals the row engine on `decimal(38,s)` data, and both raise at the same boundary.
- Gate: `uv run ruff check`, `uv run ruff format --check`, `uv run pyright`, `uv run pytest`.

## Design

Boundary, shared by both engines: the exact deviation `|l - r|` is representable when its integer digits plus its fractional digits, with trailing fractional zeros dropped, total at most 38 (`MAX_DECIMAL_DIGITS`). A mismatching row beyond that raises `QualityError` naming the column; matching rows never compute a deviation.

Row engine: `absolute_deviation` keeps its exact subtraction and adds the digit count after the exact result; it needs the column name, so the check lives in `_Tally.add`, which already knows the column.

Spark engine: when the common-decimal cast needs at most 38 digits the current expression is kept (it is exact). Otherwise (`decimal(38,s)` pairs, unparsed numeric types) the deviation is built from exact parts: each operand is split into a truncated integer part (decimal(38,0)) and a fractional remainder (`x % 1`, exact), the signs are reconciled by borrowing one unit so both parts share a sign, and the result is the struct `(abs integer part, abs fraction)`, which orders correctly for `max` and `desc`. A per-row overflow flag (integer parts of opposite sign summing to 10^38 or more, or total digits above 38) is aggregated as one more max; the driver raises `QualityError` when it is set. `_as_decimal` rebuilds the exact Decimal from the struct. No subtraction ever exceeds 38 digits, so Spark's precision-loss rules never apply.

## Alternatives Considered

- Double fallback for oversized pairs: rejected by the owner decision (lossy).
- Keep raising from declared types: rejected, it fails every `decimal(38,*)` column regardless of values.
- Per-row null instead of raise: rejected, it silently hides the largest deviations.

## Open Decisions

- none — the owner decision of epic 47 settles the contract; the scale-above-36 limit is parked as a risk.

## Risks

- The wide Spark path cannot be run against a real cluster in this environment; the remote parity test covers it only when a Free profile is available, and its absence is reported, not hidden.
- Decimal scales 37 and 38 would round in the fraction subtraction; they raise `QualityError` at plan time (documented) instead of degrading.
- `CASE WHEN` guarding the integer sum relies on Spark evaluating only the selected branch.
